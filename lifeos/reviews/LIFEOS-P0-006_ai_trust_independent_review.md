## 评审摘要

1. **[事实]** P0-004 已清楚建立“可读、可整理、可建议，不可替用户确认”的 V1 上限，并区分用户原文、外部来源、AI 整理/生成、AI 推断、AI 建议和用户确认状态；对象级确认、来源历史不改写和 L4-L5 排除可进入冻结候选。
2. **[判断]** 六维 Authorization 足以作为 V0.1 的核心授权判定框架，但不能被解释为全部安全约束。敏感级别、接收处理者及其政策版本、保留/删除能力、训练/评估用途和跨项目输出传播必须成为不可绕过的政策属性或前置门槛。
3. **[关键问题]** 当前“撤回 Authorization”“断开 Source”“删除 Artifact/原文”“撤回 Feedback”虽分别出现，但授权撤回后的处理规则仍倾向一律令派生物失效/删除，尚未完整区分停止未来处理、停止活跃使用、撤销保留许可和请求删除。该歧义会造成撤回假象，也可能错误影响用户已确认对象。
4. **[判断]** L1 派生展示与 L3 持久业务写入的概念分界正确，但四类 L3 仍只能冻结为候选白名单上限，不能冻结为 V1 已允许能力。候选 Action/Decision/Link 在 SP-06 证明同步、撤回和用户权威不变量前，应默认按 L1 Derivation 展示。
5. **[事实]** P0-005 的 SP-04、SP-05、SP-06 对运行时授权、撤回/删除传播和状态一致性的主风险覆盖充分；SP-07、SP-08补足可信证据和导出验证。但计划存在审计反向识别、第三方政策资格、跨项目信息泄漏和高风险能力降级测试缺口。
6. **[风险]** “最小审计不保存正文”不自动等于不可泄露；稳定对象标识、路径、细粒度时间、范围组合和错误详情仍可能关联或重识别敏感活动，需要数据最小化、访问控制、保留期和反向识别测试。
7. **[结论]** Gate 3 在原则层面条件通过，Gate 2 条件通过，Gate 1 通过；Gate 4 只在验证计划层面通过，实现可行性尚未通过。P0-004 是合格的冻结基础，但不是可直接无条件冻结的完成版。

## 已通过内容

以下内容可接受，并可在整改后作为 V0.1 冻结基线的一部分：

1. **AI 总能力与权威边界**
   - V1 主体为 L0-L2，L3 仅限小范围、明确授权、可逆的内部候选动作，L4-L5 不进入自动执行。
   - AI 不能替用户确认事实、承诺、Decision、Action、Next Step 或重要 Link。
   - 重大、外部、高影响、难以撤销和高风险动作必须由用户进行对象级、当次确认。

2. **内容身份与转换不变量**
   - 用户原文、外部来源/外部主张、AI 整理/生成、AI 推断、AI 建议和用户确认事实被显式区分。
   - AI 来源身份不会因用户接受而被抹除；接受摘要不等于确认摘要中所有陈述。
   - 自由文本抽取默认只生成候选；结构化明确命令才可按后续 PRD 规则视为用户直接创建/确认。
   - 候选 Action、Decision、Link 的提出者、证据、版本和用户 Feedback 被保留。

3. **Authorization 核心结构**
   - 主体、范围、动作、目的、位置、时效六维能覆盖“谁基于什么授权，为何、在哪里、对哪些数据做什么”的核心判定。
   - 默认拒绝、排除优先、多输入取最严格约束、范围扩大重新授权、任务执行时重检均正确。
   - 本地读取不自动包含云同步，LifeOS 云处理不自动包含第三方模型处理，搜索授权不自动包含摘要、建议、个性化或训练/评估。

4. **Derivation、Feedback 与来源链**
   - Derivation 对精确输入版本、Authorization、处理位置/主体、模型/工作流版本、输出身份、时效和有效状态的最低包络合理。
   - Feedback 以追加历史表达确认、拒绝、纠正、忽略、完成、延期和撤回，不用当前状态覆盖历史。
   - 用户纠正默认只影响对象及明确依赖，不自动泛化为跨项目规则、敏感长期记忆或训练许可。

5. **撤回与删除的底线方向**
   - “活跃使用立即阻断、物理清理状态追踪”是可接受的冻结原则。
   - 向量、全文索引、缓存、队列、提示副本、备份、离线设备和第三方副本均不能成为删除或撤回绕过。
   - 不能把“已停止使用”误报为“所有物理副本已删除”；第三方限制必须在发送前披露并在删除后如实显示。

6. **Obsidian 与处理位置分层**
   - 连接 Vault 仅授权所选范围内的只读接入和已清楚说明的本地必要处理，不等于允许 AI 派生、云同步或第三方模型处理。
   - AI 派生不写回 Vault 原文；目录/文件排除、来源指针、版本和块级定位方向正确。
   - 本地生成式处理也必须透明，不因“发生在本地”而隐藏。

7. **高风险场景与健康依赖**
   - 心理、医疗、法律、财务在 V1 仅限用户请求的信息辅助、整理或草稿，不做主动诊断、评分和自动执行。
   - 高风险 L3-L5 全部排除；不以持续监控或权威口吻制造虚假安全感。
   - 主动建议少量、可关闭、可降频、可忽略，不以焦虑驱动。

## 关键问题

### K-01｜六维授权缺少强制政策包络

- **[事实]** P0-004 将敏感等级、保留期限和数量/频率列为“辅助字段建议”，并用主体/位置/目的处理第三方与训练边界。
- **[判断]** 六维模型在逻辑上够用，但“建议字段”力度不足。仅凭六维匹配仍可能允许把高敏感数据发送给保留策略不合格、默认用于训练/评估或存在未披露接收方的第三方。
- **[风险]** 授权有效不等于处理者有资格接收数据；用户同意也不能修复供应商能力或政策不达标。
- **[建议]** 保留六维作为核心，不新增一串并列“第七至第十维”；新增强制政策包络：数据敏感级别、精确处理者/供应商及政策版本、保留与删除能力、训练/评估开关、接收方/子处理者类别、跨项目/跨目的传播限制。授权判定必须同时满足 Authorization 和处理者资格门槛。

### K-02｜撤回、断开、删除与保留许可语义仍可能混淆

- **[事实]** P0-004 分别描述 Authorization 撤回、Source 断开、Artifact 删除和 Feedback 撤回，也规定撤回后先阻断活跃使用。
- **[判断]** 文档尚未定义每类用户意图的精确效果矩阵。例如撤回“第三方摘要”许可，可能只要求停止未来第三方处理，也可能同时要求删除该用途生成的可识别派生；断开 Vault 也不必然等于删除用户主动保留的 LifeOS 内容。相反，用户发起删除时不能只停止未来处理。
- **[风险]** UI 显示“已撤回”但旧派生仍被其他用途使用，会形成撤回假象；一律删除又可能破坏用户已确认的 Action/Decision 历史。
- **[建议]** 分离并定义四种命令：`revoke_processing`、`disconnect_source`、`delete_content`、`retract_feedback`，并额外表达是否撤回保留许可。每种命令需列明对原文、可识别快照、Derivation、索引、用户已确认业务对象、审计、备份、离线设备和第三方副本的效果。

### K-03｜L1/L3 边界清楚，但 L3 尚未证明值得持久化

- **[事实]** P0-004 以“是否改变持久业务状态”区分 L1 与 L3；D-0040 允许复杂度过高时将 L3 降级为 L1。
- **[判断]** 该分界可接受，但“将候选保存为独立 Action/Decision/Link”会进入同步、冲突、撤回、排序、提醒和审计链，影响远高于纯 Derivation 展示。
- **[风险]** 内部候选对象可能被 UI、检索或排序误认为用户任务，或在离线冲突中覆盖用户确认状态。
- **[建议]** 冻结的只能是 L3 白名单上限和禁止不变量；在 SP-06 通过前，候选默认保留在 L1 Derivation 中。任一 L3 项进入 V1 还需 PRD 指定触发、数量/频率、可见状态、撤销和不影响用户权威状态的验收。

### K-04｜审计最小化尚不足以防止反向泄露

- **[事实]** P0-004 禁止 AuditEntry 保存原文、完整提示、生成正文和可逆向向量；P0-005 要求抽样验证不能重建内容。
- **[判断]** 即使没有正文，稳定对象 ID、文件路径、精确时间、Project 名、细粒度范围和错误堆栈组合仍可能泄露敏感行为或支持关联攻击。
- **[风险]** 审计系统成为独立的隐私数据库，或在导出、客服、日志平台中扩大敏感信息访问面。
- **[建议]** 冻结前补充审计最小字段类别、随机/作用域化不可反推标识、禁止路径和用户内容进入日志、访问控制、导出边界、保留期/删除规则。SP-05 应加入字典攻击、关联攻击和日志/错误链路抽查，而不只测试“能否重建正文”。

### K-05｜第三方处理边界有原则，但缺少“发送前资格判定”

- **[事实]** P0-004 要求披露第三方无法即时或完全删除的限制；SP-04/05 计划建立第三方能力矩阵。
- **[判断]** 披露限制是必要条件，不是充分条件。对凭据、客户机密、高风险内容等数据，某些保留、训练、地区或删除限制应直接使处理不合格，而非让用户点击同意后继续。
- **[风险]** 将不可撤销或用途不兼容的数据发送给第三方后，LifeOS 无法兑现撤回、删除和数据主权承诺。
- **[建议]** 定义供应商/处理者资格门槛与 fail-closed 规则：政策未知或版本变化时暂停对应处理；训练/评估默认不授权；高敏感数据在删除、保留或接收方条件不满足时禁止发送。授权记录需引用实际处理者与政策版本，不能只记“供应商类别”。

### K-06｜跨项目传播与推断泄漏需要显式测试

- **[事实]** P0-004 规定跨 Project 使用需授权、多输入采用最严格约束，且 Project 归属不能放宽 Source 权限。
- **[判断]** 这些规则能约束输入读取，但还需约束输出去向。摘要或建议可能不逐字包含受限原文，却泄露其事实、存在性或敏感推断；把输出保存到另一个 Project 不能被视为自动“去敏”。
- **[风险]** 受限来源通过摘要、向量近邻、候选 Link、恢复包或模型缓存跨 Project 泄露。
- **[建议]** Derivation 必须继承可用范围、允许目的、位置、保留和披露限制；任何跨 Project 展示、保存或再派生都重新判定。SP-04/07 增加非逐字推断泄漏、否定查询、候选 Link 和跨项目恢复包测试。

### K-07｜高风险原则清楚，但实现验证未被显式安排

- **[事实]** P0-004 明确高风险不主动诊断/评分，L3-L5 排除；P0-005 的相关 Spike 未把高风险识别与降级列为独立通过项。
- **[判断]** 原则可进入冻结候选，但技术计划无法证明系统会在混合项目资料、间接表达或错误分类下稳定降级。
- **[风险]** 普通项目恢复流程可能从日常记录中主动生成健康、心理、法律或财务推断，并被保存为长期派生或今日建议。
- **[建议]** 不必新增重型安全平台，但需在后续 AI/PRD 验证任务加入高风险夹具：禁止主动推断/评分、禁止持久化未请求敏感推断、限制主动性、保留用户求助入口，并测试误报/漏报的产品失败模式。

### K-08｜同意疲劳尚未被验证

- **[事实]** P0-004 已识别授权过碎风险，建议按来源/目的合理打包低风险处理；P0-005 将 UI 转译交给体验设计。
- **[判断]** 这是合理工作假设，但尚无证据证明用户能理解 Vault 连接、本地索引、AI 派生、云同步和第三方处理之间的差异。
- **[风险]** 授权过粗会越界，授权过碎会导致机械同意，两者都破坏真实控制。
- **[建议]** 模型冻结不必等待完整 UI，但 Stage 1 PRD/原型冻结前必须完成授权理解测试，并以任务完成率、关键差异理解、撤回可发现性和错误授权率作为护栏，而非点击同意率。

## 必须整改项

以下事项须在 PM 冻结 P0-004 前完成。可以用勘误/规范补充方式完成，不要求本独立评审重写原交付物。

### M-01｜补充 Authorization 强制政策包络

- 保留主体、范围、动作、目的、位置、时效六维。
- 将敏感级别、实际处理者/供应商及政策版本、保留/删除能力、训练/评估用途、接收方/子处理者类别、跨项目传播限制改为强制判定属性或资格门槛，不再只是可选辅助字段。
- 明确：处理者资格失败时，即使存在用户授权也必须拒绝。

### M-02｜补充四类撤回/删除命令及效果矩阵

- 区分 `revoke_processing`、`disconnect_source`、`delete_content`、`retract_feedback`，并说明保留许可是否撤回。
- 明确用户已确认 Action/Decision/Assertion 的处理：不得篡改历史，但证据失效后应退出自动排序/建议依据并进入待复核；用户主动删除该对象时按删除语义处理。
- 明确“撤回完成”“活跃阻断”“物理清理中/失败/供应商受限”“已物理清理”的用户可见状态。

### M-03｜把 L3 冻结范围限定为候选上限

- 四类 L3 只冻结为不得扩大的候选白名单，不视为 V1 已允许能力。
- SP-06 未通过前，候选 Action/Decision/Link 默认留在 L1 Derivation 展示层。
- 后续任何 L3 启用必须有对象级授权/触发、数量与频率限制、撤销、审计和“AI 不覆盖用户权威状态”的自动化测试。

### M-04｜补充审计隐私规范

- 定义允许字段类别、标识符策略、访问控制、保留期、导出与删除边界。
- 禁止原始路径、用户内容、完整提示、生成正文、向量和高敏感错误上下文进入审计/遥测/日志。
- 要求审计测试覆盖关联与重识别风险，而不仅是逐字重建。

### M-05｜补充第三方发送前资格门槛

- 记录实际处理者、用途、地区/接收方类别、训练/评估状态、保留/删除能力和政策版本。
- 政策未知、版本实质变化或资格不满足时 fail closed；不能把披露加确认当成所有高敏感数据的通行证。
- 第三方限制必须在首次发送前可理解地披露，并在撤回/删除后显示真实清理状态。

### M-06｜扩展 Spike 验收缺口

- SP-04：加入敏感级别与处理者资格、政策版本变化、训练/评估默认禁止、输出约束继承、跨项目非逐字推断泄漏。
- SP-05：加入四类命令效果矩阵、审计关联/重识别测试、日志与遥测泄漏检查、供应商受限状态验证。
- SP-06：保留现有对象级状态与 tombstone 测试，并以其结果决定 L3 是否降级 L1。
- SP-07：加入受限来源的非逐字泄漏、证据撤回后的恢复包降级、候选 Project 关系不扩大权限。
- SP-08：加入导出权限、外部内容许可、审计最小字段和已删除/已撤回内容不复活验证。
- 高风险能力降级与同意疲劳另由后续 PRD/AI 安全验证任务承接；不得以 SP-04 至 SP-08 已计划为已验证。
