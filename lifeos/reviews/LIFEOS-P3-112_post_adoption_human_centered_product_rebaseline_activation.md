## 4. 人本双领域自用 MVP 候选定义

### 4.1 一句话定义与用户结果

**一句话定义：** LifeOS 是由用户掌控、可追溯、可纠正的个人长期外脑；它以“人”为主体，结合工作与健康／健身的长期记忆和今天状态，主动补问会改变判断的信息，并给出少量有依据、跨领域、可反馈的建议。

**首个用户结果：** 用户打开首页时，不必先选择 Project；系统能说明今天最值得注意、回答、决定或行动的 1–3 件事，并清楚展示依据、不确定性和用户控制入口。

### 4.2 核心闭环

`多源感知 → 长期记忆 → 当前理解 → 主动提问 → 个性化建议 → 用户反馈 → 记忆与理解更新`

### 4.3 Must / Should / Not Now

**Must**

- 单用户、工作 + 健康／健身两个领域；至少两个清晰 Source，首版可全部为固定合成／脱敏手工输入。
- 表达稳定事实、目标、偏好、约束、当前状态、事件、决定、反馈及未确认 AI 推断。
- 每条重要记忆具有身份、来源、时间、确认状态、事实／推断身份、有效性、适用范围与时效。
- 首页最多 1–3 条建议、0–1 个高价值主动问题；依据不足时先问或降级。
- 至少一个跨领域场景：工作负荷、睡眠／疲劳、膝盖约束和可用时间共同影响当天低风险训练／恢复建议。
- 建议展示“做什么、为什么现在、依据、领域、不确定性、事实／推断身份”，并支持接受、修改后接受、拒绝、忽略、延后和结果反馈。
- 反馈历史追加保留；不得静默覆盖原建议；重要记忆可查看、确认、纠正、失效或删除。
- 健康内容只做低风险生活方式辅助；伤情／持续疼痛／高风险信号时停止激进建议并建议专业评估。
- 关闭重开后记忆、建议身份和反馈历史仍一致；失败关闭、来源与授权边界继续成立。

**Should**

- 解释“为什么问这个问题”和“不回答时如何降级”。
- 支持新发现模式／冲突的候选提示，但 AI 推断必须等待用户确认。
- 复用 P3-111 本地桌面壳和持久化底座；领域语义与 UI 不绑定具体 Schema/API。
- 为后续真实模型保留本地／云／第三方可替换处理合同，但默认关闭。

**Not Now**

- 真实健康或敏感工作数据、Apple Health／穿戴设备／日历／邮箱／GitHub／Obsidian 等真实连接器。
- 真实云或第三方模型、网络、同步、多设备、移动端、外部用户、商业化。
- 医疗诊断、治疗、高影响自动执行、L3-L5、完整 Project 管理系统、重型知识图谱／微服务／多 Agent 平台。

### 4.4 首页、主动提问、建议与反馈合同

- 首页核心问题是：“根据对这个人的长期了解、近期状态和今天条件，现在有哪些事情值得注意、回答、决定或行动？”
- 首页不固定每个领域一张卡，不固定 Project 恢复为主卡；Project 只在相关工作建议中作为上下文。
- 主动问题只在答案会实质改变建议时出现；必须说明原因、允许跳过，不把未回答当作健康默认值。
- 缺少关键状态时输出“信息不足／保守建议／暂不建议”，不得补造睡眠、疼痛、疲劳或可用时间。
- 建议必须引用当前有效且授权可用的记忆／Source；已失效、未确认推断或越权来源不得成为无披露依据。
- 用户反馈分离“认可、实际执行、执行结果、情境偏好、长期候选记忆”，长期泛化必须再次确认。

### 4.5 安全降级与完成定义

- 任何来源、身份、授权、记忆有效性、关键健康状态或处理位置不明时 fail closed。
- 不具备可靠依据时可以没有建议；不得为填充首页而生成。
- 健康建议不得诊断或替代专业医疗意见；高风险信号触发停止和专业评估提示。
- 候选 MVP 完成必须以合成／脱敏数据实际跑通全部七段闭环、一次跨领域判断、一次主动补问、一次建议反馈更新、一次关闭重开恢复，并能逐项追溯来源和身份。
- 该完成定义只形成工程纵向切片准入候选，不等于真实自用价值或 Stage 4。
