## 需要用户确认的事项

### 1. 是否接受 006 的 `Pass with Conditions` 结论？

- PM 建议：接受。
- 可选方向：
  - A：接受，`P0-004` 保持 Accepted but Not Frozen，先做条件整改。
  - B：要求 006 返工，重新评审。
  - C：忽略条件，直接冻结 `P0-004`。
- 不确认的影响：无法决定 AI 权限模型是进入整改，还是直接冻结。

### 2. 是否采用“六维核心 + 强制政策包络”？

- PM 建议：采用。
- 可选方向：
  - A：保留六维 Authorization 为核心，同时增加强制政策包络。
  - B：把敏感级别、处理者政策、训练/评估用途等增加为平行维度。
  - C：继续作为辅助字段。
- 不确认的影响：第三方处理、训练/评估、保留/删除能力可能绕过授权模型。

### 3. 是否正式区分四类用户命令？

- PM 建议：确认区分：
  - `revoke_processing`
  - `disconnect_source`
  - `delete_content`
  - `retract_feedback`
- 可选方向：
  - A：按四类命令建立效果矩阵。
  - B：只区分撤回与删除。
  - C：留到 PRD 再说。
- 不确认的影响：后续 UI、数据模型、删除 Spike 都会混淆“停止处理”“断开来源”“删除内容”“撤回反馈”。

### 4. 是否冻结 L3 仅为候选白名单上限，并在 SP-06 前默认降级为 L1 Derivation 展示？

- PM 建议：确认。
- 可选方向：
  - A：L3 仅作为候选上限；未通过 SP-06 前不进入持久业务状态。
  - B：允许部分 L3 进入 V1 默认能力。
  - C：完全排除 L3。
- 不确认的影响：AI 候选可能被误作用户确认状态，触发 R-0017 / R-0020。

### 5. 第三方处理者资格失败，是否属于硬拒绝？

- PM 建议：确认硬拒绝。
- 可选方向：
  - A：资格失败则 fail closed，即使用户点击同意也不能发送。
  - B：充分披露后允许用户继续。
  - C：只对高敏数据硬拒绝。
- 不确认的影响：LifeOS 可能无法兑现撤回、删除和数据主权承诺。

### 6. 是否将 M-06 纳入后续 Spike 任务卡验收要求？

- PM 建议：纳入。
- 可选方向：
  - A：全部纳入 SP-04 至 SP-08 的补充验收要求。
  - B：只纳入 SP-04 / SP-05 / SP-06。
  - C：暂不修改 Spike 验收。
- 不确认的影响：技术 Spike 可能验证了 happy path，却漏掉非逐字泄漏、审计反向识别、高风险降级等关键风险。

### 7. 是否登记 / 合并新增风险？

- PM 建议：至少新增或合并以下 P0 风险：
  - 撤回处理许可、断开来源与删除内容语义混淆。
  - 授权有效但第三方处理者政策 / 能力不合格。
  - 受限数据通过摘要、推断、候选 Link 跨 Project 泄漏。
- 可选方向：
  - A：按建议登记 / 合并。
  - B：只登记 P0。
  - C：暂不更新风险日志。
- 不确认的影响：后续整改和 Spike 缺少明确风险归属。

### 8. 条件整改后，冻结范围是什么？

- PM 建议：冻结为 **V0.1 原则与语义基线**，不冻结具体技术实现、删除 SLA、供应商能力、授权 UI 或 L3 上线范围。
- 可选方向：
  - A：原则与语义基线先冻结，运行承诺等待 Spike。
  - B：等 SP-04 / SP-05 / SP-06 实测后整体冻结。
  - C：当前直接冻结全部。
- 不确认的影响：后续 Stage 1 PRD 无法判断哪些规则已稳定，哪些仍是条件性需求。

## 可接受内容

可以沉淀为项目共识或后续任务输入的内容：

1. `P0-004` 的骨架是有效的，不需要推倒重来。
2. AI V1 上限仍为“可读、可整理、可建议，不可替用户确认”。
3. 用户原文、外部来源、AI 派生、AI 推断 / 建议、用户确认事实必须持续区分。
4. 六维 Authorization 是核心模型，但必须叠加强制政策包络。
5. 删除 / 撤回必须区分不同用户意图，不能用一个“撤回”概念包打天下。
6. L3 只能作为候选白名单上限；是否进入 V1 默认能力取决于 SP-06 和 PRD。
7. 审计最小化不仅是不保存正文，还要防止对象 ID、路径、时间、范围组合造成反向识别。
8. 第三方处理者资格是发送前门槛，不是发送后披露问题。
