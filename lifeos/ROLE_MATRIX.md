# LifeOS 项目角色与职责矩阵 V0.1

更新时间：2026-08-11

## 使用原则

本文件定义的是项目专业视角，不代表必须增加真实成员或管理岗位。

当前组织方式仍然是：

- 用户：最终决策人
- PM 主会话：项目总负责人，负责节奏、验收、决策记录和范围控制
- 专项任务会话：按任务承担一个或多个专业角色视角

每个专项任务必须指定：

- 主责角色
- 协审角色
- 必须通过的评审关卡

角色不是职位头衔，而是守门责任。任何任务若影响某个角色负责的边界，必须在交付物中显式回答该角色关心的问题。

## Agent 执行角色

本节定义“哪个 Agent 更适合承担哪类任务”。它不改变上方专业角色，也不增加管理层级。

| Agent | 默认定位 | 更适合任务 | 不适合 / 需谨慎任务 | 权限边界 |
|---|---|---|---|---|
| PM 主会话 | 唯一项目负责人 | 任务拆解、验收、决策、账本更新、冻结判断、阶段推进 | 不应替代专项任务完成所有专业细节 | 可更新 PM 账本；可提出冻结 / 阶段建议，但仍需用户最终确认 |
| Codex | 主执行 / 工程 Agent | 工程实现、P0 修复、技术 Spike、测试复跑、evidence 整理、流程文件落地 | 独立复评自己刚完成的工程；高风险冻结前单独自证 | 不得自行改 PM 账本、冻结资产、关闭风险或启动后续任务 |
| WorkBuddy | 独立评审 / 反例攻击 Agent | 独立评审、二轮复评、风险复核、产品 / 体验 / 证据链挑错、文档一致性检查 | 大规模工程改动、需要复杂本地环境的任务需先确认能力 | 不得自行改 PM 账本、冻结资产、关闭风险或启动后续任务 |
| 未来 Agent | 专项辅助 Agent | 由 PM 按能力分派 | 未观察前不得承担高风险最终判断 | 同专项 Agent 边界 |

PM 应根据 `lifeos/AGENT_ROUTING_SCORECARD.md` 中的历史表现持续调整分派建议。

## 核心角色

| 角色 | 主要职责 | 守住的风险 | 典型产物 |
|---|---|---|---|
| PM / 项目总负责人 | 阶段推进、任务拆解、验收、决策记录、范围控制 | 项目失焦、任务失序、决策漂移 | 任务卡、PM Review、决策记录、风险登记 |
| 产品架构负责人 | 产品定位、V1 范围、场景闭环、需求一致性 | 功能堆叠、企业后台化、开发者工具化、IT 运维化 | 产品章程、V1 范围、PRD、信息架构 |
| 数据 / 领域模型负责人 | 核心对象、关系、生命周期、来源、版本、导出语义 | 数据混乱、语义漂移、后期不可扩展 | 领域模型、数据语义、来源/派生/反馈规则 |
| AI 信任与安全负责人 | AI 权限、内容身份、主动性、确认、纠正、撤回、审计 | AI 越界、错误建议、信任崩塌、高风险误用 | AI 权限模型、信任规则、安全边界 |
| 技术架构负责人 | 技术路线、Spike、性能、同步、搜索、模型网关、可替换性 | 技术过重、技术过轻、早期架构锁死 | 技术架构、Spike 计划、风险验证 |
| 用户研究 / 市场验证负责人 | 目标用户、真实痛点、付费意愿、反证、验证计划 | 自嗨、市场假设失真、错误目标用户 | 用户研究、验证计划、商业假设 |
| 体验设计负责人 | 用户理解、信息层级、交互状态、文案、原型可用性 | 系统正确但难懂难用、界面后台化 | 设计审查、原型建议、交互状态清单 |

## 角色边界

### PM / 项目总负责人

负责：

- 维护项目阶段和节奏
- 拆解任务和依赖
- 验收专项交付物
- 记录决策、风险和开放问题
- 判断是否进入下一阶段

不负责：

- 替代专项任务完成所有专业细节
- 在没有专项输入时冻结复杂技术或产品方案

必须确认：

- 产品定位变化
- V1 范围变化
- 技术架构冻结
- 核心领域模型冻结
- AI 权限边界变化
- 商业模式假设变化

### 产品架构负责人

负责：

- 判断功能是否服务 LifeOS 的个人终身外脑定位
- 判断需求是否服务 V1 第一场景
- 控制 V1 范围和非范围
- 防止产品滑向企业后台、IT 运维、开发者工具或普通笔记/任务工具

关键问题：

- 这个方案服务谁？
- 解决哪个核心问题？
- 属于 V1 闭环哪一步？
- 是否破坏产品宪法？
- 是否把长期愿景提前塞进 V1？

### 数据 / 领域模型负责人

负责：

- 守住 `Project`、`Artifact`、`Source`、`Assertion`、`Decision`、`Action`、`Event`、`Derivation`、`Feedback`、`Authorization`、`AuditEntry`、`Link` 等领域语义
- 判断新需求是否乱造概念
- 判断数据是否能表达来源、版本、权限、确认、纠正、失效和导出

关键问题：

- 用户原文在哪里？
- 来源在哪里？
- AI 派生在哪里？
- 用户确认和纠正如何记录？
- 删除、导出、权限撤回如何影响派生物？
- 这个模型会不会被误读成数据库表冻结？

### AI 信任与安全负责人

负责：

- 定义 AI 使用哪些数据
- 区分 AI 生成、AI 推断、AI 建议和用户确认事实
- 定义确认、拒绝、纠正、撤回和失效机制
- 定义 AI 主动性 L0-L5 边界
- 控制心理、医疗、法律、财务等高风险场景边界

关键问题：

- AI 输出是什么身份？
- AI 有什么证据？
- 用户如何核对？
- 用户如何纠正？
- 错了以后如何撤销或失效？
- 哪些动作必须用户确认？

### 技术架构负责人

负责：

- 判断技术方案是否能支撑 V1 闭环和长期扩展
- 设计技术 Spike 验证路径
- 控制早期技术复杂度
- 确保本地保存、同步、搜索、来源追踪、模型可替换等关键能力可验证

关键问题：

- 这个方案是否能在 V1 做出来？
- 哪些风险必须 Spike？
- 有没有过早引入重型架构？
- 有没有未来不可扩展的硬伤？
- Obsidian 只读接入、本地保存、派生失效、权限边界能否落地？

### 用户研究 / 市场验证负责人

负责：

- 检查目标用户和问题是否真实
- 设计访谈、原型测试和商业假设验证
- 收集反证
- 防止团队只基于内部想象推进

关键问题：

- 用户现在如何解决？
- 这个问题是否高频/高价值？
- 用户是否愿意导入数据？
- 用户是否愿意学习和付费？
- 哪些证据会推翻当前判断？

### 体验设计负责人

负责：

- 确保复杂语义能被用户理解
- 审查首页/今日页是否表达“今天从哪里继续”
- 审查原文、来源、AI 建议、确认状态是否可见
- 审查空状态、错误态、离线态、权限态、响应式状态

关键问题：

- 用户一眼能否看懂这是原文、AI 建议还是外部来源？
- 今日页是否压迫或制造焦虑？
- 交互是否支持确认、忽略、纠正和撤回？
- 页面是否像个人外脑，而不是后台系统？

## 阶段参与

| 阶段 | 必须参与角色 |
|---|---|
| Stage 0 地基定义 | PM、产品架构、数据/领域模型、AI 信任与安全、技术架构、用户研究 |
| Stage 1 V1 定义 | PM、产品架构、体验设计、数据/领域模型、AI 信任与安全 |
| Stage 2 原型与技术 Spike | PM、体验设计、技术架构、数据/领域模型、AI 信任与安全 |
| Stage 3 MVP 开发 | PM、技术架构、体验设计、数据/领域模型、AI 信任与安全 |
| Stage 4 Alpha/Beta 验证 | PM、用户研究、产品架构、体验设计、技术架构 |
| Stage 5 商业化准备 | PM、产品架构、用户研究、技术架构、体验设计 |

## 任务默认角色映射

| 任务类型 | 主责角色 | 协审角色 |
|---|---|---|
| 项目章程 / 产品宪法 | 产品架构负责人 | PM、AI 信任与安全负责人 |
| 目标用户 / 市场验证 | 用户研究 / 市场验证负责人 | 产品架构负责人、PM |
| 核心领域模型 | 数据 / 领域模型负责人 | AI 信任与安全负责人、技术架构负责人 |
| AI 权限与信任 | AI 信任与安全负责人 | 数据 / 领域模型负责人、产品架构负责人 |
| 技术架构 / Spike | 技术架构负责人 | 数据 / 领域模型负责人、AI 信任与安全负责人 |
| PRD / V1 范围 | 产品架构负责人 | 体验设计负责人、数据 / 领域模型负责人、AI 信任与安全负责人 |
| 原型 / 首页 / 交互 | 体验设计负责人 | 产品架构负责人、AI 信任与安全负责人 |
| 商业 / 定价 / Beta | 用户研究 / 市场验证负责人 | 产品架构负责人、PM |

## 默认任务到 Agent 映射

| 任务类型 | 默认推荐 Agent | 交叉验证建议 |
|---|---|---|
| 工程实现 / 修复 / 测试 | Codex | WorkBuddy 后续独立评审 |
| P3 快车道 P1 / P2 工程补丁 | Codex | WorkBuddy 可提前准备反例清单，但不得并行修改工程文件 |
| P3 快车道独立复评 / 反例清单 | WorkBuddy | 发现 P0 必须回到 PM 主会话，不得自行要求 Codex 直接修 |
| 技术 Spike / 性能验证 | Codex | WorkBuddy 复核报告与 evidence 支撑 |
| 独立评审 / 复评 | WorkBuddy | Codex 仅作测试复跑辅助，不给最终评审结论 |
| PRD / IA / 产品规则 | 由 PM 按重心选择 Codex 或 WorkBuddy | 另一个 Agent 做范围和风险复核 |
| 体验 / 文案 / 设计审查 | WorkBuddy 优先 | Codex 可补结构化整改任务 |
| 项目流程和模板维护 | Codex | PM 自行验收 |

## 交付物要求

每个专项交付物必须包含：

- 主责角色视角下的结论
- 协审角色视角下的风险
- 必须通过的评审关卡
- 需要 PM 或用户确认的事项

若专项任务没有覆盖其指定角色的关键问题，PM 主会话应标记为 Rework 或 Partial。
