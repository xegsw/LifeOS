# LifeOS External Agent Briefing Pack

更新时间：2026-08-22

用途：给 Codex 以外的专项 Agent（例如 WorkBuddy）快速进入 LifeOS 项目上下文。它是轻量同步包，不替代 `AGENTS.md`、`CURRENT_STATUS.md`、任务卡或 PM 主会话决策。

## 1. 项目一句话

LifeOS 是个人长期使用的“终身外脑”，用于承接个人原始记录，连接知识、行动、项目、领域和 AI 辅助思考。它不是企业管理后台，不是 IT 运维平台，也不是单纯任务管理器、笔记软件或聊天机器人。

## 2. 当前组织方式

LifeOS 工作区由用户本人拥有并明确授权维护。涉及安全、权限、撤回、删除或负向反例的工程任务，默认只可在当前任务卡指定的本地工作区、候选代码和合成测试数据内用于防御性代码审查、缺陷修复与回归验证；这项背景不授予任何新权限，具体范围、只读资产、停止条件和用户确认边界仍以当前任务卡为准。

- 用户：最终决策人。
- PM 主会话：唯一项目负责人，负责方向、阶段、任务拆解、验收、账本更新、冻结和风险关闭。
- Codex / WorkBuddy / 其他 Agent：专项任务执行或独立评审 Agent，只完成任务卡指定范围。

外部 Agent 可以产出交付物、做评审、提出风险和建议；但不能自行更新项目账本，不能冻结资产，不能关闭风险，不能启动后续任务。

### 任务卡投递授权

PM 创建任务卡只代表登记。用户把任务卡路径发送给本专项会话（新建或 PM 指定）时，即授权本会话在任务卡限定目录和范围内执行；无需等待额外口令。首份会话报告必须记录该路径、会话类型和接收时间。

若仅在 PM 主会话提及路径、查看路径或事后提交交付物，则不是专项执行授权。真实个人数据、真实 DB、真实用户路径／文件、Vault、Tauri/IPC、网络、云／第三方、同步、多设备、L3、外部用户、风险／冻结／基线／Stage 4 等任务卡列明的重大事项，仍须在投递前另有用户明确确认；任务卡路径不能覆盖这些例外。

P3-067 后形成的能力包原则在 D-0516 后升级为“结果级任务”：同一 Task Contract 内一并完成实现、回归、动态验证、Evidence／Manifest、同范围修正和 PM 验收，不拆治理微任务。普通任务不自动要求独立评审或用户逐任务采纳；L3/Gate 和 PM 有具体触发事实时才独立评审。

自 P3-074 起，执行侧须在提交 PM 前完成包内自检：干净副本中的首次／幂等／重启演练、失败与拒绝审计、静态关闭态、只读资产 hash，以及验收标准→测试→Evidence 矩阵；须保留可运行 runner／测试、逐项结果、日志、快照、hash、Manifest 与复跑说明。此类同范围发现应在原能力包内解决。只有 PM 或独立评审发现实质 P0/P1、合同违反、Evidence／独立性不足、越权／范围扩大、真实能力关闭失效或影响完成定义的 Unknown／Not Implemented，才形成正式 Rework；不降低任何独立性或用户确认要求。

D-0516 后采用轻量风险分级治理：长期质量原则持续有效；L0/L1/L2 使用任务卡内嵌 Task Contract，用户一次“创建／开始”授权合同内执行，不单独生成 ABF；只有 L3/Gate 使用 Frozen ABF。新反例必须映射到长期原则或 Task Contract，不得移动验收终点。

PM 首次未通过时一次性列明合同内 Closure List，原任务内收口，不重复授权；不使用统一两轮 Rework 上限。只有 Task Contract／ABF 或结果／风险／数据／入口／权限／架构／Schema/API／冻结／阶段边界必须变化，或历史无法可信恢复时才新建任务。完整规则见 `lifeos/ACCEPTANCE_GOVERNANCE.md`。

## 3. 必读入口

每次专项任务开始前，读取最小启动包：

1. `AGENTS.md`
2. `lifeos/CURRENT_STATUS.md`
3. 当前任务卡：`lifeos/tasks/{TASK_ID}.md`
4. L0/L1/L2 的内嵌 Task Contract；L3/Gate 才读取任务卡引用的 Frozen ABF
5. 任务卡明确要求的模板

外部 Agent 还必须读取本文件。随后只读取任务卡明确列出的直接输入材料和定向规则章节；独立评审、P0/P1、删除／撤回／权限、风险关闭、工程基线恢复、真实能力、冻结或阶段切换任务，必须按任务卡补读其列出的高风险规则和主账本材料。

不要主动读取完整历史。若上下文不足，先列出缺少哪些文件和原因，等待 PM 或用户补充。

## 4. 当前阶段摘要

项目处于有限 Stage 3 / 自用 MVP 最小切片条件准入执行。技术架构 V0.1 合同已冻结；正式外部用户验证线暂停；当前工程主线围绕 P3-001 合成数据最小纵向闭环的返工、复评和风险关闭。

以 `lifeos/CURRENT_STATUS.md` 为最新状态入口；如它与 `TASK_REGISTRY.md`、`FREEZE_STATUS.md`、`DECISION_LOG.md` 冲突，以后三者为准并回报 PM。

## 5. 核心产品规则

- 用户拥有自己的数据。
- 用户原文不可被 AI 静默改写。
- 必须区分用户原文、AI 生成内容、AI 推断或建议、外部引用来源。
- AI 可以主动帮助用户，但重大行动必须经过用户确认。
- 系统应增强用户长期掌控感，而不是制造焦虑依赖。
- V1 优先做好记录、整理、检索、今日重点和下一步行动，不追求一开始全知全能。
- 原始数据是资产；向量、摘要、分类、关联等派生产物应可重建。
- 模型和供应商必须可替换，不能把核心能力绑死在单一模型或平台上。

## 6. Agent 权限边界

专项 Agent 默认允许：

- 读取任务卡指定材料。
- 创建或更新任务卡指定的交付物。
- 在明确授权的工程任务中运行脚本、测试和生成 evidence。
- 在评审任务中做只读复核、反例分析和风险判断。

专项 Agent 默认禁止：

- 修改 `CURRENT_STATUS.md`、`TASK_REGISTRY.md`、`FREEZE_STATUS.md`、`DECISION_LOG.md`、`RISK_LOG.md`、`OPEN_QUESTIONS.md`。
- 冻结产品、PRD、原型、技术架构、数据模型或 AI 权限边界。
- 自行关闭风险或宣布进入下一阶段。
- 自行启动后续任务。
- 处理真实敏感数据、真实 Vault、真实云服务、真实第三方模型或付费资源，除非任务卡明确授权。

## 7. Codex / WorkBuddy 默认分工

- Codex：优先承担工程实现、修复、技术 Spike、测试、evidence 整理、可运行验证。
- WorkBuddy：优先承担独立评审、反例攻击、风险复核、文档一致性审查、产品 / 体验 / 证据链挑错。

PM 可以根据历史交付质量调整分派建议。执行 Agent 和独立评审 Agent 应尽量不同，避免自证循环。

## 8. 交付与回复要求

完整交付物必须写入文件：

- 研究 / 补丁 / 工程报告：`lifeos/deliverables/`
- 独立评审：`lifeos/reviews/`
- 工程 evidence：`lifeos/engineering/{TASK_ID}/evidence/` 或任务卡指定目录

聊天回复只输出：

- 任务完成摘要
- 交付物路径
- evidence / 预检路径（如有）
- 是否需要 PM 决策

不要在聊天中粘贴完整报告、完整日志或长篇历史。

## 9. 如果无法访问项目文件

如果外部 Agent 无法直接访问项目目录，应要求用户至少提供：

1. 本文件内容或最新版截图 / 文本。
2. `lifeos/CURRENT_STATUS.md`。
3. 当前任务卡全文。
4. 任务卡列出的直接输入材料。

仍然不要让外部 Agent 自行根据记忆补全重大项目规则。
