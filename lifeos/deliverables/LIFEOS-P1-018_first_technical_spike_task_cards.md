# LIFEOS-P1-018｜首批技术 Spike 任务卡：SP-01 / SP-02 / SP-03

## 1. 任务边界与结论摘要

- **[事实]** 当前处于 Stage 1；V1 范围、核心领域语义和 AI 权限与信任语义已冻结，但技术架构仅为候选，MVP 开发仍为 `Blocked / Not Allowed`。
- **[事实]** P1-015、P1-016、P1-017 已分别给出最小切片准入、端到端流程和 Obsidian 条件需求；本任务只将其转成可执行、可复核、可失败的技术验证合同。
- **[建议]** 先冻结本批 Spike 的“测试合同”，不冻结实现：SP-01 与 SP-03 可基于共用夹具并行启动；SP-02 的扫描/解析准备可并行，但其正式结论依赖 SP-01 的最小可靠存储语义和 SP-03 的统一身份包络。
- **[建议]** `Pass` 只表示任务卡列明的风险被证据证明；`Pass with Conditions` 仅允许明确的非底线缺口在限定范围内继续，须记录条件、影响和截止任务；任何 P0 不变量失败均判 `Fail`。
- **[事实]** 本文件未执行 Spike、未写代码、未连接真实 Vault、未处理真实敏感数据，也不构成 Obsidian 实现承诺、技术架构冻结或 Stage 3 准入。

## 2. 首批 Spike 总体策略

三项 Spike 共用一个确定性测试合同和结果包：SP-01回答“能否可信保存与恢复”，SP-02 回答“能否只读接入并维持来源身份”，SP-03 回答“能否从输出反查输入并正确失效”。验证只使用合成、脱敏或可丢弃数据；实现可以替换，断言不可因框架选择而改变。

统一结果判定：

| 结论 | 判定规则 | 后续含义 |
|---|---|---|
| **Pass** | 必测及失败场景完成；全部 P0 断言通过；证据包可复跑、可复核 | 仅解除该 Spike 对应的条件阻断，不自动准入真实敏感数据或正式开发 |
| **Pass with Conditions** | P0 断言全部通过，仅平台覆盖、体验预算或 Should 项存在有界缺口；已有降级、负责人和复验条件 | 只在记录的设备、数据类型和能力边界内继续；PM 决定是否接受 |
| **Fail** | 任一 P0 断言失败；出现数据丢失/覆盖、早报保存、越界读写、身份混淆、证据链漏报、不可解释全库失效，或证据不可复现 | 停止对应真实数据/产品承诺，执行降级；不得以“后续补”放行 |

每项 Spike 证据包必须包含：任务结论、固定数据集及版本、环境/依赖/配置、运行说明、测试矩阵、断言结果、原始日志与失败样例、性能/资源数据、清理说明、已知限制、对 V1/风险/架构候选的影响。日志和 AuditEntry 夹具不得包含可还原原文、完整路径、Project 名、完整提示/输出或可枚举标识。

## 3. 共用夹具与统一语义口径

### 3.1 确定性夹具包

夹具版本建议固定为 `fixture-pack-v1`：

1. 3 个个人 Project（P-A/P-B/P-C），含跨 Project 和无 Project 材料；文本、链接、文件指针；同一 Artifact 两个版本；可达/不可达 Source。
2. 身份样本：LifeOS 用户原文、Obsidian/外部来源原文、外部主张、AI 整理、AI 未确认候选、用户确认对象；身份不因展示或 Feedback 被覆盖。
3. 状态样本：允许/拒绝/过期/撤回 Authorization；确认、编辑、拒绝、纠正、完成、延期、撤回 Feedback；有效/stale/invalid/review_required Derivation；删除墓碑。
4. 确定性假模型，只产生固定恢复包和至多一个候选，不调用真实模型、云服务或第三方 API。
5. 模拟 Vault：多目录 `.md`、正常/异常/重复 YAML、标签、标题/块引用、Markdown/Wikilink、嵌入、附件指针、破损链接、同名/同内容文件、乱码、隐藏项、`.obsidian`、排除目录和越界符号链接；变化脚本覆盖新增、修改、重命名、移动、复制后删除、并发修改/删除、离线期间变化和暂不可达。
6. 故障夹具：写前/写中/提交后/回执后强杀、磁盘满、I/O 失败、重复提交、长读、备份恢复、漏 watcher 事件和来源断开。

### 3.2 统一对象与状态合同

- `Source` 表达来源容器与授权边界；`Artifact` 表达具体内容；`ArtifactVersion` 是测试映射中的不可覆盖版本语义，不新增冻结对象。
- 所有对象使用夹具内稳定、不含语义的 `object_id`；每次内容变化生成新 `version_id` 和内容校验值。路径是可变定位信息，不是唯一永久身份；相同内容也不等于同一 Artifact。
- `Derivation` 至少引用精确输入版本、目的、主动性/输出身份、Authorization/政策版本、处理位置/主体、工作流/模型版本、生成时间、有效状态、替代关系及输出约束包络。
- `Feedback` 是追加事实；用户确认产生或更新用户权威对象，但不改写原文和 AI 来源身份。来源身份、用户认可、业务状态、证据状态、派生状态正交保存。
- `Authorization` 使用主体、范围、动作、目的、位置、时效六维判定并默认拒绝；Project、文件夹、标签、双链或 Link 均不得扩权，多输入继承最严格限制。
- 重要 `Link` 保存建立者/来源、确认状态和有效性；`AuditEntry` 仅记录作用域化引用、动作类别、政策版本、结果/原因码及阻断/清理状态。
- 四类命令 `revoke_processing`、`disconnect_source`、`delete_content`、`retract_feedback` 不互相冒充；恢复、重连和重导入先应用撤回、墓碑及用户权威状态。

### 3.3 共用 E2E 断言

复用 P1-016 的 E2E-01～07：在线/离线捕获与耐久回执、无 Project 后手选归属、合法子集恢复与明确缺口、候选拒绝/纠正后的失效、撤回/删除活跃路径零命中与不复活、部分导出披露。SP-01 至少执行 E2E-01/02/06 的保存与恢复段；SP-02 执行 E2E-04/06 的来源段；SP-03 执行 E2E-01/03/04/05/06/07 的证据段。

## 4. SP-01 技术 Spike 任务卡

### 4.1 编号、名称、风险与目标

- **编号/名称：** SP-01｜本地可靠落盘、离线捕获、备份恢复。
- **风险：** “已保存”早于耐久提交、故障造成原文丢失/半写/覆盖、重复提交，或备份恢复复活已删内容。
- **目标：** 证明无网络时可保存原文；只有耐久提交后返回“已保存”；故障和一致快照恢复后，确认记录、版本、墓碑及撤回状态完整。

### 4.2 范围、非范围与输入

- **范围：** 最小捕获写入、版本与幂等语义；保存状态；强杀/磁盘/I/O 故障；长读与后台索引影响；一致备份、完整性检查、恢复与墓碑优先。
- **非范围：** 完整 UI、云同步、多设备一致性、正式附件架构、生产备份 SLA、数据库/框架冻结。
- **输入：** P0-005 SP-01；P1-015 保存底线；P1-016 第 8 节；共用 `fixture-pack-v1`。
- **夹具要求：** 至少 1,000 条含重复幂等键和两版本原文的确定性记录；四个强杀时点；磁盘满/I/O 失败；活跃写入期间快照；带删除墓碑、撤回 Feedback 和待同步状态的恢复包。

### 4.3 必测与异常场景

1. 在线/离线捕获均经历“编辑中→保存中→耐久提交后已保存”；本地已保存与待同步分离。
2. 写前、写中、commit 后、UI 回执后循环强杀；重启后核对确认集合、hash、版本和幂等结果。
3. 磁盘满、I/O 错误、重复提交、时钟偏移时不早报、不覆盖旧版，且返回可行动错误。
4. 长读/后台索引并发下记录输入延迟、日志增长及恢复能力；验证输入主路径不被冻结。
5. 活跃存储形成一致快照；恢复后执行完整性检查、对象计数、hash、墓碑/撤回优先重放；禁止裸拷贝活跃数据库作为合格备份。
6. 文件指针失效、附件缺失或部分恢复时，原文与缺口状态分离，不冒充完整成功。

### 4.4 验收断言与判定

- 已返回“已保存”的记录恢复后 100% 存在且 hash 一致；未确认提交可不存在，但不得出现半条原文、错误版本或静默覆盖。
- 1,000 次随机强杀中完整性检查全部通过，确认记录丢失、重复和覆盖均为 0；磁盘/I/O 失败误报保存为 0。
- 标准 16GB 开发机上单条文本捕获暂定 p95≤150ms、p99≤500ms；这是 Spike 工程预算而非市场承诺，超标但正确性成立可判 `Pass with Conditions`。
- 一致快照可恢复；删除墓碑和撤回优先于旧内容生效，恢复后活跃路径复活数为 0。

**Pass：** 全部正确性/恢复 P0 断言通过，性能预算达到。**Pass with Conditions：** P0 断言通过，仅性能长尾、非核心文件类型或限定平台存在有界缺口。**Fail：** 任何确认记录丢失/覆盖、半写、早报、完整性失败或墓碑复活。

**允许降级：** 单写入者、短事务、减少离线文件范围、附件仅指针/元数据；可调整批次和后台工作。不得以降低耐久性、关闭安全同步或取消版本/墓碑换性能。

**证据路径建议：** `lifeos/spikes/SP-01/` 下保存 `SP-01_report.md`、`test_matrix.csv`、`environment.md`、`raw_logs/`、`backup_restore_report.md`、`cleanup.md`。

**禁止触碰：** 重要或唯一副本真实数据、真实敏感文件、生产库、云同步与付费资源。通过前 LifeOS 不得作为重要真实数据唯一副本。

## 5. SP-02 技术 Spike 任务卡

### 5.1 编号、名称、风险与目标

- **编号/名称：** SP-02｜Obsidian Vault 只读接入与来源身份。
- **风险：** “只读”只停留在文案；扫描改写 Vault、越界读取排除目录、漏事件造成状态漂移，或重命名/复制导致错误强合并和来源断链。
- **目标：** 在模拟 Vault 中证明读取、解析、对账、来源指针、变化/不可达/断开语义成立，且 Vault、排除范围和外发边界不被突破。

### 5.2 范围、非范围与输入

- **范围：** 首扫/增量/离线后 reconciliation；关键 Markdown 语法的保真解析或明确失败；来源身份候选；路径规范化、排除、符号链接越界拒绝；断开后的停止访问与保留许可检查。
- **非范围：** 真实 Vault、Obsidian 插件/私有数据库、写回/双向同步、全社区语法、附件正文全量提取、云/第三方处理可行性（由 SP-04 验证）。
- **输入：** P0-005 SP-02；P1-017 第 2～11 节；共用 Vault 夹具；SP-01 最小可靠存储接口语义；SP-03 身份包络。
- **夹具要求：** 完整复用 3.1 的模拟 Vault，每个变化脚本有预期清单、稳定窗口和前后树/hash/元数据快照；所有写/改名/删除/sidecar/metadata 写调用可拦截计数。

### 5.3 必测与异常场景

1. 首扫、正常增量及应用离线期间新增/改/删；主动漏掉 watcher 事件后全量对账恢复。
2. 同/跨目录重命名、移动、复制后删除、同内容不同文件、并发修改删除；不确定时保留候选/新对象。
3. 正常/异常 YAML、链接、双链、标题/块、嵌入、附件指针、乱码和破损链接；失败不覆盖上次有效版本、不把部分解析标为完整。
4. 排除目录、目录撤回、`..` 路径遍历、绝对路径和越界符号链接；验证读取、索引及远端 mock 发送字段均为 0。
5. 来源暂不可达、恢复可达、`disconnect_source`；来源指针返回文件/标题或块，不可返回时给出明确缺口。
6. 全流程核对 Vault 树、内容 hash、元数据以及 `.obsidian`，确认 LifeOS 引起的变化为 0。

### 5.4 验收断言与判定

- Vault 写/改名/删除/sidecar/metadata 写调用为 0，前后树、原文件 hash 和元数据无 LifeOS 引起的变化。
- 首扫后，稳定窗口内新增/修改/删除 100% 对账；漏 watcher 事件可由 reconciliation 修复。
- 明确重命名样例自动识别率暂定≥95%；歧义样例错误强合并为 0。低于 95% 但可完整降级为候选且无断链/误合并，可判 `Pass with Conditions`。
- 排除/撤回/越界路径的读取、索引和外发为 0；来源指针可回查，不可达时不伪装最新。
- 断开后监听与新读取为 0；已有副本只按既有保留许可处理。

**Pass：** 全部只读、边界、对账和身份 P0 断言通过，并达到重命名目标。**Pass with Conditions：** P0 断言通过，仅自动移动识别、块定位或附件元数据存在明确平台限制。**Fail：** 任一 Vault 改写、越界访问/索引/外发、错误强合并、不可恢复对账漂移，或解析失败覆盖有效版本。

**允许降级：** 手工导入/来源指针；路径+内容版本作为证据、移动仅候选并让用户纠正；附件仅指针/元数据；必要时移出 Obsidian V1 正式接入。只读、排除和不越权不可降级。

**证据路径建议：** `lifeos/spikes/SP-02/` 下保存 `SP-02_report.md`、`vault_fixture_manifest.md`、`compatibility_matrix.csv`、`readonly_invariant_report.md`、`reconciliation_report.md`、`source_pointer_samples.md`、`raw_logs/`、`cleanup.md`。

**禁止触碰：** 真实 Vault、真实敏感笔记、`.obsidian` 真实配置、真实云/模型/API、任何写回或 Vault 内导出。通过前不得承诺 Obsidian V1 正式接入。

## 6. SP-03 技术 Spike 任务卡

### 6.1 编号、名称、风险与目标

- **编号/名称：** SP-03｜来源、版本、Derivation 与证据链最小映射。
- **风险：** 输出无法定位精确输入/权限；AI 候选和用户确认共用权威字段；输入变化失效漏报或全库失效；撤回、删除或导出洗掉身份、约束或墓碑。
- **目标：** 用最小映射证明 Source/Artifact 分离、不可覆盖版本、Derivation、重要 Link、Feedback、Authorization 和最小 AuditEntry 足以支撑追溯、确认、失效与基础导出，而不预设最终 Schema。

### 6.2 范围、非范围与输入

- **范围：** 两条证据链；一次调试查询的完整回查；精确依赖闭包；身份/五维状态；多输入最严格约束与合法子集重建；墓碑优先的基础导出/重导入夹具。
- **非范围：** 真实模型质量、完整知识图谱、最终 Schema/API、全量事件溯源、SP-04 运行时授权、SP-05 全链路物理清理、SP-08 正式迁移格式。
- **输入：** P0-003+P0-009 冻结语义；P0-004+P0-007 信任基线；P0-005 SP-03；P1-016/017 的证据链与 E2E；`fixture-pack-v1`。
- **夹具要求：** 两条主链：①Obsidian 版本→恢复包/候选下一步→编辑确认→完成 Feedback；②外部材料→Decision 证据→输入更新/删除/撤权→证据失效/待复核。另含跨 Project、多输入冲突、合法子集、Feedback 撤回、部分导出和旧包重导入。

### 6.3 必测与异常场景

1. 从关键输出反查全部精确输入版本、Source、Authorization/政策版本、目的、位置/主体、工作流/模型版本、生成时间、身份、状态与 Feedback。
2. 候选经确认、编辑、拒绝、纠正、完成、延期和撤回；确认不洗掉 AI 身份，历史以追加记录保留。
3. 修改、删除、不可达、断源、撤权和 Feedback 撤回分别触发依赖闭包；验证无漏报、误报可解释且不全库失效。
4. 跨 Project、文件夹/标签/双链 Link、多输入不同许可；Project 不扩权，限制取交集，不能合并时拒绝或用合法子集生成新 Derivation 并披露缺口。
5. 用户已确认但唯一证据失效：保留确认历史，标记 `evidence_unavailable/review_required`，退出自动建议依据。
6. 基础导出区分身份、版本、来源、确认与部分失败；旧包重导入先应用墓碑/撤回，删除内容不复活。
7. 对比少量关系映射、聚合包络等最小候选，只记录取舍；不得把 11 个语义对象强制等同为 11 张表。

### 6.4 验收断言与判定

- 任一关键输出可在一次调试查询中返回完整证据包；缺任一精确版本、Source、权限/政策、处理位置、生成版本或 Feedback 即不合格。
- 原文、外部来源、AI Derivation、AI 候选与用户确认对象没有共享的可静默覆盖权威字段；重要 Link 有来源、确认和有效状态。
- 所有预期受影响 Derivation 漏报为 0；误报必须可列举解释且不产生无法解释的全库失效。
- Project/外部结构扩权为 0；多输入限制继承和合法子集新建成立；用户确认历史在证据失效时不被删除。
- 重导入复活数为 0；AuditEntry 不含禁止字段；最小映射不依赖图数据库、事件总线、固定 11 表或企业审计平台。

**Pass：** 全部追溯、身份、失效、权限继承和不复活断言通过。**Pass with Conditions：** P0 断言通过，仅调试工具便利性、可解释误报上限或非核心导出字段存在有界缺口。**Fail：** 证据链缺失/错链、身份被覆盖、依赖漏报、Project 扩权、全库失效不可解释、确认历史被抹除或墓碑复活。

**允许降级：** 增加显式 Derivation 输入依赖索引；假模型或无 AI，仅显示来源恢复信息/缺口；L3 候选降为 L1 Derivation 展示；Obsidian 降为来源指针。不得删除 Source、版本、Derivation、Feedback、Authorization 或身份/状态边界。

**证据路径建议：** `lifeos/spikes/SP-03/` 下保存 `SP-03_report.md`、`mapping_options.md`、`evidence_chain_samples.json`、`dependency_invalidation_report.md`、`export_reimport_report.md`、`audit_privacy_check.md`、`raw_logs/`、`cleanup.md`。

**禁止触碰：** 真实敏感内容、真实模型/云/API、生产日志、正式 Schema 迁移、技术架构冻结。通过前不得承诺可信恢复包、AI 候选证据链或真实 AI 辅助恢复。

## 7. 依赖、顺序与可并行性

1. **准备阶段：** 先只确认 `fixture-pack-v1`、统一结果包和断言编号；这是测试合同，不是数据模型冻结。
2. **并行骨架：** SP-01 与 SP-03 可并行。SP-01 负责耐久/恢复语义，SP-03 负责身份/证据语义；两者必须每日以同一夹具版本对账，不得各建对象 ID、版本、保存回执或墓碑规则。
3. **SP-02：** Vault 夹具、解析矩阵和只读测试可与两者并行准备；正式执行至少依赖 SP-01 的最小可靠存储接口语义，最终判定同时复用 SP-03 的 Source/Artifact/版本/Link 包络。
4. **收口：** 三项分别出结论后执行一次跨 Spike E2E；任何夹具或语义变更必须升级版本并重跑受影响断言。SP-01/03 Fail 时不得用 SP-02 的演示结果绕过底线。

## 8. 阶段准入与禁止承诺清单

## 9. 失败降级与后续决策路径

- **SP-01 Fail：** 只保留可丢弃夹具；修复后重跑。若附件一致性失败，降为文本/链接/文件指针；若可靠落盘本身失败，则阻断所有真实数据与后续工程承诺。
- **SP-02 Fail：** 降为手工导入或来源指针；保留外部原件在原系统，必要时将 Obsidian 正式接入移出 V1。任何范围变更需 PM 记录。
- **SP-03 Fail：** 禁用 AI 候选与可信叙述，降为 FTS/元数据和来源列表；L3 降为 L1 或无 AI；若最小来源/版本链也失败，阻断恢复包承诺。
- `Pass with Conditions` 必须附条件清单、适用平台/数据类型、用户可见缺口、复验任务和失效条件，由 PM 决定接受、返工或调整 V1 条件范围。
- 超出本批范围的运行时授权、撤回清理、同步、搜索质量、正式导出和容量问题，分别进入 SP-04～SP-09，不在本任务扩写实现。

## 10. 需要 PM / 用户确认的问题

1. **[需 PM 确认]** 是否批准三张任务卡及 `fixture-pack-v1`/统一结果包为执行合同；批准不等于技术架构冻结。
2. **[需 PM 确认]** 是否接受 SP-01 与 SP-03 并行、SP-02 准备可并行但正式收口依赖两者语义的顺序。
3. **[需 PM 确认]** 是否接受本文 `Pass with Conditions` 的有限使用，以及任何 P0 断言失败必须判 `Fail`。
4. **[需 PM 确认]** 是否继续采用 P0-005 的暂定工程阈值：SP-01 p95/p99、1,000 次强杀；SP-02 明确重命名≥95%。阈值仅用于 Spike，不作市场承诺。

6. **[需 PM 持续确认]** 任一 Fail 后按第 9 节降级或移出条件范围；正式 MVP 开发和技术架构继续阻塞。
