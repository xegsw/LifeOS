# LIFEOS-P2-006｜SP-06 离线同步与状态一致性技术 Spike 报告

## 1. 任务边界与结论摘要

**最终结论：`Pass`，严格限于 Python 标准库、确定性合成夹具、单账号、单进程服务端权威状态机与 mock 队列的候选机制层。**

**[已验证事实]** 本任务实际创建并运行 `lifeos/spikes/SP-06/run_spike.py`。39/39 项通过，P0 失败为 0：同一操作提交 100 次只产生一次业务效果并解释 99 次重试；A/B/C 离线乱序和 A-E 五设备扩展均未丢原文版本；用户原文静默覆盖、AI/旧设备覆盖用户权威、删除/撤回后复活、过期队列可见输出、隐私扫描命中均为 0。

**[合理推断]** “客户端操作 ID + 不可变版本 + 服务端权威投影 + 对象级前置版本 + 追加式 Feedback/操作日志 + tombstone/restriction generation 优先 + 队列发布前重检”足以支撑 V1 单账号少设备的最小离线同步候选，无需现在引入全量 CRDT、完整事件溯源或重型同步平台。

**[建议｜需 PM 确认]** V1 若保留同步，应限定为单账号、少设备、非实时、对象级同步；原文冲突保留双版本并由用户处理，Action/Decision/Link/Feedback 不做字段级 LWW。候选 Action/Decision/Link 继续以 L1 Derivation 展示，不默认物化为 L3 持久业务对象。

**[边界]** 本任务未实现真实服务、数据库事务、网络分区、进程并发、备份恢复、跨平台客户端、正式冲突 UI 或容量测试；不证明同步 SLA，不冻结 Schema、API、事件流、队列、云端权威范围、技术栈或技术架构，也不解除正式 MVP 开发阻塞。

## 2. 最小同步模型与非冻结说明

候选模型由四层组成：

1. **不可变事实层**：ArtifactVersion、Feedback 和业务操作只追加；编辑、纠正、修订、完成、延期和撤回均不覆盖旧记录。
2. **权威投影层**：服务端基于已接纳操作计算 Artifact 当前版本、Action/Decision/Link 当前状态、候选认可状态与证据状态。投影可重算，但客户端缓存、队列和 AI 输出不是权威源。
3. **并发栅栏层**：业务操作携带对象级前置版本；删除、撤权、断源携带单调 generation/version。前置不匹配时保留输入并显式冲突或默认拒绝，不按客户端时间抢占。
4. **执行辅助层**：队列只运送任务。可见输出发布前重新校验对象、授权、政策、墓碑、来源和租约；任一不匹配即拒绝发布。

这是验证最小语义的内存状态机。字段名、对象集合和枚举是测试包络，不对应冻结表结构或接口。完整事件溯源并非必要：V1 只需为高价值业务变化保存追加历史，同时允许当前投影服务读取。全文协作 CRDT 也非必要：LifeOS V1 没有多人共享，且冲突时“保留双版本”比不透明自动合并更符合原文保护。

## 3. 操作包络、身份、版本与 generation 合同

| 字段 | 判定作用 | 失败处理 |
|---|---|---|
| `operation_id` | 全局幂等键；绑定规范化操作包络摘要 | 同 ID 同包络返回原结果并累计重试；异包络拒绝 |
| `device_id` | 解释操作来源和冲突设备 | 只作来源，不参与权威优先级 |
| `base_version` | ArtifactVersion 或业务对象的乐观并发前置 | 原文保留分支并显式冲突；业务状态追加未应用尝试并冲突 |
| `object_version` | 服务端当前投影的单调版本 | 队列或业务操作不匹配即拒绝 |
| `tombstone_generation` | 删除代际栅栏，支配旧副本和旧任务 | 旧 generation 不得复活、入模或发布 |
| `auth_version` | Authorization 当前版本与活跃状态 | 过期、撤回或不匹配 fail closed |
| `policy_version` | 强制政策包络版本 | 政策变化后旧任务不得继续 |
| `lease(owner,generation,valid)` | 防止过期/重复 worker 发布 | 所有权、代际或有效性任一失败即拒绝 |

服务端接纳顺序只决定哪个匹配前置版本的操作先形成当前投影，不丢弃其他输入。客户端时间不用于解决权威冲突；`device_id` 也不形成固定设备优先级。

## 4. 状态转换与冲突规则

**[已验证事实]** 完整矩阵见 `state_transition_matrix.csv` 和 `conflict_matrix.md`。核心规则如下：

- Artifact 编辑前置匹配时追加新版本并移动当前指针；前置过期时仍保存新版本为冲突分支，不移动当前指针。
- 候选接受、编辑后接受、拒绝只可由显式用户操作触发。第一个匹配候选版本的响应生效；并发的其他响应追加为未应用 Feedback 并生成用户可处理冲突。
- Action 完成/延期、Decision 修订、Link 确认/纠正都按对象版本 compare-and-append；前置过期不覆盖当前状态。
- Feedback 撤回是指向旧事件的新事件；重算只使用仍有效且已应用的事件。历史本身不删除。
- tombstone、授权撤回、Source restriction 是更高优先级栅栏；不参与普通 LWW，也不允许旧业务操作解除。

自动安全收敛只包括：完全相同操作的幂等重试、前置版本匹配的单一路径变化、单调限制代际、可重算投影。原文双编辑、候选认可分歧、完成/延期、决定修订、关系确认/纠正等语义冲突必须显式化。

## 5. 幂等、重复、乱序、延迟与离线重放

**[已验证事实]** T03 将同一 `operation_id` 和同一包络提交 100 次。最终 ArtifactVersion 总数只增长 1，操作登记的 `retry_count=99`，对应最小 AuditEntry 同样记录 99 次重试；没有为每次网络重投复制业务事件。若同一 ID 携带不同包络，候选实现拒绝为 `OPERATION_ID_PAYLOAD_MISMATCH`。

T04-T06 从同一 `av-1` 产生 A/B 离线双编辑与 A/B/C 乱序消息。首个合法操作成为当前版本，后续两个版本都以冲突分支保留；4 个总版本（基线 + 三个输入）均存在，静默覆盖为 0。T36 将同样机制扩展到 A-E：基线加 5 个输入共 6 个版本，形成 4 个显式冲突，版本丢失为 0。

**[限制]** 这证明消息排列对候选状态机的安全性，不证明真实网络、跨进程事务隔离、批量上传、同步游标、断点续传或吞吐性能。

## 6. 原文、AI 候选与用户权威对象一致性

T07-T10 验证候选 Action 的接受、拒绝、接受/拒绝并发及“编辑后接受/接受原候选”并发。并发响应不会字段级 LWW：已生效响应保持，其他响应保留为冲突历史，要求用户选择。AI 候选仍保留 Derivation 身份；只有用户操作能形成用户权威投影。

T11 让用户原文先从 `av-1` 编辑为 `av-user`，再让基于旧 `av-1` 的 AI 重建到达。重建因输入版本过期被拒绝，Artifact 当前指针仍为 `av-user`，候选没有创建。由此验证 AI 重建无法回写或抢占用户原文。

T12-T15 验证 Action 完成/延期、Decision 修订、Link 确认/纠正：生效变化与冲突尝试都追加历史，当前状态不被旧 base 覆盖。Decision 的旧恢复包只能被视为 stale；它不是权威 Decision 来源。

## 7. Feedback 追加历史与当前状态重算

**[已验证事实]** T16-T20 分别覆盖确认、拒绝、纠正、完成、延期的撤回。每组先产生一个业务 Feedback，再追加一个 retract 事件；原事件保留并带撤回引用，事件数为 2。投影重算后：候选回到 `available_unconfirmed`，Link 回到 `candidate`，Action 回到 `confirmed`。撤回未改写 AI 来源身份、原文或历史事件。

冲突操作也进入追加历史，但标记 `applied=false` 和受控原因码，因此可以解释“发生过什么”而不会误当现行状态。正式实现可缓存投影，但必须能从有效 Feedback/版本重建；缓存不是唯一权威。

## 8. tombstone、撤权、断源与不复活

T21-T25 覆盖删除后旧设备上传、撤权后旧队列、断源后旧读取结果、tombstone 先到/旧版本后到和旧版本先到/tombstone 后到。结果为：旧上传拒绝；旧任务可见输出为 0；断源后新候选为 0；两种消息顺序最终所有目标版本均不活跃，复活数为 0。

该机制继承 SP-05 的两阶段语义：同步层只证明阶段 A 的活跃阻断与代际优先；物理副本清理仍可异步并真实披露。恢复包、导入和备份开放读取前必须先加载更严格且更新的 tombstone/restriction/auth 状态。Source 重连只恢复连接能力，不得降低内容墓碑或恢复旧授权。

唯一证据失效时，已确认 Action/Decision 等历史不静默删除，而是保留用户确认身份并进入 `evidence_unavailable/review_required`，退出自动排序、建议和模型输入；T32 验证了该正交状态。

## 9. 队列执行前重检与租约 fencing

T22、T26-T30B 分别注入 Authorization 撤回、租约过期、重复领取的旧 lease、`auth_version`、`policy_version`、输入 tombstone、对象版本和 Source 状态变化。每项均在发布前失败，`visible_outputs=0`；T30C 证明六项全匹配时只发布一个可见输出。

发布闸门必须在同一权威判定点检查：目标 `object_version`、Authorization 活跃且版本相同、policy 版本相同、对象活跃且 tombstone generation 相同、Source 仍连接、lease owner/generation/有效期相同。先生成隔离输出再重检是允许的候选实现，但未通过闸门的输出不得进入搜索、恢复包、今日页、缓存或后续派生。队列 payload 和消息到达顺序不能代替当前权威状态。

## 10. 方案对比

| 方案 | 本任务结论 | 理由 |
|---|---|---|
| 服务端权威 + 不可变版本 + 追加日志 | **推荐候选** | 39 项断言可用有限机制表达；冲突可解释，限制代际可强制 |
| 字段级 LWW | **禁止用于权威字段** | T33 展示较晚拒绝可无痕覆盖较早接受；同样会丢原文、纠正和完成/延期意图 |
| 有限 CRDT | **暂不引入** | 对集合/计数等窄字段未来可能有用，但文本语义、Authorization、tombstone 和撤回需额外因果/合并规则；V1 无多人协作价值依据 |
| 队列作为权威 | **禁止** | 旧租约、重试、政策变化和删除竞态会使旧状态发布；队列只能辅助执行 |

本建议不排斥未来对特定可交换字段采用有限 CRDT；任何引入须用同一夹具证明收益大于因果元数据、删除传播和迁移成本。

## 11. L3 候选物化成本与降级建议

候选 Action、Decision、Link 一旦 L3 物化，每一类都新增对象版本、Feedback 投影、并发冲突、撤回、证据失效、tombstone/restriction、队列重检、审计和冲突体验。三类语义又不同，不能用 Action 的结果外推 Decision/Link。

**[建议｜需 PM 确认]** V1 继续把三类候选作为 L1 Derivation 展示；用户接受或编辑接受时，才通过显式命令创建/更新用户权威对象。这样保留“候选下一步—用户确认—反馈”闭环，同时避免大量无人确认的候选进入同步集合。若未来某类 L3 有明确价值，必须独立通过对象级触发、频率上限、撤销、同步、撤权和用户理解测试。

## 13. 最终判定、限制与风险

依据任务卡规则，本任务判定 `Pass`：所有 P0 安全断言通过且证据可一条命令复跑。合成单进程和 mock 队列是任务授权边界，因此不单独把结论降为 `Pass with Conditions`；但引用时必须携带边界，不能写成“生产多设备同步已通过”。

主要限制/风险：

- 未证明服务端事务与操作登记原子、网络重试游标、跨进程隔离、真实租约时钟、发布闸门 crash consistency。
- 未证明冲突数量、长离线窗口、真实 3-5 台设备和大操作日志下的性能与可用性。
- 未验证正式冲突 UI、辅助技术、通知频率及用户是否理解“当前版本/冲突版本/旧设备被拒绝”。
- 未验证 SP-08 旧导出包重导入的正式墓碑合并，也未验证 SP-09 容量。
- 生产实现若让 operation ledger、对象写入、tombstone 或 outbox 非原子，仍可能产生重复效果或复活；建议 PM 评估补充 R-0020/R-0035/R-0037 的实现风险，不由本会话修改风险表。

## 14. 对 V1 与后续验证的影响

**[建议｜需 PM 确认]**

1. V1 同步能力可“保留但收窄”：单账号、3-5 台设计目标、非实时、对象级操作同步、显式冲突、无多人共享；设备数和实时性不作承诺。
2. 不安全自动合并统一降级为双版本/双意图保留、冲突提示和用户处理；不得用 LWW 隐藏分歧。
3. AI 候选继续 L1；真实云/第三方处理仍保持关闭，除非具体路径另获授权和处理者资格。
4. SP-07 应消费当前版本、证据状态与冲突状态，不能从旧队列/冲突分支生成看似确定的恢复包。
5. SP-08 必须验证删除前旧包、较低 generation、离线 Feedback 和业务版本合并；SP-09 必须测 operation ledger、冲突分支、Feedback 历史与 tombstone 的规模成本。
6. 本次结果可作为未来技术架构候选输入，但技术架构冻结和进入正式 MVP 开发仍须完整 Spike、独立评审与 PM 决策。
