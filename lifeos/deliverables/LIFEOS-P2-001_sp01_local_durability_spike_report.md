# LIFEOS-P2-001｜SP-01 本地可靠落盘、离线捕获、备份恢复技术 Spike 报告

## 1. 任务边界与结论摘要

**任务结论：Pass（仅限本 Spike 候选实现和本次 macOS arm64 环境）。**

**已验证事实：** 本任务实际创建并运行了隔离的最小本地存储候选，使用 1,000 条确定性合成提交、1,000 次确定性随机强杀、写失败注入、重复提交、时钟偏移、长读/后台索引、活跃写入期间一致备份及恢复进行验证。15 项测试矩阵全部通过：收到“已保存”回执的记录恢复后 100% 存在且 SHA-256 一致；误报保存、半写、旧版覆盖、不可解释重复、完整性失败、删除或撤回复活均为 0。基线捕获 p95 约 0.078ms、p99 约 1.774ms，低于暂定 150ms/500ms 工程预算。

**合理推断：** 在“单设备、单写入者倾向、短事务、文本/链接/文件指针元数据、SQLite WAL + FULL 同步、数据库感知备份”的有限候选边界内，LifeOS 能建立下一项 Spike 所需的可信本地保存语义：先耐久提交，后显示已保存；离线本地已保存与待同步分离；恢复时墓碑和撤回优先。

**建议：** SP-01 可作为 SP-02/SP-03 后续验证的存储语义输入；继续保持正式 MVP 开发阻塞，并保留单写入者、短事务和附件仅指针/元数据作为允许降级。不得把 Pass 解释为 SQLite、Schema、API、桌面框架、同步架构或生产备份方案冻结。

**风险：** 本次强杀是进程级 `SIGKILL`，磁盘满/I/O 是确定性写错误注入；未覆盖突然断电、设备/内核虚假 fsync、真实坏块、跨平台和生产恢复 SLA。这些不是本任务最低断言失败，但限制了结论外推范围。

## 2. 验证实现说明

最小实现位于 `lifeos/spikes/SP-01/run_spike.py`，仅使用 Python 标准库和 SQLite。候选配置为 `journal_mode=WAL`、`synchronous=FULL`、外键开启、5 秒 busy timeout。它服务验证，不进入正式产品目录。

一次新捕获在同一短事务中完成：

1. 以幂等键查询既有提交；同键、同 Artifact/Version、同 hash 返回既有结果，同键异 payload 返回可行动的 `IDEMPOTENCY_CONFLICT`。
2. `BEGIN IMMEDIATE` 后追加 Artifact（若不存在）、不可覆盖的 Version、Submission 幂等映射。
3. `COMMIT` 返回后，调用方才输出 `ACK_SAVED`。事务中任何 SQLite 错误均回滚且不发回执。
4. UI 语义上的“编辑中/保存中”不进入耐久成功态；commit 后根据网络条件记录 `local_saved` 或 `offline_local_saved`，同步状态另记为 `not_required` 或 `pending_sync`。

用户原文保存在 Version，SHA-256 与之同事务保存；Artifact 与版本分开；旧版本不更新。删除采用 Artifact 级墓碑，Feedback 采用追加事件并以更晚的 `retract` 使旧确认退出活跃视图；Authorization 含允许、拒绝、过期、撤回四个最小样本。客户端时间被保存为输入元数据，但版本身份和确定性 `created_seq` 不依赖客户端时钟，避免未来/过去时钟造成覆盖。

这足以验证 SP-01，是因为测试目标是耐久点、原子性、幂等、版本、保存状态和一致恢复，而不是选定长期技术组件。它没有实现完整 UI、云同步、附件架构、模型调用或产品 API，也没有提出 Schema 冻结。

## 3. 测试夹具说明

固定种子 `20260808` 生成 1,000 次基线提交：900 个 Artifact、1,000 个 Version，其中 100 个 Artifact 有两个版本；每 10 条有 1 条无 Project，其余分布在 3 个个人 Project。250 条为 `offline_local_saved + pending_sync`。所有原文都是带序号的合成字符串，不含真实材料。

重复场景包含 20 次同键同 payload 重投和 10 次同键异 payload 冲突；结果分别为 20 次复用、10 次拒绝，版本/Submission 数量不增长。用户权威状态包含 3 个删除墓碑、1 条确认 Feedback 及其追加撤回、4 种 Authorization。另有未来和过去客户端时钟样本。强杀、并发和备份线程还生成独立的合成记录，避免碰触基线身份。

日志只记录固定种子、计数、状态、时延、hash 统计和错误代码，不记录 `original_text`；AuditEntry 的本 Spike 等价样本也是不可还原的最小元数据。夹具生成规则见证据包 `fixture_manifest.md`。

## 4. 故障注入与测试矩阵

### 4.1 四时点强杀

主进程启动独立写入子进程，并等待其输出内部阶段标记后发送真实 `SIGKILL`。1,000 次阶段由固定随机种子选择，分布为：写前 270、写中 239、commit 后/回执前 249、回执后 242。每次重启连接后都执行一次 `PRAGMA integrity_check`，1,000 次均为 `ok`。

- 写前：尚未开启事务，记录可不存在且无回执。
- 写中：Artifact/Version/Submission 已在未提交事务中，强杀后整体回滚，不出现半条原文或孤儿映射。
- commit 后/回执前：记录可能已耐久存在，但用户未收到回执；恢复不得把它错误标成已回执，也允许幂等重试发现原提交。
- 回执后：242 条全部恢复存在，hash 不一致 0。

全部强杀最终形成 491 条已提交记录（249 条 commit 后/回执前 + 242 条回执后）；无重复幂等行、半写或完整性失败。这个结果直接证明回执没有早于 commit。

### 4.2 写失败、重复与时钟

磁盘满和 I/O 失败通过候选存储层的确定性 SQLite `OperationalError` 注入模拟；两者均返回 `WRITE_FAILED`，回执数 0，数据库对象计数不变，既有旧版本 hash 不变。面向用户的可行动结果是“保留当前编辑内容，可重试或复制”，不把 AI 或同步状态混入保存失败。

重复提交已在夹具中验证；时钟偏移样本不参与版本覆盖判断。局限是本次未让真实 APFS 卷耗尽，也未在 SQLite commit 内部每个 I/O 点注入内核错误；因此不能把结果外推为硬件故障认证。

### 4.3 长读、后台索引与 checkpoint

一个线程保持长读事务，另一个线程把内容 hash 写入可重建的 `derived_index`，主线程同时完成 100 次捕获并执行 passive WAL checkpoint。捕获错误 0、后台索引错误 0；p95 约 0.068ms、p99 约 0.188ms、最大约 1.118ms。checkpoint 返回 busy=0，长读没有冻结捕获主路径。派生索引与原文分表，删除/撤回的完整传播仍由 SP-05 验证，本任务没有越界宣称全链路清理完成。

完整 15 项断言及证据索引见 `test_matrix.csv`。

## 6. 性能与资源结果

基线 1,000 次单条提交：p50 0.059ms、p95 0.078ms、p99 1.774ms、最大 5.725ms。并发场景 100 次提交：p95 0.068ms、p99 0.188ms、最大 1.118ms。两组均满足 p95≤150ms、p99≤500ms 的暂定 Spike 预算。

活跃数据库约 772 KiB，备份约 756 KiB；主 Python 进程峰值常驻内存约 20.0 MiB，完整运行约 33 秒。该测量在 24 GiB、10 核 Apple arm64 本机完成，且是 SQLite/Python 内部写入延迟，不包含未来 UI、IPC、加密、杀毒软件、低端磁盘或云同步开销。性能结论只能说明候选没有显著阻断风险，不能成为市场承诺。

## 7. 备份恢复与不复活验证

使用 SQLite Online Backup API 在后台写线程完成 50 次提交的同时创建快照，禁止把活跃数据库裸拷贝作为合格方式。快照前最低 Version/Submission 数为 1591，快照捕获 1592，备份结束后活库为 1641，证明快照与活跃写入交叠且形成一致时点。恢复库与快照六类对象计数完全一致，`integrity_check=ok`，原文 hash 不一致 0。

恢复保留 3 条墓碑、2 条 Feedback event、4 条 Authorization 和 400 条待同步 Version。恢复后已删对象活跃命中 0；再执行旧包式 `INSERT OR IGNORE` 重放，墓碑仍先于活跃读取生效，复活 0。已撤回 Feedback 的活跃命中也是 0。这里验证的是最小优先级和恢复语义，不代替 SP-05 的所有索引/缓存/队列/第三方清理传播，也不代替 SP-08 的正式导出/重导入协议。

## 8. 日志与隐私检查

本任务未访问真实 Obsidian Vault、用户文档、网络、云、模型或第三方 API。合成原文具有明确 `SYNTHETIC...NO_REAL_DATA` 标记；原始日志文件只保留结构化计数、环境、时延、错误类别和 hash 统计。错误样例不含原文。数据库中虽含合成原文字段，但属于可丢弃夹具，并有精确清理说明。

## 9. 最终结论

**Pass。** 依据是所有 P0 正确性/恢复断言通过，性能预算达到，且证据可一条命令复跑。候选实现足以作为下一项 Spike 的“最小可靠存储接口语义”输入：用户原文与版本不可覆盖；幂等重试可解释；已保存只在 commit 后；离线耐久与待同步正交；恢复先应用墓碑与撤回。

Pass 不表示技术架构已冻结，也不表示 SP-02～SP-09、正式 Stage 3、真实敏感数据、云或第三方路径获准。特别是物理断电/介质故障、跨平台和生产备份仍是后续工程风险。

## 10. 降级建议与后续影响
