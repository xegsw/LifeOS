# LIFEOS-P1-016｜核心信息架构与端到端流程

## 1. 任务边界与结论摘要

- **[事实]** P1-015 已被用户采纳为后续共同输入；自用版最小切片固定围绕“捕获 → 保存 → 来源 / Project → 找回 / 今日恢复 → AI 候选 → 用户反馈 → 导出 / 删除底线”。正式 MVP 开发仍为 `Blocked / Not Allowed`。
- **[事实]** 已冻结基线要求：Project 是用户确认的上下文边界而非授权来源；用户原文、外部来源、AI 派生 / 推断 / 建议、用户确认内容必须分离；证据不足时允许“暂无可靠建议”；四类命令不得互相冒充。
- **[建议]** 最小切片采用五个一级区域：**今日、Inbox、Projects、找回、数据与权限**；另设全局“快速捕获”。Artifact / Source / AI 证据 / Feedback 采用上下文详情，不增设一级后台模块。
- **[建议]** 端到端主路径以“先耐久保存，再整理归属；先恢复证据，再给候选；先对象级确认，再进入用户行动；任何撤回 / 删除先活跃阻断，再报告物理清理”为顺序。
- **[推断]** 该 IA 已足以转成 SP-01 的保存状态夹具和 SP-03 的来源—版本—Derivation—证据链夹具；无需先冻结数据库、API、事件流或前端框架。
- 本交付物是研究型流程输入，不是完整 PRD、视觉稿、技术架构、Spike 结果或开发准入结论。

## 2. 自用版最小切片信息架构

### 2.1 一级区域与入口

| 一级区域 / 入口 | 主要问题 | 最低内容与动作 | 明确非范围 |
|---|---|---|---|
| **今日** | 我从哪个 Project 继续？ | 当前 Project / 未选态；恢复包；零或一个候选下一步；已确认安排；快速捕获；异常摘要 | 全局任务墙、KPI、系统运行台、完整日历 |
| **Inbox** | 我刚保存了什么，哪些还未归属？ | 已耐久保存的文本、链接、文件 / 来源指针；保存回执；待归属状态；手选 Project；打开原文 / 来源 | AI 自动归类静默生效、通用知识库管理 |
| **Projects** | 某个 Project 的可信上下文是什么？ | Project 列表与选择；Project 恢复页；停点、变化、决定、未处理材料、证据缺口、已确认行动 | 团队项目管理、Sprint、工单、权限容器 |
| **找回** | 我能否回到原文和证据？ | FTS + 元数据查询；按 Project / 身份 / 来源筛选；结果回到 Artifact / Source；不可达与失效状态 | 向量搜索作为 Must、跨 Project 自动综合答案 |
| **数据与权限** | 我的数据在哪里、如何处理、怎样导出或停止？ | Source 列表；授权摘要；四类命令入口与状态；基础导出；删除 / 撤回处理记录 | 企业审计台、供应商运维台、完整清理状态机平铺 |
| **全局快速捕获** | 我能否不离开当前工作就记下来？ | 文本、链接、文件 / 来源指针；可选当前 Project / Inbox；保存中、已耐久保存、失败 | 捕获时强迫结构化、AI 静默改写原文 |

### 2.2 二级上下文页

- **Artifact 详情**：原文 / 指针、版本、内容身份、Source、Project Link、AI 派生、Feedback、删除入口。
- **Source 详情**：来源身份、定位、可达性、授权摘要、关联 Artifact、断开来源与撤回处理入口。
- **AI 结果 / 证据详情**：输出身份、适用 Project、输入版本、关键证据、缺口、生成时间、处理位置、授权与反馈历史。
- **命令处理详情**：对象、影响预览、明确确认、活跃阻断、物理清理与失败 / 受限状态。

这些详情是一级区域内的上下文目标，不是新的顶层后台。首页只显示准确入口、影响摘要和最小回执。

### 2.3 导航原则

1. 今日是默认恢复入口，不是所有数据和任务的总览。
2. 捕获始终可达；结构化与 Project 归属可以在保存后完成。
3. 当前 Project 只来自用户本次选择或最近由用户确认的延续；系统只能提出待选择候选。
4. “查看证据”必须回到 Artifact / Source；AI 文本不能成为唯一上下文。
5. 影响用户控制的异常才升级到当前页；底层审计和清理细节按需进入详情。

## 3. 端到端主流程

### 3.1 主路径

| 步骤 | 用户可见流程 | 身份 / 状态要求 | 结果 |
|---|---|---|---|
| 1. 捕获 | 从全局入口或今日输入文本、链接、文件 / 来源指针；可选当前 Project，也可先入 Inbox | 输入明确标为“你的原文”或“外部来源指针”；AI 不改写 | 形成待提交内容 |
| 2. 本地保存 | 显示“保存中”；只有耐久提交后显示“已保存”；离线时分别表达本地保存与待同步 | 失败不得显示成功；原文和版本稳定 | 产生可回查 Artifact / Source 指针与保存回执 |
| 3. Project 定界 | 用户保存时选择、在 Inbox 手选，或接受一个带理由的候选 Project | 未选择时为“待归属”；候选 Link 不扩权、不静默生效 | 建立用户确认或待确认的 Project Link |
| 4. 今日 / Project 恢复 | 用户选择 Project；系统以当前合法输入显示停点、变化、决定、未处理材料和证据缺口 | 恢复信息标“AI 整理”或规则整理；可逐项回到证据；缺口不得被流畅叙述掩盖 | 得到可核对恢复包，或明确无足够内容 |
| 5. 候选判断 | 授权和证据充分时显示零或一个“AI 建议 / 未确认”的候选下一步 | 展示动作、理由、Project、关键证据、时效与缺口；依据不足则“暂无可靠建议” | 候选保持 Derivation / `ai_proposed` 身份 |
| 6. 对象级反馈 | 用户可确认、编辑后确认、拒绝、纠正或忽略；只有确认后才成为用户当前选择 | 编辑保留前后版本；Feedback 追加历史；AI 来源身份不消失 | 形成用户确认 Action / 当前 Next Step，或候选退出主位 |
| 7. 执行反馈 | 对已确认 Action，用户可完成或延期；也可撤回先前确认 / 拒绝 / 纠正 | “完成 / 延期”不适用于未确认候选；撤回不覆盖旧 Feedback | 当前业务状态重算，历史可解释 |
| 8. 导出 / 控制 | 用户从数据与权限、Artifact 或 Source 详情进入导出、撤回、断源或删除 | 显示作用对象、LifeOS 可控边界和实际状态；删除 / 撤回后不得复活 | 形成导出包或命令处理记录 |

### 3.2 Project 选择四态

1. **本次用户选择**：立即成为当前 Project，但所有读取 / 派生仍需 Authorization 重判。
2. **最近确认延续**：今日标注“沿用你上次确认”，允许切换。
3. **系统候选**：显示候选理由；用户接受前不得生成该 Project 的跨源恢复或建议。
4. **未选 Project**：允许捕获到 Inbox、查看原文和手动选择；禁止跨 Project 恢复、建议和全局排序。

### 3.3 候选与反馈转换规则

- 确认候选：追加 `Feedback(confirm)`，对具体对象、版本和用途生效；不会把其 AI 来源改写成用户原文。
- 编辑后确认：保留 AI 版本和用户编辑版本，追加差异与确认 Feedback。
- 拒绝：退出主位置；没有新证据或情境变化不重复推送。
- 纠正：保留目标与修正范围；相关 Derivation / Link 进入重建、stale 或 invalid。
- 忽略：只表示本次不处理，不等于拒绝、完成或错误。
- 完成 / 延期：只作用于已确认 Action，追加 Feedback 并更新业务状态。
- 撤回 Feedback：追加撤回记录并重算当前认可状态，不删除内容、不抹去历史。

## 4. 关键异常 / 降级流程

| 状态 | 进入点与用户说明 | 可继续做什么 | 禁止 / 降级 |
|---|---|---|---|
| 未选 Project | 今日 / 捕获后显示“尚未选择 Project” | 捕获到 Inbox、手选、查看候选理由 | 不跨 Project 恢复或建议 |
| 保存中 | 捕获提交后、耐久完成前 | 保留输入、等待或取消未提交操作 | 不显示“已保存” |
| 保存失败 | 明确失败原因类别、内容仍在当前编辑态、提供重试 / 复制 | 重试、复制原文、缩小文件范围 | 不丢弃输入、不伪造回执；SP-01 阻断案例 |
| 离线 | 显示“已本地耐久保存 / 待同步”或“尚未保存”之一 | 捕获、浏览已合法本地内容、手选 Project | 云 / 第三方处理暂停；旧结果标时效 |
| 权限受限 | 指明受影响 Source / 目的 / 位置和影响 | 继续无 AI、查看合法原文、请求最小授权 | 默认拒绝；不以总开关或 Project 归属扩权 |
| 来源不可达 | 显示来源、上次可用时间、受影响证据 | 查看合法保留副本、重连或断开来源 | 依赖结果 stale / invalid；不得伪装最新 |
| AI 证据不足 / 冲突 | 显示具体缺口或冲突 | 查看材料、补充记录、手动选择下一步 | “暂无可靠建议”，不得凑数或伪置信度 |
| AI 生成失败 | 恢复页保留原文、已确认决定和行动 | 重试或继续无 AI | 不把 AI 失败解释为保存失败 |
| 删除 / 撤回活跃阻断中 | 先显示命令已接受，再显示是否已 `active_blocked` | 查看范围、清理进度、失败重试 | 未零遗漏阻断前不得写“已停止使用” |
| 导出失败 / 部分导出 | 列出成功范围、排除项类别、失败对象与重试入口 | 保存已完成部分、重试失败部分 | 不把部分包宣称为完整；不得夹带无许可内容 |

异常表达统一回答三件事：**发生了什么、影响哪些能力、用户现在还能做什么**。技术错误码、队列和日志不进入主体验。

## 5. 内容身份与状态规则

| 内容身份 | 主路径展示 | 可发生的转换 | 不变量 |
|---|---|---|---|
| 用户原文 | “你的原文”、版本、保存时间、Project / Inbox、来源入口 | 用户编辑产生新版本；可删除 | AI 不覆盖，旧版不静默消失 |
| 外部来源 | 来源名称 / 类型、定位、版本 / 访问时间、可达性 | 可断开；合法副本按保留许可处理 | 外部主张不是用户确认事实 |
| AI 派生 / 整理 | “AI 整理”、输入范围、生成时间、证据入口、有效状态 | 输入变化可 stale；权限 / 删除命中则 invalid；可重建 | 不成为原文或唯一证据 |
| AI 推断 / 建议 / 候选 | “AI 推断”或“AI 建议 / 未确认”、理由、支持 / 反证、时效 | 可被确认、编辑、拒绝、纠正、忽略 | 确认前不是承诺、决定或当前 Next Step |
| 用户确认内容 | “你已确认”、对象版本、确认时间、原始身份与证据状态 | 可完成、延期、修订、替代或撤回 Feedback | 确认不扩授权；证据失效时保留历史但待复核 |

状态必须保持五维正交：**来源身份、用户认可、业务状态、证据状态、派生状态**。例如“用户曾确认 + 证据不可达 + 待复核”可以同时成立，不能用一个“已确认”掩盖其余状态。

## 6. 四类命令入口与最低流程

| 命令 | 入口 | 执行前最低表达 | 提交后最低流程与回执 |
|---|---|---|---|
| `revoke_processing` 撤回处理许可 | AI 证据详情、Source / 授权详情 | 停止哪些主体、范围、动作、目的、位置；原文默认是否保留 | 明确确认 → 耐久接受 → 活跃读取 / 搜索 / 建议 / 队列 / 新模型调用阻断 → 派生与副本清理追踪；不冒充断源 / 删除 |
| `disconnect_source` 断开来源 | Source 详情、来源不可达状态 | 停止继续读取 / 监听 / 同步；既有副本保留选择；不影响外部原件 | 明确确认 → Source 断开 → 依赖结果 stale / invalid → 合法保留或清理副本；若还要删除须组合 `delete_content` |
| `delete_content` 删除内容 | Artifact / Source 详情、数据与权限 | 删除对象、版本、LifeOS 可控副本、依赖影响、外部原件边界 | 二次确认 → 耐久墓碑 → 活跃阻断 → 派生 / 索引 / 缓存清理 → `pending / failed / vendor_limited / cleaned`；备份 / 重导入不复活 |
| `retract_feedback` 撤回反馈 | “你已确认 / 拒绝 / 纠正 / 完成 / 延期”详情 | 目标 Feedback、将重算的当前状态、不会删除内容或外部效果 | 追加撤回 → 当前认可 / 业务状态重算 → 依赖派生或索引按需重建；保留历史 |

共同状态至少区分：`accepted`、`active_blocked`、`physical_cleanup_pending`、`physical_cleanup_failed`、`vendor_limited`、`physically_cleaned`、`completed_no_physical_cleanup_required`。页面可以使用用户语言，但语义不能合并。

## 7. 领域语义映射

| 语义 | 流程职责 |
|---|---|
| `Artifact` | 文本原文、链接书签、文件 / 来源指针及稳定版本；承载可打开、导出、删除的内容身份 |
| `Source` | 内容从哪里来、如何定位、当前是否可达、以何许可取得；与 Artifact 分离 |
| `Project` | 用户恢复与选择下一步的上下文边界；未选态合法，但不授予权限 |
| `Derivation` | 恢复包、摘要、推断、候选和索引的输入版本、处理目的 / 位置、授权、生成时间及有效状态 |
| `Feedback` | 确认、编辑、拒绝、纠正、忽略、完成、延期和撤回的追加历史 |
| `Authorization` | 对读取、索引、派生、云 / 第三方处理等执行默认拒绝的六维判定与政策包络 |
| `AuditEntry` | 保存、授权、导出、四类命令和关键状态变化的最小不可还原说明；不成为后台日志流 |
| `Link` | Artifact—Source、Artifact—Project、候选—证据等有来源、确认和有效期的关系；候选 Link 不扩权 |

流程也会消费 `Action / Decision / Event / Assertion`，但本任务不改变其核心语义，也不把上述对象设计成数据库表、页面或 API。

## 8. SP-01 / SP-03 输入清单

### 8.1 共用确定性夹具

建议两项 Spike 复用同一组语义夹具：3 个个人 Project；跨 Project 与无 Project 材料；文本、链接、文件指针；同一 Artifact 的两个版本；可达 / 不可达 Source；用户原文、外部主张、AI 整理、AI 候选、用户确认五类身份；允许 / 拒绝 / 过期 / 撤回 Authorization；候选确认、编辑、拒绝、纠正、完成、延期、撤回 Feedback；删除墓碑；确定性假模型输出。

### 8.2 SP-01 必须继承

1. 保存状态序列：编辑中 → 保存中 → 仅在耐久提交后“已保存”；离线本地已保存与待同步分离。
2. 故障案例：强杀、磁盘满 / 写入失败、重启恢复、重复提交、文件指针失效、备份恢复。
3. 验收断言：原文 / 版本 hash 可核对；失败不丢输入、不覆盖旧版；墓碑和撤回在恢复前优先重放；回执不早报。
4. UI 结果夹具：正常保存、保存中、保存失败、离线已本地保存、恢复后仍不复活已删内容。

### 8.3 SP-03 必须继承

1. 证据链：候选 → Derivation → 精确 Artifact 版本 → Source → Authorization / 处理位置，且可从用户路径回查。
2. 状态案例：未选 Project、跨 Project 候选、来源不可达、输入版本变化、权限撤回、证据冲突、证据不足、用户纠正。
3. 验收断言：Project Link 不扩权；多输入继承最严格限制；旧输出 stale / invalid 后退出正常建议；合法子集变化产生新 Derivation 并显示缺口；用户确认不改写 AI 身份。
4. 结果夹具：完整恢复包 + 一个候选、完整恢复包 + 无可靠建议、部分恢复 + 来源缺口、用户已确认但证据失效 / 待复核。

### 8.4 共用端到端验收案例

- E2E-01：在线文本捕获 → 耐久回执 → 手选 Project → 可核对恢复 → 一个未确认候选 → 编辑确认 → 完成 → 基础导出。
- E2E-02：离线捕获 → 本地耐久保存 → 重启仍在 → 待同步说明，不触发无权限云处理。
- E2E-03：无 Project 捕获 → Inbox 待归属 → 手选 Project 后才进入恢复；系统候选不得静默生效。
- E2E-04：来源不可达 / 权限受限 → 合法子集恢复 + 明确缺口 → 暂无可靠建议。
- E2E-05：候选被拒绝 / 纠正 → 无新证据不重推；相关 Derivation 重建或失效。
- E2E-06：`delete_content` / `revoke_processing` 后活跃路径零命中；备份恢复、重连、旧导入包不复活。
- E2E-07：部分导出明确披露成功、排除与失败范围，不把包误报为完整。

## 9. 后续任务依赖

1. **P1-017 Obsidian 条件需求**应继承：Source / Artifact 分离、只读、不写回、目录 / 文件排除、Project 不扩权、来源不可达、断开后的副本选择、手工导入 / 指针降级，以及 SP-02 + SP-03 双 Pass 条件。
2. **SP-01 / SP-03 任务卡**应继承第 8 节夹具、状态、断言和 E2E 案例；两项不得各自发明对象身份或回执语义。
3. **后续 SP-04 / 05 / 07 / 08**分别验证运行时授权、四命令传播、可信恢复 / 非逐字泄漏、导出 / 重导入不复活；本任务不替代这些 Spike。
4. **未来动态原型 / PRD 补充**应验证 Project 四态、保存回执、证据展开、Feedback 转换和命令状态的理解；不得修改已冻结首页 / 今日页规则。

## 10. 需要 PM / 用户确认的问题

1. **[建议｜需 PM 确认]** 是否接受“今日、Inbox、Projects、找回、数据与权限 + 全局快速捕获”作为自用版最小切片的一层 IA 输入。该确认不等于冻结完整产品 IA 或导航实现。
2. **[建议｜需 PM 确认]** 是否接受对象详情承载完整证据与四命令处置、首页只承担入口 / 影响摘要 / 最小回执的责任分工。
3. **[建议｜需 PM 确认]** 是否批准第 8 节作为 SP-01 / SP-03 共用夹具和验收任务卡输入。
4. **[需后续验证]** 顶层“找回”是否必须独立常驻，还是可并入全局搜索入口；这属于未来原型可用性选择，不影响本任务定义的找回能力。
5. **[需 PM 持续确认]** 本任务不得被解释为技术架构、Schema、API、Obsidian 实现或正式 MVP 开发准入；正式开发继续阻塞。

## 11. 角色与关卡自检

### 11.1 角色检查点

- **主责｜体验设计负责人：Pass。** 用户可从捕获走到保存、Project、恢复、候选、反馈和数据控制；今日保持“从哪里继续”的入口；异常均说明原因、影响和可继续能力。
- **产品架构负责人：Pass。** IA 只覆盖自用最小闭环，不引入企业后台、全局任务墙、完整知识库或自主 Agent。
- **数据 / 领域模型负责人：Pass（语义层）。** 原文 / 来源 / 派生 / 用户确认与五维状态分离；八个指定领域语义均有流程职责，未冻结 Schema。
- **AI 信任与安全负责人：Pass（规则层）。** 候选始终未确认；对象级 Feedback、授权默认拒绝、四命令分离、活跃阻断与真实清理状态均已覆盖。
- **技术架构负责人：Pass（验证合同层）。** 流程已转成 SP-01 / SP-03 的夹具、状态、断言与 E2E 案例，且不依赖未冻结架构。
