- 更新日期：2026-08-08
- 项目阶段：Stage 1（V1 定义）
- 任务类型：研究型任务

- 任务边界：定义只读来源、LifeOS 写入层、导出边界与 Spike 验收输入；不写代码、不设计插件或双向同步、不冻结 Schema/API/技术架构、不放行正式 MVP 开发

## 1. 任务边界与结论摘要

### 1.1 标记口径

- **[事实]**：已由冻结基线、已验收文件或决策日志确认。
- **[推断]**：由既有事实推出、仍需技术 Spike 或用户验证证明。
- **[建议]**：本任务提出的条件需求，待 PM 验收后作为后续输入。
- **[需 PM 确认]**：涉及条件需求采纳、降级或范围结果，专项会话无权冻结。

### 1.2 核心结论

1. **[事实]** Obsidian Vault 在 V1 是 `Should Have + 条件性需求`，不是最小闭环成立前提；必须同时通过 SP-02 与 SP-03，并满足只读、来源身份、分层授权和不写回原文，才能进入实现范围。
2. **[建议]** “只读接入”是对 Obsidian 来源边界的保证，不是对 LifeOS 能力的限制：LifeOS 可读取获准范围、建立来源指针和索引、产生派生与内部业务对象，但所有新增或变化内容写入 LifeOS 自己的写入层。
3. **[建议]** 一个 Vault 是 `Source`；一个 Markdown 文件是外部原始 `Artifact`；观察到的文件内容状态是该 Artifact 的来源版本。路径用于定位，不作为唯一永久身份。frontmatter、标签、链接和附件指针首先是原文片段或显式关系，不自动成为 LifeOS 的事实、Project 或权限。
4. **[事实]** AI 摘要、恢复包、候选下一步、候选关系等保留 `Derivation`；确认、拒绝、纠正、完成、延期、撤回等保留追加式 `Feedback`。用户确认不改写 AI 来源身份，也不修改 Obsidian 原文。
5. **[建议]** V1 可提供用户明确触发的 Obsidian 兼容 Markdown 导出。导出创建独立文件或下载包，是一次性数据迁移动作；不得后台运行、不得冒充同步、不得覆盖来源文件。
6. **[事实]** Project 是恢复上下文边界，不是 Vault 文件夹、标签、双链或授权容器。Project Link 不得扩大 Source 的读取、处理位置或用途权限。
7. **[事实]** 正式 MVP 开发继续为 `Blocked / Not Allowed`；本交付物只形成 Stage 2 Spike 的验证合同输入。

## 2. “Obsidian 只读接入”的定义

### 2.1 允许行为

在当前有效 Authorization 覆盖的 Vault/目录/文件范围内，LifeOS 可以：

- 读取 Markdown 正文与最低来源元数据；
- 解析 frontmatter、标签、标题、Markdown 链接、`[[双链]]`、嵌入和附件路径；
- 在 LifeOS 内建立来源指针、版本记录、全文/关键词索引和解析状态；
- 观察新增、修改、移动、重命名、删除及暂时不可达，并通过对账修复漏掉的文件事件；
- 在单独授权后生成 AI/算法派生、候选 Project Link、候选 Action/Decision 或恢复包；
- 让用户从 LifeOS 的证据入口回到当前可达的 Vault 文件、标题、块或可理解的最近定位；
- 由用户明确触发，将 LifeOS 内容导出为独立的 Obsidian 兼容 Markdown。

### 2.2 禁止行为

LifeOS V1 不得自动或静默：

- 修改正文、标题、frontmatter、标签、链接、嵌入、附件或 `.obsidian` 配置；
- 创建、删除、重命名、移动或重排 Vault 内文件/目录；
- 创建 sidecar、索引文件、锁文件或隐藏元数据污染 Vault；
- 把 AI 摘要、建议、用户确认状态或 LifeOS Project 关系写回来源文件；
- 进行双向同步、后台写回、冲突合并，或把一次性导出描述为“保持同步”；
- 因用户接受一条建议而获得写 Vault、扩大读取范围、云同步或第三方处理权限。

**只读不变量：**在任一测试窗口内，除用户另行执行的明确导出外，连接前后 Vault 树、文件内容 hash 和文件元数据不得因 LifeOS 发生变化。导出若选择 Vault 内位置，也必须经过文件级目标确认、冲突预览和用户提交；它仍是新文件保存动作，不改变 Source 的只读属性。

## 3. Obsidian Source / Artifact 最小语义映射

| Obsidian 概念 | LifeOS 最小语义 | 必须保留/处理 | 不得自动解释为 |
|---|---|---|---|
| Vault | `Source` 容器 | 来源身份、获准根范围、排除规则、处理位置、授权版本、连接/可达状态 | Project、全库授权、云同步许可 |
| Markdown 文件 | 外部原始 `Artifact` | 相对路径、文件名、大小、修改时间、读取时间、内容 hash、编码/解析状态、版本与 Source 指针 | 用户确认事实、已确认 Decision/Action |
| 文件版本 | Artifact 的来源版本 | 精确内容 hash、观察时间、来源修改时间、前后版本关系 | 覆盖旧版本后的唯一真相 |
| 标题/段落/块 | 可定位引用单元 | 原始文本/锚点、解析状态、所属文件版本；V1 不要求每块成为根对象 | 独立业务对象或永久稳定 ID |
| frontmatter | 原始 Artifact 的结构化片段 | 原始键值与解析失败状态；重复/未知字段不静默丢失 | 用户确认事实、Authorization、Project 字段 |
| 标签 | 外部显式标记或原文片段 | 原始写法、位置和文件版本；归一化结果另作 Derivation | LifeOS Project、权限范围、确认分类 |
| Markdown/双链 | 外部显式 Link 候选 | 原始文本、目标字符串、解析/歧义/断链状态、两端版本 | 用户确认关系、授权传播路径 |
| 外部链接 | Artifact 中的外部来源指针 | URL 原文与出现位置；不默认抓取目标内容 | 已验证外部事实或新的读取许可 |
| 嵌入 | 引用/呈现关系 | 原始语法、目标指针、解析状态；目标内容仍按自身许可判定 | 内容复制、跨目录授权 |
| 附件 | 关联 Source/Artifact 指针 | 相对路径、名称、类型/大小（可读时）、可达与排除状态 | Must 的正文提取对象 |
| 目录选择/排除 | Authorization 的范围约束 | 包含/排除规则、授权版本、判定结果 | Project 层级或业务分类 |

### 3.1 最低读取范围

**[建议] Must（接入能力本身若获准实现时）**：`.md` 正文；相对路径、文件名、修改时间、大小、内容 hash、读取时间；frontmatter/标签/标题/链接/双链/嵌入/附件指针的保真解析或明确失败状态；目录与文件排除；新增/修改/移动/重命名/删除/重复/编码异常/附件不可达状态。

创建时间在不同文件系统中可能不可靠，若可取得应作为非权威来源元数据保存，不得用它替代 LifeOS 的 `captured_at`。隐藏目录、`.obsidian`、临时文件和用户配置的排除项默认不进入内容扫描；符号链接或路径规范化后的越界必须拒绝。具体默认排除表由 SP-02 兼容矩阵验证，不在本文件冻结。

### 3.2 身份与变化规则

- 修改：形成新的外部 Artifact 版本；依赖旧版的 Derivation 进入 `stale/invalid` 检查，合法时以当前输入重建。
- 移动/重命名：可依路径、hash、大小/时间及平台可用标识推断同一来源对象的定位变化；不确定时保留“可能为同一文件”的候选，不强行合并。
- 复制/重复：相同内容不等于同一 Artifact；保留各自来源位置，可提出候选重复关系。
- 删除：标记来源侧删除/不可达，不修改外部原件之外的历史；LifeOS 副本按保留许可与 `delete_content` 命令分别处理。
- 编码/解析异常：保留文件级来源记录和失败原因，不用乱码或部分解析覆盖上次有效版本；不得把部分解析冒充完整。
- 附件不可达：保留指针与缺口，不臆造附件内容；附件正文提取属于 Should/条件项。

## 4. LifeOS 新知识写入层设计

**[建议]** LifeOS 维持自己的可写权威层，至少承接：

1. 用户在 LifeOS 捕获的文本、链接、文件/来源指针，作为 LifeOS 内部原始 Artifact 和不可静默覆盖的版本；
2. 用户明确创建或确认的 Action、Decision、Project Link，以及相关状态；
3. AI/算法产生的摘要、分类、恢复包、候选关系、候选下一步等 Derivation；
4. 用户的确认、编辑、拒绝、纠正、忽略、完成、延期、撤回等追加式 Feedback；
5. Authorization、重要 Link 与最小 AuditEntry。

这些内容通过 Link/证据边连接 Obsidian Source 与精确 Artifact 版本，而不是写进 Markdown 原文件。推荐可信链为：

`Obsidian Source → 外部 Artifact/版本 → Derivation → 候选 Action/Decision/Link → Feedback → 用户确认对象/状态`

LifeOS 内部新原文也可与 Obsidian Artifact 建立“引用、依据、补充、回应”等 Link。Link 必须保存建立者/来源、确认状态、有效状态与必要时效；AI 候选 Link 未经用户确认不得冒充用户归属，也不得扩权。

## 5. 内容身份、AI 派生与用户确认规则

| 内容类别 | 写入位置 | 默认身份/状态 | 核心不变量 |
|---|---|---|---|
| Obsidian 原文 | Vault 外部原件；LifeOS 仅按许可保留指针/版本或副本 | 外部来源内容 | 不因接入或 AI 处理成为用户确认事实 |
| LifeOS 用户原始记录 | LifeOS 写入层 | 用户原文、可版本化 | AI 不覆盖；与 Obsidian 引用分离 |
| AI 整理/摘要/恢复包 | LifeOS 派生层 | `Derivation`，未确认或当前有效 | 保留精确输入版本、授权、位置、生成版本、时间和失效状态 |
| AI 推断/建议/候选 | LifeOS 派生层；SP-06/PRD 未批准 L3 前保持 L1 展示 | 未确认候选 | 不自动成为承诺、决定、事实或 Next Step |
| 用户确认内容 | LifeOS 业务/语义层 + Feedback 历史 | 用户已确认，但原始来源身份仍在 | 确认不改写 Obsidian、不洗掉 AI 身份、不扩大权限 |
| 用户反馈 | LifeOS Feedback 层 | 追加记录，可被后续 Feedback 撤回/替代 | 不覆盖历史，不反向修改来源原文 |

状态持续按五维正交表达：来源身份、用户认可、业务状态、证据状态、派生状态。“用户曾确认 + Obsidian 来源不可达 + 证据待复核”可以同时成立。

## 6. 权限、Project 与处理边界

### 6.1 分层 Authorization

连接 Vault 仅表示用户允许 LifeOS 在选定范围执行已披露的本地只读必要处理。以下能力必须分别判定六维 Authorization（主体、范围、动作、目的、位置、时效）及强制政策包络：

1. 本地读取与解析；
2. 本地 FTS/关键词索引；
3. 本地 AI/向量或其他派生；
4. 同步到 LifeOS 云；
5. 发送第三方模型/服务；
6. 为摘要、Project 恢复、候选下一步、跨 Project 建议等具体目的处理。

允许本地搜索不等于允许摘要；允许云同步不等于允许第三方模型；允许某目录不等于允许被其链接引用的排除目录。多输入 Derivation 继承最严格的范围、目的、位置、接收方、保留/删除和披露限制；不能合法合并时缩小输入并显示缺口，或拒绝生成。

### 6.2 Project 不扩权

- Obsidian 文件夹是来源定位结构；标签和双链是外部显式标记/关系；Project 是用户推进工作的上下文边界，四者不自动等价。
- 文件可关联零个、一个或多个 Project；关系可由用户确认或由 AI 作为候选提出。
- 把文件关联到 Project 不得读取原本排除的文件，不得把仅本地内容送云端，也不得让 Project 的其他内容继承该 Source 的许可。
- 当前 Project 只能来自用户本次选择或用户确认的延续；基于文件夹/标签的推断只能作为候选。

## 7. 用户可见流程与状态

### 7.1 连接与日常更新

1. 用户选择 Vault/目录，看到读取范围、排除项、本地索引、AI/云/第三方处理是否启用、保留选择和断开后果。
2. 用户确认后才连接；系统显示首次扫描/索引状态、成功范围、排除范围、异常和最近对账时间。
3. 日常变化按新增、已更新、可能移动/重命名、已删除、解析失败、来源不可达呈现；技术事件流不进入主体验。
4. 恢复包或建议显示“Obsidian 外部来源”、文件/位置、证据版本与时间；可返回来源，不能返回时说明缺口与仍可做的事。
5. AI 证据不足、冲突或受限时显示“暂无可靠建议”或合法子集结果，不生成看似完整的叙述。

### 7.2 用户必须能区分的状态

| 状态/动作 | 用户可见含义 | 最低系统行为 |
|---|---|---|
| 已连接 | 当前范围可按授权读取 | 不代表云/第三方已授权 |
| 正在索引/更新 | LifeOS 正在更新自己的派生索引 | 不修改 Vault；旧结果标明时效 |
| 来源暂不可达 | 当前不能核对最新原件 | 不推断为删除；依赖结果 stale，显示上次可用时间 |
| 已断开来源 | 停止继续访问/监听 | 不自动等于删除 LifeOS 副本；按用户保留选择处置 |
| 已撤回处理许可 | 指定用途/位置停止使用 | 活跃路径先阻断，物理清理状态继续可见 |
| 已删除 LifeOS 内容 | LifeOS 可控目标及可识别副本进入删除 | 不声称删除外部 Vault 原件；墓碑防重导入复活 |
| 已撤回 Feedback | 原响应不再维持当前效力 | 追加撤回并重算，不删除内容或历史 |
| 已导出 | 一次性生成文件/包 | 不建立持续同步关系 |

## 8. Markdown 导出与非写回边界

### 8.1 V1 建议能力

**[建议｜需 PM 确认]** 支持用户从 LifeOS 选择自己有权导出的内容，明确触发“一次性导出为 Obsidian 兼容 Markdown”：

- 导出 LifeOS 用户原文、用户确认的 Action/Decision/Project 关系、可选择的 AI 派生与 Feedback 摘要；
- 用清楚的标题/frontmatter 或正文分区标明内容身份、生成时间、确认状态和来源引用，绝不把 AI 内容伪装为用户原文；
- 外部 Obsidian 原文默认用来源指针/引用表达，避免在新文件里无提示复制；若用户明确选择包含合法保留副本，导出清单须说明范围与许可限制；
- 默认生成下载包或 Vault 外目标；若用户选 Vault 内目录，必须选择目标、预览文件名与冲突处理，并逐次提交；默认不得覆盖已有文件；
- 返回完整/部分/失败状态及排除项类别；导出记录最小 AuditEntry。

### 8.2 明确非同步

一次导出完成后，LifeOS 不监视或继续更新该导出文件，不把它与内部对象建立自动回写通道，不因导出取得未来写权限。再次导出必须再次由用户触发。自动合并、覆盖、冲突解决、增量回写、双向状态同步均为 Not Now。

## 9. 异常、撤回、断开、删除与不可达处理

| 情形 | Source/Artifact | Derivation/索引 | 用户确认对象与反馈 |
|---|---|---|---|
| 文件修改 | 新来源版本，旧版按保留规则留存 | 依赖旧版者 stale；合法时产生新 Derivation | 不自动撤销确认；若证据变化则提示复核 |
| 移动/重命名 | 高确定性更新定位；歧义保持候选/新对象 | 指针重判，不能错误强合并 | 保留历史，必要时提示来源定位变化 |
| 来源删除 | 标记来源侧删除/不可达；外部原件不受 LifeOS 控制 | 退出最新结果或 stale/invalid；副本按保留许可 | 唯一证据失效则 `evidence_unavailable/review_required` |
| 暂时不可达 | 保留上次状态与时间，不等同删除 | 不伪装最新；允许合法保留副本但受时效/许可约束 | 保留历史并披露证据缺口 |
| 目录被排除/撤权 | 后续读取立即拒绝 | FTS、向量、缓存、队列、建议退出活跃使用并追踪清理 | 不抹掉历史确认；失去唯一证据时待复核 |
| `disconnect_source` | 停止读取/监听/同步 | 实时依赖 stale/invalid；副本按连接时保留选择处理 | 不等于撤回 Feedback 或删除内容 |
| `delete_content` | 删除 LifeOS 控制的目标/副本；不动外部原件 | 依赖物 invalid，可还原派生/索引清理 | 若确认对象本身被删则删除；否则证据失效待复核 |
| `retract_feedback` | 无直接影响 | 直接依赖该反馈者重建或失效 | 追加撤回，重算认可/业务状态，不改写历史 |

四类命令不得互相冒充。所有撤回/删除至少区分 `accepted`、`active_blocked`、`physical_cleanup_pending/failed`、`vendor_limited`、`physically_cleaned` 或“无需物理清理”。未达到活跃路径零遗漏阻断前，不得向用户声称“已停止使用”。

## 10. Must / Should / Not Now 条件需求

### 10.1 Must（Obsidian 条件能力获准进入实现时不可降级）

- Vault 全程只读且可通过前后树/hash及写调用拦截验证；无 sidecar、无 `.obsidian` 或原文件变化。
- Source/Artifact/版本分离，保留最低来源元数据、内容身份、可达/解析/变化状态和可返回的来源指针。
- 支持目录/文件排除、路径规范化与越界拒绝；撤权后不再读取、索引、发送或用于建议。
- Markdown、frontmatter、标签、标题、链接、双链、嵌入和附件指针至少能保真解析或明确失败。
- LifeOS 新原文、Derivation、确认对象和 Feedback 全部写入 LifeOS 层，不写回 Vault。
- 分层六维授权、Project 不扩权、多输入最严格约束、权限/版本变化后的失效传播成立。
- 用户可区分索引、不可达、断源、撤回处理、删除 LifeOS 内容、撤回 Feedback 和一次性导出。
- SP-02 与 SP-03 均 Pass；任一未通过均不得承诺 Obsidian V1 正式接入。

### 10.2 Should（可在条件/成本验证后进入）

- 在高确定性样例中自动识别移动/重命名，歧义可由用户纠正；不承诺无损识别。
- 提供 Obsidian 兼容 Markdown 一次性导出及部分导出报告；Vault 内保存仍需逐次明确触发。
- 为标题/块提供较稳定的证据定位和返回体验。
- 附件类型/大小元数据与可达性；附件正文提取仅在范围、性能和权限均验证后考虑。
- 以透明状态展示初次扫描、增量对账和来源恢复；具体时间/SLO 待 SP-02 实测。

### 10.3 Not Now

- Obsidian 插件、双向同步、后台写回、自动覆盖/合并、写入 frontmatter/标签/双链/正文。
- 用文件夹、标签、双链自动创建/确认 Project、Action、Decision、事实或 Authorization。
- 自动把 LifeOS 内容持续发布到 Vault，或自动把导出文件与内部对象保持一致。
- 全量附件摄取与内容提取、支持所有社区插件私有语法、读取 Obsidian 私有内部数据库。
- 冻结具体 watcher、存储、Schema、API、桌面框架、冲突算法、供应商或删除 SLA。

## 11. SP-02 / SP-03 输入清单

### 11.1 SP-02：夹具、断言与验收案例

**确定性夹具**：多目录模拟 Vault；包含 `.md`、YAML 正常/异常/重复字段、标签、标题/块引用、Markdown/双链、嵌入、附件指针、破损链接、同名/同内容文件、非 UTF-8/乱码、隐藏及 `.obsidian`、排除目录、符号链接越界；覆盖新增、修改、重命名、同/跨目录移动、复制后删除、同时修改删除、应用离线期间变化、来源暂不可达。

**必须断言**：

1. 全程 Vault 树、原文件 hash 和元数据无 LifeOS 引起的变化，写/改名/删除/sidecar 调用为零；
2. 首扫与稳定窗口内增量变化 100% 对账，丢 watcher 事件后 reconciliation 可恢复；
3. 明确重命名样例达到既定 Spike 工程门槛，歧义样例错误强合并为零；
4. 排除目录、撤回目录、路径遍历和符号链接越界读取/索引/外发为零；
5. 来源指针能回到 Vault/文件/标题或块；不可达时返回明确缺口；
6. 解析失败不覆盖上次有效版本，不把部分结果标为完整；
7. 断开 Source 后停止监听/读取，保留副本严格服从既有保留许可。

### 11.2 SP-03：夹具、断言与验收案例

**两条证据链**：`Obsidian 原文版本 → 恢复包/候选下一步 → 编辑确认 → 完成 Feedback`；`Obsidian/外部材料 → Decision 证据 → 输入更新/删除/撤权 → 证据失效与待复核`。

**必须断言**：

1. 任一关键输出可反查全部精确输入版本、Source、Authorization/政策版本、目的、位置/主体、工作流/模型版本、生成时间、输出身份、状态和 Feedback；
2. Obsidian 原文、LifeOS 用户原文、AI Derivation 和用户确认对象不存在共享的可静默覆盖权威字段；
3. Project Link、标签/文件夹/双链均不扩权；多输入继承最严格限制；合法子集变化必须产生新 Derivation 并显示缺口；
4. 修改、删除、不可达、断源、撤权、Feedback 撤回只影响正确依赖闭包，无漏报且不触发无法解释的全库失效；
5. 用户确认不洗掉 AI 来源身份；证据失效不删除确认历史，而是退出自动依据并待复核；
6. 导出能区分身份、版本、来源和部分失败，删除墓碑/撤回在重导入时优先，已删除内容不得复活；
7. 最小映射不依赖图数据库、全量事件溯源、11 张固定表或企业审计平台。

### 11.3 对其他 Spike 的影响

- **SP-04**：加入 Vault 本地读取、索引、AI 派生、云同步、第三方处理分层授权；测试 Project Link/嵌入不扩权、长任务撤权竞态和凭据硬拒绝。
- **SP-05**：加入目录排除、断源、撤回处理、删除 LifeOS 副本四种影响集合；验证 FTS/向量/缓存/队列/备份/第三方 mock 的活跃阻断与清理状态。
- **SP-08**：加入 Obsidian 兼容 Markdown 的完整/部分/失败包、身份标记、来源引用、禁止重导入复活及“导出不建立同步”断言。
