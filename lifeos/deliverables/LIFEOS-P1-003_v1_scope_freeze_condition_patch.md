## 3. V1 Must 最小范围合同

Must 的最低可验收切片是：用户能捕获并可靠保存项目原始记录，借助最低找回路径恢复可信 Project 上下文，获得至多一个有充分依据的候选下一步，完成核对与反馈，同时保有最低权限、删除、导出和审计保障。

1. **捕获与保存**：Must 支持文本、链接、文件 / 来源指针；文件最低能力仅包含指针及必要来源元数据，例如可理解的名称或类型、来源定位、捕获时间、可访问状态与版本/完整性线索。完整文件摄取、正文解析、附件管理、格式覆盖、内容提取属于 Should / 条件项，不得作为 Must 验收的隐含要求。
2. **找回与恢复**：以 `Project` 为边界，通过 **FTS + 元数据**形成最低找回路径，并能回到相关 `Source / Artifact`。向量检索、混合重排、跨源自动关联及专用搜索基础设施不是 Must 前提；是否加入由 SP-07 / SP-09 的增益证据决定。
3. **AI 最低产出**：在有效 `Authorization` 与证据范围内，提供可核对的 Project 恢复信息，并在依据充分时提出 **1 个**候选下一步，标明 AI 身份、所属 Project、理由、关键来源、时效/缺口与未确认状态。若依据不足，应诚实呈现证据缺口或“暂无可靠建议”，不得为满足数量而生成建议。
4. **支撑手段边界**：摘要、分类、候选关联是形成恢复信息和候选下一步的可选手段，不要求各自成为独立、完整、通用的 Must 功能面。首页 / 今日页的 1–3 个候选只是场景呈现上限，允许少于 1 个；不是强制凑数，也不改变“先找回上下文”的价值排序。
5. **用户权威与信任底线**：用户能核对原文/外部来源与 AI 派生，确认、编辑、拒绝、纠正、完成或延期；AI 不替用户确认事实、决定、承诺或当前下一步。四类命令、分层授权、派生失效、活跃阻断、清理状态、基础可迁移导出和最小审计继续作为 Must 的最低价值合同，但不冻结完整后台、全量日志、物理清理 SLA、格式或实现。

## 4. 四类命令的范围级约束

四类命令必须继承 `P0-004 + P0-007` 与 `P0-003 + P0-009` 的冻结语义；组合意图必须显式组合命令，不能用含糊的“移除 / 撤回”替用户推断：

| 命令 | V1 范围级意图 | 不得冒充的结果 |
|---|---|---|
| `revoke_processing` | 撤回指定主体、范围、动作、目的、位置或时效下的处理许可；命中数据立即退出相关活跃使用 | 不自动断开 Source，不自动删除权威原文或用户确认历史 |
| `disconnect_source` | 停止继续读取、监听或同步某 Source；既有内容按独立保留许可处理 | 不等于删除所有已保存内容，也不等于撤回 Feedback |
| `delete_content` | 删除目标内容及 LifeOS 可控的可识别副本；依赖派生失效，墓碑优先并追踪清理 | 不得只停止处理却继续保留可识别目标；不能声称已删除 LifeOS 不控制的外部原件 |
| `retract_feedback` | 追加撤回记录，撤销某条确认、拒绝或纠正对当前状态的效力并重算依赖 | 不删除内容、不撤销来源授权、不逆写或抹去历史 Feedback |

所有命令均须区分“已耐久接受”“活跃使用已阻断”与物理清理中、失败、供应商受限、可控范围已完成或无需清理等状态。`Authorization`、`Source` 连接、`Artifact` 保留、`Derivation / Link` 失效、`Feedback` 历史和 `AuditEntry` 最小记录分别处理；具体字段、状态机和 UI 不在本补丁冻结。

## 5. Obsidian V1 条件合同

- **优先级**：Obsidian Vault 固定为 **Should Have + 条件性需求**。它是首批技术型独立产品构建者的高价值来源和重要验证对象，但不是“捕获—保存—找回—确认下一步—反馈”最小闭环成立的前提。
- **进入条件**：只有 SP-02 与 SP-03 均通过，证明只读接入、可靠来源身份/指针、`Source / Artifact / Derivation` 证据链、分层授权、目录排除及 AI 派生不写回原文，Obsidian 才进入 V1 实现范围。
- **失败降级**：任一 Spike 未通过时，优先降级为手工导入或来源指针；若仍无法守住来源、只读或授权底线，则移出 V1。具体结果属于 V1 范围变化，须由 PM 记录。
- **排期约束**：PRD、排期和验收不得把 Should 静默升级为 Must，不得让 Obsidian 阻断不依赖它的最小闭环，也不得扩张为插件、双向同步或自动写回。

## 6. 最小用户验证合同

### 6.1 招募与测试任务

- 招募对象须满足第一目标用户行为门槛：个人或极小规模构建，实际同时维护 1–3 个项目；每周多次跨项目/工具切换；至少使用四类工具承接信息；已有主动记录/回顾和 AI 使用习惯，并明确关注本地保存、导出、来源或模型边界。
- 使用参与者真实的、或在敏感信息处理后仍等价的中断项目；项目应存在离开后返回、近期变化、未处理材料/行动或待确认下一步，不能用无历史的演示项目替代。
- 同一参与者先按当前拼接工具方式完成恢复基线，再用 LifeOS PRD / 原型所代表的最小切片完成同类任务；不要求现阶段虚构可运行产品。

### 6.2 观察与判定

必须记录：是否找到停点和近期关键变化；是否能定位支撑结论/建议的原文或外部来源；是否能区分 AI 派生与用户确认；是否能确认、纠正或拒绝一个合适的下一步；完成所需的工具跳转、追问、回查、犹豫和主观认知负担。上下文是否可信、下一步是否适合由参与者最终判断，研究者记录依据与失败点，不替用户判定。

**[建议]** “明显改善”不预设虚构数字：至少应在可信恢复、依据定位、下一步确认三项中表现出相对当前方式的实质改善，且没有以更高确认负担或信任损失换取表面速度。若结果混合或参与者无法解释改善来自何处，按未证实处理，进入下一轮验证而非宣称 Gate 5 已通过。

### 6.3 必记反证与失败动作

必须记录：用户不愿持续捕获、导入或连接来源；恢复仍依赖回到原工具重新拼接；AI 建议缺证据、过时或误导；核对/确认成本高于收益；权限与内容身份难理解；首页制造未完成焦虑；产品只被理解为开发者工具。

若没有明显改善，按证据优先收窄而非增加功能：先收窄低价值/高摩擦来源，再压缩首页信息面或改为用户主动选择 Project，最后缩减 AI 建议面至恢复信息、证据缺口或单一候选；随后重审“项目恢复与下一步确认”的价值假设。任何范围调整、价值假设变化和数字阈值均需 PM 确认；本合同不等于已完成用户验证。
