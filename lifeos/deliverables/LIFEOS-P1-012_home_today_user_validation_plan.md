# LIFEOS-P1-012｜首页 / 今日页用户验证计划与测试脚本

## 1. 任务状态与范围声明

- 任务类型：研究型任务；当前状态：Completed，待 PM 验收。
- **[事实]** `LIFEOS-P1-004 + P1-006` 已冻结为首页 / 今日页 PRD V0.1；三张 `LifeOS 精修版` 已冻结为静态关键原型 V0.1。冻结不包含动态交互、响应式、可访问性、技术实现、用户验证结果、Stage 2 或 MVP 准入。
- **[事实]** 本任务只形成可执行研究计划，没有招募、联系或测试真实用户，没有修改 Stitch、PRD、代码、页面或状态。
- **[证据边界]** 当前没有 LifeOS 一手用户测试结果。下文数字仅是小样本形成性研究的操作判定线，不是市场统计结论、商业 KPI、留存率或付费率目标。
- **[建议]** 先验证静态首屏与三态理解，再验证真实 / 等价中断 Project 恢复。前者只能证明“可理解”，不能替代后者对“有价值”的证明。

## 2. 验证目标与关键假设

本轮要证明或推翻以下假设：

| ID | 待验证假设 | 主要证据 | 关键反证 |
|---|---|---|---|
| H1 | 用户在 5–10 秒内把首页理解为个人 Project 上下文恢复入口，而非 IT 运维台、企业后台、团队工作台或任务墙 | 无提示首屏复述、第一动作 | 以监控、工单、全局待办、团队排期为主叙事 |
| H2 | 用户能区分用户原文、外部来源、AI 整理、AI 建议 / 未确认、用户确认内容 | 指认、解释身份及可执行动作 | 把 AI 建议当事实、安排或承诺；把“你已确认”当系统核验 |
| H3 | 用户理解候选下一步在确认前不是已安排事项 | 对默认态候选和“今日安排”的比较 | 认为系统已经替自己排定，或直接把候选标为完成 |
| H4 | “暂无可靠建议”被理解为证据不足时的诚实降级，且用户仍知道如何继续 | 原因—影响—动作复述、接受度追问 | 认为系统坏了、无价值，或最近痕迹会被静默跨 Project 推断 |
| H5 | 权限受限 / 离线态能让用户说清原因、影响及仍可继续的动作 | 分层复述、动作选择 | 认为全部数据丢失、已确认内容失效、AI 仍可读取受限来源，或无法继续记录 |
| H6 | 该信息结构足以支持中断 Project 的可信恢复，并优于现有拼接方式 | 同一参与者的现状基线与恢复测试 | 仍需回原工具重拼；核对成本或不信任抵消速度收益 |

**研究结论边界：** H1–H5 可由静态原型形成初步证据；H6 只有使用参与者真实项目，或经过脱敏但保持真实停点、变化、决定和来源结构的等价项目，才能形成价值证据。固定演示内容最多判断“测试就绪”，不能通过 Gate 5 的真实价值部分。

## 3. 参与者画像、样本与筛选

### 3.1 正式样本建议

- 主样本：至少 8 名技术型独立产品构建者，分两批各 4 名；第一批后只修订测试脚本或测试材料问题，不改冻结原型，第二批验证问题是否稳定出现。
- 次级对照：可选 2–4 名技术 / AI 产品经理或多客户独立顾问，单独分析，不与主样本合并计算通过线。
- 样本是形成性验证，不做总体推断。若第 8 名后关键误读仍出现新类型，建议追加一批，而不是用比例掩盖未饱和问题。

### 3.2 必须满足的招募条件

1. 个人或极小规模构建，但工具选择和项目推进主要由本人决定；LifeOS 服务个人上下文而非团队管理。
2. 当前实际维护 1–3 个软件、AI 产品、技术副业或长期技术项目。
3. 每周至少多次在编码、产品思考、研究、用户反馈和个人事务之间切换，并能举出最近一次中断恢复。
4. 信息分布在至少四类工具 / 来源，例如代码库、Issue、AI 对话、Markdown/Obsidian/Notion、网页、聊天、日历、临时记录。
5. 已有主动记录或回顾习惯，并实际使用 AI 做编码、研究、写作或规划。
6. 对本地保存、导出、来源可核对或模型数据边界至少一项有明确要求。
7. 愿意在不暴露敏感内容的前提下使用真实或等价中断 Project 参加后续恢复测试。

### 3.3 配额与排除

样本尽量覆盖：不同主记录工具、不同 AI 使用强度、不同隐私敏感度、独立工作年限和项目类型；不能全是设计师或当前项目熟人。排除 LifeOS PRD / 原型参与者、已看过三张截图者、以 IT 运维监控为主要工作且不符合第一用户行为门槛者、只做单一短期编码任务者，以及无法提供近期真实切换实例者。

### 3.4 招募筛选问题

先问行为，不透露理想答案：

1. 过去四周你同时推进哪些个人项目？各自持续多久？
2. 最近一次隔几天返回某项目时，你按什么顺序找回上下文？打开了哪些工具？
3. 过去一周使用过哪些记录、项目、AI、网页、沟通或日历工具？
4. 什么信息一旦漏掉或记错，会带来返工或错误决定？
5. 你允许 AI 读取 / 整理哪些内容？哪些绝不允许？为什么？
6. 你是否有一个中断至少 3 天、且材料足以脱敏的 Project 可用于测试？

筛选记录须保存原始回答和判定理由；不得仅凭“独立开发者”职业标签入组。

## 5. 测试流程（单场约 60–75 分钟）

1. 说明与同意（5 分钟）：说明测试产品而非测试参与者；可跳题、撤回和随时停止。
2. 现状访谈（10 分钟）：在展示原型前了解最近一次真实中断、当前拼接方式和信任边界。
3. 5–10 秒首屏理解（5 分钟）：默认态无引导暴露 8 秒后遮罩并复述。
4. 默认恢复态深测（10 分钟）：身份、候选与确认边界、第一动作、压力感。
5. 另外两态逐张测试（10–15 分钟）：参与者按 AB/BA 交替顺序观看，降低固定顺序效应。
6. Project 恢复测试（20 分钟；若本场只有静态刺激物，则执行“测试就绪检查”，不得宣称价值通过）。
7. 总结访谈（10 分钟）：比较现有方式、价值、导入意愿、学习 / 核对成本和反证。

主持人禁止先说“个人外脑”“恢复入口”“这是 AI 建议”“它很诚实”等目标答案；参与者沉默时用“请继续说你在看什么 / 会做什么”，不用“你有没有注意到……”诱导。

## 6. 5–10 秒首屏理解测试脚本

**主持词：**“接下来会看到一个尚未发布产品的页面 8 秒。像平常打开新工具一样看即可；页面消失后，请告诉我你认为它是什么。现在不需要点击。”

遮罩后依次问：

1. 这是什么页面？你会用自己的话怎么称呼它？
2. 它主要帮助谁、解决什么问题？
3. 你刚才最先看到什么？如果继续使用，第一步会做什么？
4. 页面上哪些内容是你自己的，哪些来自别处，哪些可能由系统生成？只说记得的即可。
5. 它有没有让你联想到后台、运维、团队管理、任务清单或别的产品？为什么？

记录首次提及内容、顺序和原话。研究者只在全部自由回答结束后追问未覆盖项。首屏单项判定：能自然提到“回到 / 继续某个个人项目、找回上次上下文或决定下一步”即主叙事命中；仅说“看任务、监控项目、团队工作台、IT 面板”不算命中。

## 7. 三状态逐张测试脚本

### 7.1 默认恢复态

给出任务：“假设你昨天暂停了这个项目，今天回来。请边想边说，指出你会先看哪里，以及你认为接下来发生什么。”

- 当前是哪一个 Project？系统为什么显示它？你能否看出是自动猜测还是沿用上次确认？
- 用一句话说上次停点。哪三条内容支持它？分别是谁写的 / 从哪里来？
- “AI 建议·未确认”和“你已确认·决定”有什么不同？哪一个已进入你的安排？
- 如果建议不合适，你会怎么做？“确认、编辑、拒绝、忽略”分别意味着什么？
- “继续设计”与候选建议是什么关系？你是否有足够信息采取下一步？还缺什么？
- 这个页面让你更有掌控感，还是增加未完成压力？请指出具体元素。

### 7.2 暂无可靠建议

给出任务：“你打开页面后看到这个状态。请解释发生了什么，并实际指出你仍能做的下一步。”

- 为什么没有建议？这是故障、数据不足、未选 Project，还是别的原因？
- “选择 Project”和“先记到 Inbox”各适合什么情况？
- 下方最近痕迹是什么身份？系统会不会用它们直接生成当前恢复或建议？你从哪里判断？
- 如果系统经常在证据不足时显示这个状态，你会更信任、无感还是失望？什么频率 / 情境会改变判断？
- 你希望系统此刻做更多吗？若希望，追问“这会不会需要更多读取权限或引入错误建议？”

### 7.3 权限受限·离线

给出任务：“请先不要解决问题。先按‘原因—影响—还能做什么’解释页面，再选择你会采取的动作。”

- 当前有几个不同限制？网络离线和来源权限受限分别影响什么？
- 哪些内容仍可查看？哪些恢复信息 / 建议不可用？AI 现在是否应读取访谈来源？
- “你已确认·决定”和“今日安排”是谁确认的？来源暂不可用会不会把它们改回 AI 判断？
- 现在记录一条内容会发生什么？“已在本地耐久保存，离线待同步”对你意味着什么？（仅测文案理解，不把静态文案当技术证明。）
- “查看影响”和“继续无 AI”分别会带来什么？你会选哪一个，为什么？
- 哪一句仍不清楚、太技术化或让你不安？

## 8. 真实 / 等价中断 Project 恢复测试

### 8.1 设计分层

**A. 测试就绪检查（当前静态原型可做）：** 参与者基于固定示例指出恢复所需位置，并用自己的真实项目逐项映射“停点、变化、决定、原文 / 来源、候选下一步、缺口”。结论只能是信息结构是否足够、缺少何种动态或内容能力。

**B. 等价中断测试：** 经参与者确认，将一个真实中断 Project 脱敏成测试包，保留真实时间顺序、矛盾、遗漏、来源身份和已确认决定；由研究者按冻结信息结构制作测试专用夹具。夹具不是新产品页面，不改冻结 Stitch，必须标注为研究材料。它可验证恢复路径，但脱敏和整理可能降低真实混乱度，结论须注明限制。

**C. 真实中断测试：** 后续可运行产品或 Wizard-of-Oz 流程必须使用真实授权内容，并与现有工具基线比较，才能形成 Gate 5 的强证据。若只能展示固定示例，不得把“回答正确”写成价值改善。

### 8.2 基线与任务

选择过去 30 天内中断至少 3 天的 Project。先让参与者按现有方式恢复，计时上限 10 分钟，任务为：“请恢复到你愿意开始工作的程度，并说出：上次停在哪里；此后有哪些关键变化；一个重要决定及依据；未处理事项；你现在愿意确认的下一步。需要时请打开原文。”随后对同一 Project 的预先冻结快照执行 LifeOS 测试夹具；为避免第一次回忆污染第二次，正式研究优先使用两个复杂度相近的 Project 并在参与者间对调基线 / LifeOS 顺序。无法配对时必须把学习效应列为限制。

记录：完成度、耗时、工具跳转、搜索 / 回查次数、错误或遗漏、证据定位成功、追问、犹豫、确认 / 纠正 / 拒绝、主观负担（1–7）和信任理由。速度只在恢复内容正确且来源可核对时有意义。

结束追问：“哪一步比你现有方式明显更好 / 更差？如果明天真实使用，你愿意连接或导入哪些来源、拒绝哪些？维护和核对成本是否值得？若没有这个页面你会损失什么？”

## 9. 总结访谈提纲

1. 不看页面，用你的话说这个产品今天最主要帮你做什么。
2. 哪部分最可信、最不可信？是什么证据造成该判断？
3. 你如何判断一条内容是原文、外部来源、AI 整理、未确认建议或你已确认的内容？
4. 你最可能确认、编辑、拒绝或忽略哪类建议？为什么？
5. “暂无可靠建议”在哪些情境可接受，何时代表产品没有价值？
6. 你愿意为恢复 Project 连接哪些来源？对本地、云端和第三方模型有什么限制？
7. 与当前做法相比，学习、导入和持续维护的成本是否值得？请举最近实例，不问抽象“你会不会用”。
8. 什么结果会让你彻底不用它？若必须删掉一个模块，你删什么？
9. 如果可自由选择，你是否会为这类改善付费？为什么？本轮只记录语言和既有付费替代，不设置价格或转化目标。

## 10. 观察指标、判定线与反证信号

| 维度 | 记录指标 | 形成性通过线 | 返工 / 反证信号 |
|---|---|---|---|
| 首屏主叙事 | 8 秒后自由复述、第一动作、后台联想 | 主样本至少 6/8 命中个人 Project 恢复；至多 1/8 以运维 / 企业后台 / 任务墙为主解释 | 2 名及以上稳定主误读，或第一动作集中在监控 / 全局清任务 |
| 内容身份 | 五类身份指认及理由 | 至少 6/8 能正确解释关键五类中的四类，且 AI 建议与用户确认均正确 | 任意 2 名把 AI 候选当已确认承诺；原文 / AI 大面积混淆 |
| 无建议 | 原因、继续动作、跨 Project 护栏 | 至少 6/8 说清未选 Project / 证据不足并找到一个继续动作 | 多数视为系统故障，或认为最近痕迹会被静默用于建议 |
| 受限 / 离线 | 原因—影响—动作三段式 | 至少 6/8 区分两类限制，并能指出仍可查看 / 记录及一个动作 | 2 名及以上认为数据丢失、AI 仍可读受限源或本地保存等于已同步 |
| 恢复价值 | 基线对比的正确恢复、证据定位、下一步确认、负担 | 多数参与者在“可信恢复、证据定位、下一步确认”中至少两项有实质改善，且无更高核对负担或信任损失 | 仍回原工具重拼；错误 / 过时建议增加；核对成本高于收益；不愿提供最低必要来源 |
| 健康压力 | 1–7 负担、压力原话、回避行为 | 无系统性“欠债、被安排、被监控”解释 | 多数把首页理解为催促或把 AI 候选当必须完成 |

上述 `6/8` 是形成性报警线，不是统计显著性。以下为零容忍事件：原文被理解为可由 AI 静默改写；未确认建议被界面表达为已承诺；受限来源被认为仍可供 AI 使用；测试材料泄露参与者秘密。任一发生即暂停结论，先定位是刺激物、主持脚本还是原型问题。

## 12. 通过、条件通过、返工与阻塞规则

- **Pass（计划执行后的研究结论）**：H1–H5 达到形成性通过线；真实 / 等价恢复证据显示相较现状有可信改善；无 S4，且改善不是靠更高核对成本、诱导或暴露更多权限换来。仅 PM 可据报告判断 Gate 5 是否通过。
- **Pass with Conditions**：主叙事成立，但存在集中于非核心文案、测试夹具或特定状态的 S1–S2；给出明确整改项和复测范围。只允许有限原型调整建议，不自动改变 PRD / V1。
- **Rework**：首屏、内容身份、候选确认、无建议或受限态任一出现重复 S3；或固定演示可懂但真实恢复无改善。先判断是原型表达、信息结构还是价值假设问题，再由 PM 下发任务。
- **Blocked**：刺激物哈希不一致、样本不符合第一用户、隐私授权不完整、真实 / 等价项目材料不足，或只能使用固定演示却要求作价值结论。阻塞时不得补写“通过”。

决策路径：

1. 仅文字 / 层级误读且不改变信息结构 → 建议有限原型返工并对失败项复测。
2. 多数用户仍不把首页理解为 Project 恢复，或恢复所需信息结构缺失 → 可能影响首页 / 今日页 PRD，**需 PM 确认**并按关键资产规则评审。
3. 用户真实恢复无改善、不愿提供最低必要来源、或核对成本持续高于收益 → 重审第一场景 / V1 假设；任何范围增删均 **需 PM 确认**，不得用新增功能掩盖反证。
4. 身份、权限或用户确认底线失败 → 暂停相关测试与阶段推进，回到 Gate 2 / Gate 3 整改；不得以平均分抵消。
5. 即使计划或首轮研究通过，也不自动进入 Stage 2 或 MVP 开发；阶段准入由 PM 结合其他任务和关卡决定。

## 13. 风险、伦理与隐私

- 只收集完成研究所需的最小资料；优先由参与者自己脱敏。禁止上传密钥、客户机密、未发布代码、财务 / 医疗 / 法律 / 心理敏感材料和第三方个人信息。
- 真实项目测试须逐来源说明本地、云端、第三方模型和录屏可见范围；录音、录像、屏幕共享分别同意。拒绝录制不应影响参与资格或补偿。
- 使用 Participant ID；身份表与研究记录分离存放；预先确定访问人、保存期限、删除日期与退出后的处理方式。参与者可跳题、暂停或撤回。
- 研究者不得替参与者登录私人账号；需要原工具基线时由参与者操作。屏幕意外出现秘密时立即停止录制、标记并删除对应片段。
- 不把 AI 建议包装成专家意见，不测试高风险诊断或自动执行，不因“愿意尝试”推断依赖、付费或长期留存。
- 主要偏差包括熟人样本、技术爱好者迎合、主持人诱导、固定顺序、演示项目过于整洁和二次任务的记忆污染；通过陌生合格样本、无提示首问、顺序交替、真实混乱材料和偏差日志缓解。
- 沿用 R-0002、R-0003、R-0007、R-0009、R-0011、R-0014、R-0015、R-0019、R-0023、R-0025；本计划未发现必须由专项会话直接新增的风险类型。

## 14. 角色检查点与关卡结论

- 主责（用户研究 / 市场验证）：已定义要证明 / 推翻的假设、主样本、非诱导脚本、真实价值与表面理解的区分、指标、反证和决策规则。
- 产品架构协审：样本、任务和判定均锁定 V1 第一用户与“5 分钟 Project 恢复 + 下一步确认”，未扩成泛 LifeOS 愿景或开发者工具测试。
- 体验设计协审：覆盖 8 秒首屏、三状态、身份、第一动作、认知负担和压力感。
- 数据 / 领域模型协审：观察 `Project`、`Source / Artifact`、用户原文、AI 派生、建议与用户确认的理解；不把语义对象当 UI 或 Schema 冻结。
- AI 信任与安全协审：覆盖未确认建议、无建议、权限 / 离线、继续无 AI、来源不可用和用户确认边界。
- Gate 1：**计划层 Pass**；真实用户理解待执行。
- Gate 2、Gate 3：**研究覆盖层 Pass**；不代表数据 / 权限实现通过。
- Gate 5：**验证计划与测试脚本层 Pass；一手用户价值证据 Not Yet Available**。本任务不宣称 Gate 5 已通过。
