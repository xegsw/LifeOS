# LIFEOS-P2-019｜最小纵向切片验收合同、风险—测试追踪矩阵与能力启用门

- 任务类型：补丁 / 条件整改型任务
- 主责角色：PM / 技术架构负责人
- 状态口径：专项交付，待 PM 验收；不新增冻结、不代表工程能力已实现或已启用
- 适用边界：单用户、单设备、本地优先、非商用、无外部用户、外部能力默认关闭

## 1. 结论摘要

1. **[事实]** D-0127 已准入“有限 Stage 3 / 自用 MVP 最小切片”，但 Gate 5 结果层未通过，R-0040 仍为 `Open / Conditional`；真实数据、真实 Vault、真实 Tauri 文件能力、导出扩权、云 / 第三方模型、向量及 L3 均未获启用许可。
2. **[建议｜待 PM 验收]** 首个可验收纵向切片固定为：捕获用户原文 → 权威耐久保存 → 用户选择 Project → 以当前合法证据恢复上下文 → 给出零或一个未确认候选 → 用户确认 / 拒绝 / 纠正 → 删除 / 撤回活跃阻断 → 基础导出 / 恢复候选验证。
3. **[推断]** 确定性规则或 stub、FTS + 元数据、合成数据足以验证上述闭环；若闭环本身不能稳定恢复上下文和完成反馈，增加模型、向量、连接器或文件权限不能补救核心价值失败。
4. **[建议]** 后续任何工程任务必须引用本合同的约束 ID、测试 ID、能力门和证据路径；P0 阻断项不得以“仅自用”或手工演示豁免。

## 2. 最小纵向切片范围合同

### 2.1 端到端合同

| 阶段 | 最低可观察结果 | 不变量 / 验收断言 |
|---|---|---|
| 捕获 | 输入文本、链接或文件 / 来源指针，可入 Inbox 或关联用户所选 Project | 用户原文不被 AI 静默改写；Project 未选是合法状态，且不授予权限 |
| 保存 | 先显示保存中，仅权威事务耐久提交后显示“已保存” | FTS、派生、队列失败不影响权威提交且不得伪造成功；旧版不可静默覆盖 |

| Project 恢复 | 用户选择 Project 后，以 FTS + 元数据生成停点、变化、决定、未处理材料与证据缺口 | 每项可回到当前合法 Artifact / Source；来源不可达、版本冲突或授权不足时只显示合法子集和缺口 |
| 候选下一步 | 证据充分时显示一个“规则 / AI 建议·未确认”；否则显示“暂无可靠建议” | 确认前不是事实、承诺、Decision、Action 或当前 Next Step；不得凑数 |
| 反馈 | 支持确认、编辑后确认、拒绝、纠正、忽略；已确认 Action 可完成 / 延期；Feedback 可撤回 | Feedback 追加留痕；纠正使正确依赖 stale / invalid；重大动作必须明确确认 |
| 控制 | 四类命令 `revoke_processing`、`disconnect_source`、`delete_content`、`retract_feedback` 分离 | 命令耐久接受后先实现读取、搜索、建议、队列、导出 / 恢复等活跃路径零命中，再诚实披露物理清理状态 |
| 导出 / 恢复候选 | 合成夹具可生成基础可读包，并验证恢复 / 重导入候选 | 身份、来源、版本、确认状态、排除与部分失败可核对；tombstone / generation 优先且不得复活；不冻结正式格式 |

## 3. 完成、失败、降级与暂停

### 3.1 完成定义（DoD）

切片仅在以下条件**全部**满足时完成：Must 主路径及异常路径均可复跑；H1-H9 对应 P0 测试为零失败；每个结果都有夹具版本、环境、命令 / 步骤、断言、机器可读或截图 / 日志证据、责任人和复跑时间；动态关键状态及键盘 / 焦点 / 可访问性走查完成；导出 / 恢复候选、不复活与删除 / 撤回 E2E 通过；默认关闭能力确实不可达；不存在把合成 / mock 结果写成真实能力、生产 SLA 或 Gate 5 结果的声明。

### 3.2 失败与暂停规则

- **立即阻塞切片验收并暂停相关能力：** 原文丢失或静默覆盖、提前显示已保存、身份混淆、越权读取 / 外发、Project 扩权、重大动作未确认、撤回 / 删除后仍活跃、备份 / 恢复 / 重导入复活、默认关闭能力可被旁路打开、任一 R-0040 P0 失败。
- **停止扩功能并回到产品 / 体验复核：** 在约定自用窗口内无法稳定恢复 Project 上下文、核对来源或完成下一步反馈；不得用增加模型、向量或连接器掩盖。
- **能力门自动失效：** capability / plugin / IPC / scope、处理者、数据级别、平台、导出目标或权限目的发生变化时，受影响能力自动回到关闭，直到触发测试复跑并由所需决策人放行。

### 3.3 可接受降级

可降为单设备、本地、手选 Project、FTS + 元数据、规则 / stub 或无候选、手工导入 / 来源指针、只导出到受控测试目录、L3 降为 L1 展示。不得降级原文保护、身份区分、来源证据、默认拒绝、对象级确认、四命令分离、活跃阻断、不复活、基础导出责任或重大动作确认。

## 6. 后续工程任务共同验收格式

每张工程任务卡至少包含：

1. 任务 ID、单一端到端目标、明确非范围、依赖与允许的数据级别；
2. 继承的冻结资产、H1-H9 与 `T-ARCH` 条目，逐项写 `Applicable / Not Applicable + 理由`；
3. 触及的能力门、默认状态、启用请求、复测触发器和所需 PM / 独立评审；
4. 正常、空、失败、离线 / 受限、撤回 / 删除、不复活场景及 P0/P1 通过阈值；
5. 测试 ID、确定性夹具版本、环境 / 平台、复跑命令或人工步骤、预期断言；
6. 证据 manifest：提交 / 变更标识、原始日志、机器可读结果、必要截图、已知限制、复跑时间与责任人；
7. DoD、失败 / 降级 / 回退与能力关闭方案；明确“代码完成”不等于任务验收或能力启用；
8. 事实、推断、建议、风险、需 PM 确认事项，以及是否改变范围、架构、核心语义或 AI 权限边界。

共同结论仅允许：`Pass`（全部适用 P0 通过）、`Pass with Conditions`（仅非底线 P1 有明确关闭能力 / 降级和 PM 接受）、`Fail`（可修复但未达 DoD）、`Paused`（触发安全 / 价值退出条件）。任何 P0 失败不得判 Pass with Conditions。
