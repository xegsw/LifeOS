# LIFEOS-P1-014｜自用版 MVP 开发准入与路线重排

## 1. 任务边界与结论摘要

- **[事实]** 当前产品定位、目标用户、第一场景、核心领域语义、AI 信任语义、V1 范围、首页 / 今日页 PRD 与三张静态关键原型均已冻结；技术 Spike 计划已 Accepted，但未实测，技术架构未冻结，正式 MVP 开发仍为 `Blocked / Not Allowed`。
- **[建议]** 允许立即进入“自用版开发准备”，并在任务卡与共用测试契约完成后进入技术 Spike；不允许把两者表述为 Stage 3 正式工程准入。
- **[推断]** 外部验证暂停不妨碍单人、可丢弃的技术验证；自用结果只能证明本人场景可运行，不能替代 Gate 5 外部价值结论。

## 2. 当前资产状态判断

冻结资产已足够回答目标用户、问题、最小闭环与信任底线，故不应继续泛化研究。尚缺完整核心流程 / 信息架构、Obsidian 可测需求、Spike 任务卡与实测、动态状态和端到端验收合同。候选栈仅可作为 Spike 基线。

## 3. 外部用户验证暂停后的路线影响

四种状态必须分开：

| 状态 | 当前判断 | 允许事项 |
|---|---|---|
| 自用版开发准备 | **准入** | 收敛最小切片、信息架构、核心流程、任务卡、夹具和验收清单 |
| 技术 Spike | **条件准入** | 按依赖做可丢弃原型、故障注入和证据包，不建设生产系统 |
| 正式 MVP 工程实现 | **阻塞** | SP-01 至 SP-09、架构冻结独立评审及 Stage 2→3 关卡未完成 |
| 商业 / 外部用户验证 | **暂停** | 保留 P1-012 与 P1-013，不联系用户、不形成市场或商业结论 |

可后置：跨用户可理解性、迁移意愿、留存、付费与样本泛化。不可接受：原文丢失 / 覆盖、身份混淆、越权入模、撤回后继续使用、删除 / 导出失真或无证据建议。真实自用日志可记录恢复成败、核对成本和反馈，但不能宣称外部价值已验证。

## 4. 自用版 MVP 最小闭环建议

单机离线捕获文本、链接及文件 / 来源指针；耐久保存原文、版本与来源；用户选择 Project，以 FTS + 元数据找回停点、变化、决定、未处理材料及证据缺口；授权内生成可追溯恢复信息，证据充分时给出至多一个未确认候选下一步；用户核对后确认、编辑、拒绝、纠正、完成或延期并保留 Feedback；同时具备最小权限入口、四类命令状态、基础导出与“不复活”验证。

可降级为单设备、本地优先、手选 Project、FTS-first、假模型、手工导入 / 来源指针。Obsidian 须 SP-02/03 通过。不可降级：可靠落盘、原文保护、来源 / 派生身份、对象级确认、默认拒绝授权、撤回 / 删除活跃阻断、证据与基础导出。

## 5. 开发准入状态判断

**[建议] PM 选择“进入自用版开发准备 + 启动技术 Spike”。** 先以切片准入清单约束 IA 与 Spike，再补核心流程和 Obsidian 需求。正式 Stage 3 仍须 SP-01 至 SP-09、Gate 2/3/4 实测复审及技术架构独立评审 / PM 冻结。P1-012 满足“至少有验证计划”，但 Gate 5 外部价值证据仍为空。

## 6. 不可跳过的技术与信任风险

| 能力 | 准入位置 |
|---|---|
| 原始记录保存 / 备份恢复 | SP-01，任何真实自用数据前的底线 |
| 来源追踪 / AI 派生身份 | SP-03，AI 与恢复包前置 |
| Obsidian 只读 | SP-02，依赖 SP-01；并与 SP-03 共同决定是否进入 V1 |
| 权限边界 | SP-04，任何云端 / 第三方模型真实调用前置 |
| 撤回 / 删除及派生失效 | SP-05，正式开发不可绕过 |
| 搜索 / Project 恢复 / 建议证据 | SP-07，最小价值闭环验收前置；向量可降级，证据不可降级 |
| 导出 / 重导入 / 不复活 | SP-08，正式 MVP 准入前置 |
| 同步一致性与容量 | SP-06、SP-09；自用可先单设备，正式准入仍须验证或由 PM 调整范围 |

## 7. 推荐后续任务顺序

1. **自用版 MVP 最小切片准入清单（决策型）**：固化闭环、非范围、真实数据启用条件、完成定义和失败降级。
2. **核心信息架构与端到端流程（产品 / 体验型）**：仅覆盖捕获、Project 选择、恢复、候选、反馈、权限与导出 / 删除入口；依赖任务 1。
3. **Obsidian 只读接入条件需求（产品 / 技术补丁型）**：形成 SP-02/03 可测输入；依赖任务 1。
4. **共用夹具 + SP-01 / SP-03（技术验证型）**：证明耐久保存和证据链；依赖任务 1，可与任务 2/3 交叠。
5. **SP-02 / SP-04（技术验证型）**：验证 Obsidian 来源与实际授权边界；依赖任务 3/4。
6. **其余 Spike 与 Stage 3 准入复审（技术验证 + 独立评审）**：完成 SP-05/06/07/08/09，形成正式开发 go/no-go；不得提前合并为生产实现。

## 8. PM 推荐决策

建议 PM 确认：项目从 Stage 1 的“继续泛化定义”转入“自用版开发准备与 Stage 2 技术验证准备”；批准任务 1–5 顺序；保持正式 MVP 开发阻塞；P1-013 留在 Backlog。该决定不改变 V1 范围、技术架构、核心模型、AI 权限或商业模式。

## 9. 需要 PM / 用户确认的问题

1. 是否接受“自用版开发准备已准入、技术 Spike 条件准入、正式 MVP 开发仍阻塞”的三层结论。
2. 是否接受外部价值风险后置，但以自用日志作为产品完成证据且不替代 Gate 5。
3. 是否批准上述六项任务顺序；涉及单设备降级、Obsidian 去留、云 / 第三方禁用或 V1 范围变化时，另行 PM 决策。
