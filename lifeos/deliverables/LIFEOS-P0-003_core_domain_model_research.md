# LIFEOS-P0-003｜核心领域模型前置研究

- 文档版本：V0.1 Draft
- 更新日期：2026-08-08
- 项目阶段：Stage 0（项目启动与底层定义）
- 文档状态：专项研究建议，待 PM 主会话评审；不构成数据模型正式冻结
- 任务边界：领域语义与生命周期研究，不是数据库表、API Schema、技术选型、UI 或完整 V1 PRD

## 0. 结论标记与使用边界

- **[项目事实]**：由已接受的项目文件或 `DECISION_LOG.md` 直接支持。
- **[推断]**：由既有事实推导出的领域判断，尚未通过实现或用户行为验证。
- **[建议]**：本报告推荐 PM 采纳的模型方案。
- **[风险]**：若建模不当，可能损害 V1 价值、信任或扩展性的事项。
- **[需 PM 确认]**：涉及核心实体边界、V1 范围或 AI 权限边界，专项会话无权冻结。

本报告中的“对象”指拥有稳定身份、独立生命周期或必须单独追溯的领域概念；不代表数据库表。“关系”也可拥有来源、确认状态和有效期，但本报告不规定其存储方式。

## 1. 研究问题

本研究回答：

1. 支撑 LifeOS V1 闭环的最小但完整领域对象是什么？
2. 哪些语义应是独立对象，哪些应是属性、状态、角色或关系？
3. 如何让用户原文、外部材料、用户确认事实、AI 派生、推断和建议互不混淆？
4. 如何从来源恢复项目上下文，并从原文形成待确认的下一步和结果反馈？
5. 如何表达来源权限、本地/云端/模型处理边界、最低审计和可重建性？
6. 哪些模型问题必须在 V1 PRD、AI 权限模型或技术 Spike 前由 PM 确认？

## 2. 执行摘要

1. **[建议｜需 PM 确认] 推荐 11 个业务核心/支撑对象：`Project`、`Artifact`、`Source`、`Assertion`、`Decision`、`Action`、`Event`、`Derivation`、`Feedback`、`Authorization`、`AuditEntry`；另以 `Link` 表达有类型、有来源的对象关系。** 这是领域边界建议，不是 11 张表。
2. **[建议] `Project` 是 V1 第一场景的核心上下文边界，但不是系统最高层级或企业项目容器。** `Area` 是持续责任范围、`Goal` 是期望结果、`Topic` 是分类视角；三者在 V1 可先作为可引用概念或关系，不与 `Project` 一起扩张成完整管理体系。`Task` 统一为 `Action`。
3. **[建议] `Source` 与 `Artifact` 必须分开。** `Source` 回答“从哪里、以什么权限取得”；`Artifact` 回答“系统保存或指向的具体内容是什么、哪个版本”。同一来源可产生多个内容对象，同一内容也可保留多个来源或导入证据。
4. **[建议] 用户原文与外部原文统一进入 `Artifact` 的版本体系，但通过作者、来源类别、采集方式和内容身份区分。** 用户原文不可变更覆盖；纠正产生新版本或新陈述。AI 摘要、抽取文本和改写是 `Derivation` 的输出，永不替换源版本。
5. **[建议] `Decision` 应为独立对象。** 它承接“为什么这样做”、证据、确认、修订和替代关系，是项目恢复区别于普通笔记/任务列表的关键。`Action`、`Commitment`、`Next Step` 推荐先统一为一个对象：`Action` 是实体，`Commitment` 是带对象/时间约束的行动类型，`Next Step` 是相对某项目与时点的角色或排序结果，而不是永久类型。
6. **[建议] `Derivation` 记录输入版本、处理目的、工作流/模型版本、输出、生成时间、权限上下文和有效性。** 摘要、分类、关联、推断、建议、向量和索引均为派生物；用户确认不会抹去其 AI 来源，输入变化、权限撤回或算法变化可使其失效并重建。
7. **[建议] `Feedback` 作为不可静默吞掉的用户响应记录独立存在。** 确认、拒绝、纠正、完成、延期和评价既可引发目标对象状态变化，又保留“用户对什么、何时、作了什么响应”的历史；状态不应替代反馈历史。
8. **[建议] V1 的恢复链路应是“项目—近期事件—原始/外部材料—已确认决定—开放行动—候选下一步—来源与反馈”，而非自动生成一篇不可核对的项目摘要。** 首页/今日页消费该领域链路，不成为新的权威数据源。

## 4. 已验证事实

1. **[项目事实]** LifeOS 是由用户掌控、可追溯、可迁移的个人终身外脑，不是企业后台、IT 运维平台或单一笔记/任务/聊天工具。
2. **[项目事实]** V1 核心闭环为“捕获—保存—整理—找回/今日—确认行动—反馈”。
3. **[项目事实]** V1 第一场景为“开工/切换项目时的 5 分钟上下文恢复与下一步确认”，价值排序为“找回上下文 > 下一步/减少遗漏 > 今日重点”。
4. **[项目事实]** 用户原文、用户确认事实、AI 整理/生成、AI 推断、AI 建议和外部来源必须区分。
5. **[项目事实]** 原文不可被 AI 静默改写；派生产物应可重建；重要结论与操作应可追溯。
6. **[项目事实]** V1 AI 主体限制在 L0-L2，L3 仅允许小范围、明确授权、可逆的内部动作。
7. **[项目事实]** V1 外部来源最低接入深度为文本、链接、文件、来源指针；Obsidian Vault 可只读接入，AI 派生不写回原文。
8. **[项目事实]** 具体数据库、同步架构、图/关系/向量技术尚未冻结。

## 5. 领域模型设计原则

### 5.1 按身份与生命周期决定是否独立成对象

一个概念满足以下任一条件时，倾向独立成对象：

- 用户需要稳定引用它，例如“这项决定”“这个行动”；
- 它有自己的状态变化，例如决定被修订、行动被延期；
- 它必须单独记录来源、权限、确认或审计；
- 多个对象会引用它，或它需要跨时间保留；
- 删除、失效、导出、重建的规则与承载它的内容不同。

仅用于筛选、显示或临时判断的概念，优先作为属性、状态、角色或关系，避免 V1 实体膨胀。

### 5.2 原始层、语义层、派生层、控制层逻辑分离

- **原始层**：`Artifact + Source`，保存用户输入、导入材料、外部指针与版本。
- **语义层**：`Project + Assertion + Decision + Action + Event + Link`，表达用户要理解和推进的现实上下文。
- **派生与学习层**：`Derivation + Feedback`，表达 AI 做了什么以及用户如何回应。
- **控制层**：`Authorization + AuditEntry`，表达允许什么处理以及关键操作实际发生了什么。

逻辑分层不要求物理分库，但任何实现都不得让派生层覆盖唯一原件。

### 5.3 关系必须可解释，不追求任意图谱

`Link` 只允许对 V1 有明确价值的关系类型，例如：

- `belongs_to_project`
- `supports` / `contradicts`
- `motivates_action`
- `implements_decision`
- `resulted_in`
- `supersedes`
- `derived_from`
- `mentions` / `related_to`

重要关系需带建立者（用户/规则/AI）、依据、确认状态和有效期。V1 不需要“万物皆节点”或开放式本体编辑器。

### 5.4 时间至少区分四种语义

- `occurred_at`：现实世界或项目变化何时发生；
- `authored_at` / `source_modified_at`：内容何时由原作者形成或修改；
- `captured_at` / `observed_at`：LifeOS 何时看到或导入；
- `recorded_at`：LifeOS 何时写入某条领域记录或审计。

不得用单一“创建时间”混合这些语义，否则恢复时间线会误导用户。

### 5.5 当前状态与历史证据分开

对象可持有当前状态以便使用，但状态变化必须由反馈、事件或审计记录解释。不得只保留“已完成”“已确认”等最终值而丢失谁、何时、依据什么作出变化。

## 6. 核心对象候选清单与取舍

| 概念 | 推荐表达 | V1 地位 | 取舍理由 |
|---|---|---|---|
| Project | 独立对象 | 核心 | 第一场景的上下文恢复边界；有状态、范围和关系 |
| Artifact | 独立对象 | 核心 | 承载可查看、可版本化、可导出的内容/文件/摘录 |
| Source | 独立对象 | 核心 | 承载来源身份、定位、获取方式与接入/许可边界 |
| Assertion | 独立对象 | 核心语义 | 表达用户确认事实与 AI/外部主张，避免把“事实”塞进标签或摘要 |
| Decision | 独立对象 | 核心 | “为何这样做”有独立生命周期，需连接证据、行动和替代关系 |
| Action | 独立对象 | 核心 | 承载下一步、承诺、执行状态和结果 |
| Event | 独立对象 | 核心 | 表达项目实际变化与多时间语义，支撑恢复时间线 |
| Derivation | 独立对象 | 核心 | 记录 AI/算法处理的输入、输出、版本、权限和可重建性 |
| Feedback | 独立对象 | 核心 | 用户确认、拒绝、纠正与结果信号需保留历史和目标 |
| Authorization | 独立对象 | 支撑核心 | 权限有授予、范围、目的、期限和撤回生命周期 |
| AuditEntry | 独立记录 | 支撑核心 | 最低审计不能仅靠业务对象最终状态推测 |
| Link | 有身份的关系 | 核心关系 | 连接对象并携带关系来源、状态、时间；不代表选用图数据库 |
| Area | 可引用概念/关系 | V1 可选 | 持续责任范围，不应阻塞项目恢复；后续可升格 |
| Goal | 属性、Assertion 或关系 | V1 可选 | V1 先表达项目期望结果，不建立完整目标管理体系 |
| Topic | 标签/派生分类/关系 | 非核心 | 无需独立生命周期；AI 分类可作为派生关系 |
| Task | `Action` 的界面称谓 | 不独立 | 避免 Action/Task 双轨 |
| Commitment | `Action` 类型与约束 | 不独立（V1） | 复用行动生命周期；保留承诺对象、来源与时间约束 |
| Next Step | `Action` 的角色/选择结果 | 不独立 | “下一步”随项目、时间和用户选择变化，不是永久类型 |
| Note / Document / File / Link / Chat Excerpt | `Artifact` 类型或表现 | 不独立 | 统一内容身份，同时保留各类型的必要元数据 |
| Summary / Tag / Embedding / Suggestion | `Derivation` 输出种类 | 不独立为根对象 | 共享可重建与失效机制；业务化输出仍可产生候选 Action/Decision/Link |
| Person / Actor | 身份引用 | 支撑概念 | V1 是个人系统，先记录作者、生成者、确认者、外部对象引用，不建 CRM |

## 7. 推荐核心对象模型

### 7.1 `Project`

**定义**：用户为了某个有边界的结果，在一段时间内持续投入注意力和行动的个人上下文单元。

**最低语义**：名称、目的/期望结果、状态、开始/结束或休眠时间、用户给出的上下文说明、最近关注时间、与 Artifact/Decision/Action/Event 的关系。

**边界**：

- 它是 V1 的核心恢复边界，不是系统根节点；一条材料可以属于零个、一个或多个项目。
- 它不等于团队空间、代码仓库、工单项目或客户账户；这些只可作为来源或外部引用。
- 生命周期建议为：候选/草稿、活跃、暂停、完成、归档、取消；恢复视图不应把归档等同删除。

**与相邻概念关系**：

- `Area` 持续存在且无明确完成点，例如“健康”“职业”；Project 可服务某 Area。
- `Goal` 是期望状态；Project 可推进一个或多个 Goal，也可把项目目的先作为自身属性。
- `Topic` 是观察/分类维度，可跨 Project。
- `Action` 是可执行推进单元；Project 不是任务容器的同义词。

### 7.2 `Source`

**定义**：内容或信号的来源位置、系统、容器或采集通道，以及访问它的边界。

**最低语义**：来源类型、稳定来源标识、可显示定位、来源所有者/发布方（可得时）、获取方式、首次/最近获取时间、可访问状态、权限/许可引用。

**示例**：LifeOS 快速输入通道、某个 Obsidian Vault、Vault 内文件路径、网页 URL、上传会话、AI 对话会话/消息位置。

**为何不与 Artifact 合并**：

- 一个 Vault 是 Source，但包含很多 Artifact；
- 一个网页 URL 可先只有指针，后续形成多个抓取快照；
- 一个 Artifact 可能由多个来源佐证或经历迁移；
- 来源失联不应删除已经合法保存的 Artifact，保存范围仍受许可约束。

### 7.3 `Artifact`

**定义**：LifeOS 保存、引用或可呈现的具体内容单元，包括文本、文件、链接书签、外部内容快照和摘录。

**最低语义**：内容种类、内容身份、作者/创建主体、当前版本指针、内容或外部指针、来源引用、内容时间、捕获时间、完整性状态、删除状态。

**内容身份建议**：

- `user_authored_original`：用户直接在 LifeOS 写下的原文；
- `external_original`：由外部作者/系统形成并被导入或指向的原始材料；
- `user_edited_version`：用户主动修改产生的新版本；
- `derived_content`：AI/算法生成的摘要、转录、抽取、改写等；必须链接 Derivation；
- `quoted_excerpt`：从另一内容中明确选取的引用，不冒充用户原文。

**版本规则**：每个版本内容稳定；用户修改产生新版本并以 `supersedes` 连接旧版本。AI 只能产生派生版本或编辑提案，不能移动“当前原文”指针，除非用户明确接受且该接受动作被记录。

### 7.4 `Assertion`

**定义**：可独立判断真伪、有效期或确认状态的陈述，用于表达“系统当前认为/用户已确认什么”。

**最低语义**：陈述内容、提出主体、认识身份、证据链接、确认状态、有效期、冲突/替代关系。

**认识身份**：`user_asserted`、`user_confirmed_fact`、`external_claim`、`ai_inference`。用户确认 AI 推断后，原 `ai_inference` 历史不改变；新增确认 Feedback，使 Assertion 的当前确认状态变为用户确认。

**边界**：不是对所有句子强制原子化。V1 只在项目恢复、重点判断或行动依据需要时创建 Assertion，避免建设通用知识本体。

### 7.5 `Decision`

**定义**：用户在候选方案之间作出的、会影响项目理解或后续行动的选择记录。

**最低语义**：决定内容、问题/选项（可选）、提出者、确认者、确认时间、理由、证据、适用 Project、状态、生效/失效时间、修订/替代关系。

**独立理由**：摘要只回答“材料说了什么”，Decision 回答“用户选择了什么以及为什么”；Action 可完成，但 Decision 仍需长期引用；决定还可能被修订或替代。

**AI 边界**：AI 可抽取“候选决定”或提出方案，但不得把候选标记为已确认。用户原文中明确表达“我决定……”时，可按明确规则形成用户提出/确认的 Decision，同时保留原文证据和解析过程。

### 7.6 `Action`

**定义**：用户可确认、执行并产生结果的工作或现实行动单元。

**最低语义**：动作描述、所属/相关 Project、提出主体、意图身份、状态、时间约束、承诺信息、依据、阻塞/依赖、结果、替代关系。

**意图身份**：

- `user_created`：用户直接创建；
- `user_committed`：用户明确对自己或外部对象作出承诺；
- `ai_proposed`：AI 候选，不能视为用户计划；
- `external_request`：外部来源表达的请求，尚不等于用户承诺。

**Next Step**：是某 Project 在某时点被用户确认优先推进的 Action 角色。AI 可提出候选排序；用户确认后记录 Feedback 和选择上下文。一个项目可有多个可执行 Action，但 V1 恢复场景只需呈现少量候选。

### 7.7 `Event`

**定义**：对用户或项目有意义的“已经发生的变化或事实性时点”，用于恢复时间线和解释上下文变化。

**最低语义**：事件类型、描述、发生时间/区间、观察/捕获时间、来源、相关 Project/Artifact/Decision/Action、确认或不确定状态。

**边界**：

- “收到反馈”“发布版本”“会议发生”“发现阻塞”可为领域 Event；
- “数据库写入成功”“某字段被更新”属于 AuditEntry，不应污染用户时间线；
- 一条外部日历记录只是 Source/Artifact，只有被导入为用户相关发生事项时才形成 Event；
- Event 的 `occurred_at` 可未知或为区间，不能用导入时间伪装发生时间。

### 7.8 `Derivation`

**定义**：由 AI、规则或算法基于明确输入产生输出的处理记录与来源包络。

**最低语义**：派生类型、输入对象及精确版本、处理目的、工作流/模型/算法版本、执行时间、处理位置、权限上下文、输出引用、状态、失效原因、可重建标记。

**输出类型**：

- 展示型：摘要、标题、转录、结构化抽取；
- 组织型：标签、候选 Project 归属、候选 Link；
- 推理型：Assertion（AI inference）、风险或冲突；
- 建议型：候选 Action、候选 Decision、今日重点排序；
- 基础设施型：分块、向量、索引、重排特征。

业务输出可拥有自己的对象身份，但必须反向引用 Derivation。例如 AI 下一步是状态为 `candidate`、意图为 `ai_proposed` 的 Action，同时由 Derivation 说明它从何而来。

### 7.9 `Feedback`

**定义**：用户对内容、关系、派生物、行动、决定或建议作出的显式响应记录。

**最低语义**：目标对象及版本、反馈类型、用户、时间、修正内容/理由（可选）、由此触发的状态变化、是否撤销前一反馈。

**反馈类型**：确认、拒绝、纠正、接受建议、忽略、完成、延期、取消、评价、标记无关、调整项目归属。

**为何独立**：只写最终状态会丢失 AI 是否判断错误、用户纠正了什么、何时延期以及哪些反馈可用于后续改进。Feedback 是用户控制和评估证据，不应被训练/个性化流程无条件泛化。

### 7.10 `Authorization`

**定义**：用户授予某主体为特定目的、在特定范围内执行特定处理的可撤回许可。

**最低语义**：授权主体、数据范围（Project/Source/Artifact 类别）、允许动作（读、本地派生、云处理、第三方模型处理、内部写入等）、目的、处理位置、有效期、授予/撤回时间、授权来源。

**边界**：V1 是个人产品，不建组织角色矩阵。`Authorization` 解决的是“什么数据能被什么处理使用”，不是企业成员管理。

### 7.11 `AuditEntry`

**定义**：重要读取、生成、状态变更、授权、删除、导出、同步或执行的不可静默覆盖记录。

**最低语义**：操作者、动作、对象/版本、时间、使用的 Authorization、结果、错误/撤销关联、客户端或处理位置（必要时）。

**边界**：审计服务用户理解、纠错和事故调查，不演变成企业监控台。V1 可按风险分级记录，普通 UI 浏览不等于每次都生成高成本审计详情。

## 8. 对象关系与不变量

### 8.1 关键关系

| 起点 | 关系 | 终点 | 最低要求 |
|---|---|---|---|
| Artifact | originated_from | Source | 来源定位、获取时间、权限边界 |
| Artifact version | supersedes | Artifact version | 保留旧版本，不覆盖 |
| Project | includes_context | Artifact / Event / Decision / Action / Assertion | 关系建立者与确认状态 |
| Assertion / Decision | supported_by / contradicted_by | Artifact / Event / Assertion | 指向精确版本或稳定引用 |
| Action | motivated_by / implements | Artifact / Assertion / Decision | 解释为什么存在 |
| Event | affected | Project / Action / Decision | 解释近期变化 |
| Derivation | consumed | Artifact version / Event / Decision / Action / Feedback | 精确输入与权限 |
| Derivation | produced | Artifact / Assertion / Action / Link 等 | 输出身份和状态 |
| Feedback | targets | Derivation 输出或业务对象版本 | 不丢失用户响应对象 |
| Authorization | governs | Source / Project / Artifact / processing purpose | 范围与有效期 |
| AuditEntry | records | 操作与目标对象 | 操作者、时间、结果 |

### 8.2 必须成立的不变量

1. 用户原文版本一经保存，不得被 AI 原地覆盖。
2. 任何 `derived_content`、`ai_inference`、`ai_proposed` 输出必须能追到一个 Derivation。
3. 任何 Derivation 必须能追到输入版本、处理目的、生成时间和当时有效的权限上下文。
4. 用户确认 AI 输出不会删除或改写其 AI 来源身份。
5. AI 候选 Action 未经用户确认不得成为 `user_committed` 或已确认 Next Step。
6. Decision 的“confirmed”必须有明确用户动作或可验证的用户明确表达，不能仅由模型置信度产生。
7. Source 失联、输入修改、权限撤回或删除会使相关派生物进入待检查/失效状态，不能继续无提示使用。
8. 删除原始数据后，不得用向量、摘要或缓存继续绕过删除与权限边界；法定/安全审计保留例外需另行明确。
9. Project 关系可以是候选关系；AI 猜测归属不得伪装成用户分类。
10. 当前状态可缓存，但权威状态变化必须能由 Feedback/Event/AuditEntry 解释。

## 9. 内容身份与来源追踪模型

### 9.1 统一表达不同输入

| 输入形态 | Source 表达 | Artifact 表达 | 内容身份与注意事项 |
|---|---|---|---|
| LifeOS 快速输入 | 本地输入通道/设备会话 | 文本 Artifact v1 | `user_authored_original`；记录用户与捕获时间 |
| Obsidian 笔记 | Vault + 相对路径/块定位 | Markdown 文件版本或块引用 | `external_original`，作者通常是用户但来源仍是外部文件；只读 |
| 网页链接 | URL/站点 | 书签 Artifact；若抓取则另有快照 Artifact | 仅链接不等于已保存正文；记录抓取时间与引用位置 |
| 上传文件 | 上传通道 + 原始文件身份 | 原文件 Artifact | 提取文本、OCR、摘要均是 Derivation 输出 |
| AI 对话摘录 | 对话服务/会话/消息指针 | 用户选定摘录或合法快照 Artifact | 区分用户消息、模型消息和摘录动作；不能将模型文本标为用户原文 |
| 手工粘贴外部文本 | 捕获通道 + 用户声明的出处 | 引用/摘录 Artifact | 作者未知时明确未知；不能因由用户粘贴而改成用户原创 |

### 9.2 来源追踪最低问题集

任一关键内容或建议应能回答：

1. 这是什么内容身份？
2. 谁写的、谁导入的或谁生成的？
3. 原始位置在哪里，当前是否仍可访问？
4. 哪个内容版本被使用？
5. 何时形成、何时导入、何时生成？
6. AI 使用了哪些证据，哪些只是候选关联？
7. 用户是否确认、拒绝或纠正过？
8. 当时允许在本地、云端或第三方模型中进行什么处理？

## 10. Obsidian Vault 只读接入模型

### 10.1 推荐映射

- **Vault**：一个 Source 容器，具有本地位置、稳定 Vault 身份、接入状态与 Authorization。
- **Markdown 文件**：外部原始 Artifact；相对路径是来源定位，不应是唯一永久身份。
- **文件版本**：以内容和来源元数据识别的 Artifact 版本，保存 `source_modified_at` 与 `captured_at`。
- **YAML frontmatter / 标签**：原始 Artifact 的结构化片段；AI 解释或归一化标签属于 Derivation。
- **Markdown 链接 / `[[双链]]`**：外部显式 Link，保留其原始文本和解析状态；未解析目标不应丢弃。
- **段落/块**：可定位引用单元；V1 可采用稳定指针 + 摘录，不要求把每个块升格为根对象。
- **附件路径**：关联 Source/Artifact；附件内容提取仍是派生物。

### 10.2 变更与冲突规则

1. LifeOS 只读观察 Vault，不写回摘要、标签、行动、反向链接或确认状态。
2. Vault 文件被外部修改时，形成新的外部 Artifact 版本；旧版本保留到满足用户保留/删除策略。
3. 文件重命名/移动应尽力识别为同一来源对象的定位变化；识别不确定时保留候选关系，不能强行合并。
4. 文件删除或 Vault 断开时，记录来源不可达/删除状态；是否保留已缓存原文由用户设置、来源许可和后续 PRD 决定。
5. LifeOS 的摘要、项目归属、Decision/Action 候选全部存在派生/语义层，不修改 Markdown 原文。
6. 导出 LifeOS 数据时，应保留回到 Vault 文件/块的可理解指针，并明确哪些内容不是 Vault 原文。

## 11. 关键生命周期

### 11.1 内容生命周期

建议语义链路：

`创建或发现 → 本地可靠保存/登记指针 → 导入并记录来源 → 整理（派生，不改原文） → 用户确认或纠正语义 → 来源/内容变化后失效检查 → 软删除/来源删除处理 → 导出`

关键规则：

- “确认”通常确认的是 Assertion、Decision、Action 或 Link，不把整个 Artifact 自动变成事实。
- 用户纠正原文产生新版本；纠正 AI 解释产生 Feedback 和新的派生/语义版本。
- `stale` 表示内容或其解释可能过时，不等于删除；应说明因何失效。
- 删除应传播到不可继续使用的派生物、索引和缓存；导出应包含原文、来源、版本、重要关系和内容身份。

### 11.2 AI 派生生命周期

`requested/scheduled → permission_checked → generated → available_as_unconfirmed → confirmed / rejected / corrected / ignored → stale → rebuilt / retired → deleted`

失效触发至少包括：输入版本变化、来源删除、权限撤回、工作流/模型升级需重算、用户纠正证据、超过时效、输出与新事实冲突。

重建规则：

- 可重建意味着保存“输入引用 + 配置/版本 + 输出类别 + 权限条件”，不是保证旧模型永远可调用或逐字复现；
- 若旧模型不可用，可用新实现产生新 Derivation，旧输出标记历史/已替代，不伪装成相同结果；
- 重建只使用当前仍可访问和获准处理的数据。

### 11.3 Action 生命周期

主状态建议：

`candidate → pending_confirmation → confirmed → in_progress → completed`

允许分支：

- `candidate/pending_confirmation → rejected`
- `confirmed/in_progress → deferred → confirmed/in_progress`
- `confirmed/in_progress/deferred → cancelled`
- 任一未终结状态 `→ superseded`，并连接替代 Action

语义说明：

- AI 生成默认进入 `candidate`，不能直接进入 `confirmed`；
- 用户直接创建可按交互意图进入 `confirmed`，但仍记录来源；
- `deferred` 必须保留延期时间/条件；
- `completed` 是用户反馈或明确授权的内部结果，不等于目标达成；结果证据可链接 Artifact/Event；
- Commitment 是 Action 上的意图类型和承诺约束，外部请求未被接受前不得标记承诺。

### 11.4 Decision 生命周期

`proposed → pending_confirmation → confirmed → referenced/active → revised / superseded / invalidated`

说明：

- `referenced` 是使用关系或活动记录，不宜成为唯一互斥状态；一个 confirmed Decision 可被多次引用；
- 修订产生新版本或新 Decision，并保留旧决定与替代关系；
- `invalidated` 表示前提不再成立或决定撤销，不能删除其历史影响；
- AI 抽取出的“似乎已决定”仍应是候选，除非原文包含可验证的用户明确决定表达。

### 11.5 Feedback 与权限生命周期

- Feedback：`recorded → applied → optionally_retracted/superseded`；撤回也新增记录，不覆盖旧反馈。
- Authorization：`proposed → granted → active → expired/revoked`；范围或目的扩大需要新授权，撤回后触发派生物和缓存检查。

## 12. V1 第一场景对象流

### 12.1 项目恢复

1. 用户选择或系统在可解释条件下建议一个 Project。
2. 系统读取该 Project 明确关联与候选关联的近期 Event、Artifact、Decision、Action、Assertion。
3. 恢复顺序优先是：上次停点/最近变化 → 已确认 Decision → 未闭环 Action/Commitment → 开放问题与冲突 → 相关原文证据。
4. AI 可生成恢复摘要，但摘要是 Derivation 输出，必须引用上述对象的精确版本，并显示未确认/可能过时状态。
5. 来源不可达、证据冲突、关系仅为 AI 候选时，必须在恢复结果中保留差异，不能“总结掉”。

**最低恢复包**建议包含：

- Project 的目的和当前状态；
- 最近若干个有意义的 Event；
- 当前有效且已确认的 Decision 及理由；
- 未完成/延期/阻塞的 Action 与 Commitment；
- 新增但尚未整理或归属未确认的 Artifact；
- 关键 Assertion 的确认/冲突状态；
- 每条重点的来源入口与时间。

### 12.2 下一步确认

1. Derivation 在当前 Authorization 范围内读取恢复包。
2. 它产生 1-3 个 `ai_proposed` Action，链接依据 Artifact/Decision/Assertion、阻塞和不确定性。
3. 用户可确认、修改、拒绝、延期或选择其中一个作为 Next Step；每个响应记录为 Feedback。
4. 确认后 Action 进入 `confirmed`，并记录“作为该 Project 当前 Next Step”的选择关系与时间，而不是修改原始材料。
5. 执行结束时，用户记录完成/延期/取消及结果；结果可以形成 Event 或新 Artifact，并反向连接 Action。
6. 后续恢复使用这些反馈更新当前状态，但继续保留原候选、用户修改和结果链路。

### 12.3 从原文到结果的完整可信链

`Source → 原始 Artifact/版本 → Project 关系 → Derivation → 候选 Assertion/Decision/Action → 用户 Feedback → 已确认 Action/Decision → 结果 Event/Artifact → 后续 Feedback`

这条链路是 LifeOS 区别于“AI 自动整理笔记”和“孤立任务列表”的最小语义壁垒。

## 13. 最小审计与权限语义

### 13.1 V1 最低审计事件

至少记录：

- 原文创建、导入、版本变化、软删除与恢复；
- 来源连接/断开与访问失败；
- AI/算法处理使用的输入范围、目的、位置和结果；
- 候选 Decision/Action/Link 的生成；
- 用户确认、拒绝、纠正、完成、延期和撤销；
- Authorization 的授予、变更、过期与撤回；
- 导出、重要删除和 L3 内部可逆动作；
- 派生物的失效、重建和替代。

### 13.2 权限维度

V1 Authorization 至少能表达：

- **范围**：某 Project、某 Source、某 Artifact/类型，或明确排除项；
- **动作**：读取、索引、本地派生、云端处理、发送第三方模型、创建内部候选、修改内部状态；
- **目的**：搜索、项目恢复、摘要、下一步建议等，不能以宽泛“改善体验”替代；
- **位置**：仅本地、LifeOS 云、第三方模型/服务；
- **时效**：单次、会话、持续至撤回、固定期限；
- **主体**：用户、LifeOS 规则、具体 AI 工作流或外部服务。

### 13.3 权限传播原则

- Derivation 的处理权限不能高于其最受限输入；
- 某来源仅允许本地索引时，不得因与 Project 关联而进入云端恢复摘要；
- 新增用途、处理位置或外部主体视为权限扩大，需重新确认；
- 权限撤回不必篡改历史审计，但必须停止未来处理并检查可识别缓存/派生物；
- 导出权限来自用户数据主权，不等于允许把受版权或保密限制的外部原文任意再分发。

## 14. 如何避免退化成普通笔记、任务或开发者工具

| 退化方向 | 模型护栏 |
|---|---|
| 普通笔记软件 | Artifact 不是终点；必须连接 Project、Decision、Action、Event、来源和反馈 |
| 普通任务管理器 | Action 必须保留提出者、意图身份、依据、Decision 和结果链，AI 候选不等于承诺 |
| AI 聊天/自动摘要 | 所有重要输出有 Derivation、来源版本、确认状态、失效和纠正机制 |
| 企业项目管理 | Project 默认服务单个用户的上下文；不引入组织、KPI、审批流、工单吞吐 |
| 开发者工具 | 仓库、Issue、PR、部署、IDE 只是 Source/Artifact/Event 类型，不成为核心对象层级 |
| 宏大知识图谱 | 只引入服务恢复、证据和行动的关系；Topic/实体抽取默认是可重建派生 |

模型评审可使用一个反向测试：若删除 Source、Decision、Derivation 和 Feedback 后产品仍自称完成 V1，那么它大概率只是“笔记 + 任务”；若删除代码/Issue 专用类型仍不能工作，则它已错误滑向开发者工具。

## 15. 不建议进入 V1 的模型复杂度

1. 通用“万物皆实体”的知识图谱、本体编辑器和任意关系推理。
2. 企业组织、团队角色、审批流、资源容量、Sprint、KPI、工单与运维对象。
3. 把 GitHub Repo、PR、Commit、IDE Session 设为顶层核心对象；它们先作为来源、材料或事件类型。
4. 完整 Goal/Area/OKR/习惯/联系人/CRM 体系；只保留最小可引用语义。
5. 每个 Markdown 块、句子和实体都强制拥有根对象身份。
6. 全量事件溯源、永久保存每次低价值读取、面向企业合规的重型审计平台。
7. 将所有向量、分块、索引暴露为用户业务对象；它们属于可重建派生基础设施。
8. 复杂多用户 ACL、跨组织共享和团队数据隔离。
9. 为所有外部系统建立专属领域模型和双向同步状态机。
10. 在领域模型阶段决定关系库、图数据库、向量库、事件总线或微服务拆分。

## 16. 对后续 AI 权限模型的影响

1. P0-004 应围绕 Authorization 的“主体—范围—动作—目的—位置—时效”定义授权，而非只有一个 AI 总开关。
2. 每类 Derivation 应声明主动性级别、允许输入、输出内容身份、最低证据、失效条件和 Feedback 类型。
3. L1 自动生成可产生摘要、候选关系和候选抽取；L2 可提出候选下一步/重点；两者都不能把 Decision 或 Action 自动标记为用户确认。
4. L3 若允许创建内部草稿，需明确它产生的是候选对象还是状态变更、是否可撤销、如何审计；本报告不扩大既定 L3 边界。
5. 用户纠正默认只影响目标对象和明确范围内的后续规则，不能自动泛化成全局事实或扩大模型权限。
6. P0-004 需定义权限撤回后摘要、向量、缓存、训练/评估样本和历史审计的保留/删除策略。

## 17. 对技术架构与 Spike 的影响

以下是待验证能力，不是技术选型：

1. 验证 Artifact 不可覆盖版本、来源指针和软删除传播能否在离线/同步场景保持一致。
2. 验证 Obsidian 文件移动、修改、删除、Vault 断开时的身份识别与失效策略。
3. 验证从 AI 输出回溯到精确输入版本、Authorization 和模型/工作流版本的成本。
4. 验证输入变化或权限撤回后，摘要、关系、向量和索引的依赖失效与重建队列。
5. 验证搜索结果能混合原文、确认语义与派生物，同时保留内容身份和来源，而非只返回合成答案。
6. 验证 100 万内容单元/约 300 万分块假设下，来源链、版本、关系和审计的最低成本；不得因此预先选图数据库。
7. 验证导出能带走原文、来源、版本、确认状态、业务对象和重要关系，并以可理解格式区分派生内容。
8. 验证本地、云和第三方模型处理边界能在实际调用链中执行，而非只在设置页展示。

## 18. 对首页/今日页 PRD 的影响

以下是信息语义要求，不是 UI 设计：

1. 首页主问题应是“今天从哪里继续”，消费 Project 恢复包，而不是展示系统健康或任务吞吐。
2. 每个候选重点/下一步至少显示：所属 Project、内容身份（AI 建议/用户承诺）、理由、关键证据、时间敏感性、确认状态和纠正入口。
3. “最近变化”应来自 Event 与来源变化，不以文件修改时间简单替代业务发生时间。
4. “已决定”只展示 confirmed Decision；AI 抽取但未确认的内容单列为候选。
5. “未处理”应区分未归属 Artifact、未确认 AI 输出、未闭环 Action 和来源失效，不能合并成焦虑式红色数字。
6. 用户确认 Next Step 后，应能看到其依据并在完成/延期/取消时给出轻量 Feedback。
7. 原文入口必须可达；恢复摘要不能成为覆盖证据的唯一界面。
8. 权限受限或来源不可达导致上下文不完整时，页面应说明缺口，不以流畅文本掩盖。

## 19. 风险与反证

| 风险/反证 | 影响 | 缓解/验证 |
|---|---|---|
| 11 个对象对 V1 实现仍过重 | R-0001 范围膨胀 | 以领域语义完整为目标，技术上允许聚合存储；Spike 测最小实现，不把每个对象等同一张表 |
| Assertion 用户价值不足 | 增加抽取和确认负担 | 仅为影响决定/行动/恢复的关键事实创建；通过原型测试是否需独立展示 |
| Source/Artifact 分离增加复杂度 | 追溯成本上升（R-0008） | 用链接书签、网页快照、Vault 文件移动测试，若合并无法回答来源生命周期则保留分离 |
| AI 候选与业务对象双重身份难实现 | 容易出现状态不一致 | 规定业务对象保存意图/状态，Derivation 保存生成链；状态变化以 Feedback/Audit 解释 |
| 关系过多滑向知识图谱 | V1 失控、检索噪声 | 关系类型白名单；优先 evidence、project、decision、action、result 链 |
| 权限撤回后的派生传播成本高 | 隐私失控或体验不可用 | 技术 Spike 验证依赖索引与异步失效，先定义强一致安全边界 |
| Obsidian 文件身份识别不可靠 | 重复内容、错误合并、来源断链 | 不确定时不强制合并；保留候选与用户纠正 |
| 用户不愿维护 Project 归属 | 恢复包缺失 | 允许零归属和 AI 候选归属；只在价值时刻要求最少确认 |
| 用户认为 Decision/Action 结构化成本高 | 回到普通笔记或放弃使用 | 从原文候选抽取、渐进确认；不要求捕获时先分类 |
| 技术用户需求诱导专属模型 | R-0011 叙事偏移 | 代码对象只作为来源类型，以次级用户样本复核模型可迁移性 |

**[建议｜需 PM 判断是否登记]** 新增 P1 风险：“核心领域语义过度实体化导致 V1 实现和交互负担超出价值。”本专项任务不直接修改 `RISK_LOG.md`。

## 20. 建议

### P0

1. **[需 PM 确认]** 接受第 6 节的核心对象边界作为 V0.1 领域模型输入，并明确它不是数据库表冻结。
2. **[需 PM 确认]** 确认 Project 为 V1 恢复上下文边界、Source 与 Artifact 分离、Decision 与 Assertion 独立、Action 统一 Task/Commitment/Next Step 语义。
3. **[建议]** 在 P0-004 中按 Authorization 与 Derivation/Feedback 链定义 AI 权限、确认、纠正和撤回传播。
4. **[建议]** 在 V1 PRD 冻结前，用两个端到端样例验模：Obsidian 笔记形成候选下一步；外部链接/文件支持一项决定并在输入更新后失效。
5. **[建议]** 技术 Spike 先验证身份、版本、来源、失效、导出和权限传播，不先验证宏大知识图谱。

### P1

6. **[建议]** 用技术/AI 产品经理或独立顾问的同构场景复核对象命名，确保没有代码/Issue 专属假设。
7. **[建议]** 首页/今日页 PRD 以“恢复包 + 候选下一步 + 来源 + Feedback”定义验收信息，不把 AI 摘要本身当完成标准。

## 21. 需要 PM 确认

| ID | 决策问题 | 本报告建议 | 备选方案与 V1 影响 |
|---|---|---|---|
| PM-1 | 是否接受 11 个对象 + Link 的 V0.1 领域边界？ | 接受为语义模型，允许技术实现聚合 | 若进一步压缩，应说明由谁承载 Assertion、Authorization 和 Audit 生命周期；若扩张则提高 V1 负担 |
| PM-2 | Project 是否为 V1 核心上下文边界？ | 是，但不是系统根对象或企业项目容器 | 若只用标签，恢复状态与生命周期较弱；若设为根容器，会损害跨项目/领域内容 |
| PM-3 | Source 与 Artifact 是否分离？ | 分离 | 合并实现更简单，但难表达 Vault/URL 容器、多快照、来源失联和多来源证据 |
| PM-4 | Assertion 是否作为独立核心语义？ | 是，但只抽取影响恢复/行动的关键陈述 | 若作为 Derivation 文本属性，用户确认事实、冲突、有效期与多证据会弱化 |
| PM-5 | Decision 是否独立？ | 是 | 若作为 Artifact 标签或 Action 属性，“为何决定”与修订/替代难以长期引用 |
| PM-6 | Action/Commitment/Next Step 如何划界？ | Action 独立；Commitment 为类型/约束；Next Step 为时点角色/用户选择 | 三实体更精确但加重 V1；全部只做状态会丢失意图身份和承诺对象 |
| PM-7 | Link 是否需要自身来源、确认与有效期？ | 重要关系需要；普通展示关系可简化 | 若所有关系均无身份，AI 错误关联无法纠正和失效；若全部重型化则成本过高 |
| PM-8 | 权限撤回后派生物与历史审计如何处理？ | 停止处理、使相关派生/缓存失效；历史审计最小保留规则交 P0-004/安全任务 | 这是 AI 权限与隐私边界，必须在技术 Spike 前明确 |
| PM-9 | 是否把“过度实体化”登记为 P1 风险？ | 建议登记并由 PRD/Spike 双重控制 | 不登记可能使语义模型被误读为必须一一实现的表和 UI |
