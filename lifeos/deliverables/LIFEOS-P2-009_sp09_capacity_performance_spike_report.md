## 1. 结论摘要

**最终判定：`Pass with Conditions`。**

**[已验证事实]** 本任务在 Apple M5、24 GiB RAM、SQLite 3.51.0/FTS5 的本机环境中，实际装载并运行了 1 万内容/3 万分块、10 万/30 万、100 万/300 万三档确定性合成数据。全量档不是外推：主库约 904.25 MiB，生成与批量导入 41.695 秒，FTS 初建 5.353 秒，integrity check 6.199 秒；整轮峰值 RSS 约 298 MiB、无 swap。查询、安全过滤、删除、备份、恢复、墓碑重放、校验扫描和 FTS 重建均进入真实代码路径。

**[已验证事实]** 100 万档关键词 + Project + 当前 Authorization / 状态过滤 p50/p95/p99 为 6.738/7.104/7.269 ms；Project 恢复包数据组装为 6.522/7.080/7.201 ms；单条增量捕获 p95 0.327 ms、p99 3.544 ms。单 Source 500 条提交即阻断 0.057 秒；1% 即 10,000 条阻断 0.535 秒；活跃泄漏、旧 generation 活跃、恢复后墓碑复活、可还原受控原文残留均为 0。

**[条件失败]** 全量 FTS rebuild 是约 4.055 秒的长写事务；隔离恢复副本上的并发捕获等待 4.099 秒，超过“后台维护不阻塞捕获 1 秒”的候选门槛。10 万档同一探针为 0.385 秒。安全没有失败，但体验与可用性条件未通过，因此不能给无条件 Pass。

**[推断]** 在本次短文本、热缓存、单进程、合成分布下，SQLite + FTS5 + 元数据/权限/状态过滤 + 轻量结果组装足以装载重度个人使用基线，并有很大查询余量。该结果支持它进入 V1 本地与早期搜索地基候选评审，但不冻结 SQLite、FTS 模式、Schema、SLA 或技术架构。

**[建议｜需 PM 确认]** V1 继续采用 FTS-first 候选；向量不作为默认硬依赖。300 万条向量仅原始 float32 已需约 4.29/8.58/17.17 GiB（384/768/1536 维），尚未含 ANN、MVCC、WAL、备份与构建峰值，而 SP-07 又未证明净增益。若未来证明语义召回价值，应先按高价值内容部分覆盖、384 维或其他低维、float16/半精度、获准云端索引或 exact 小集合验证，不默认全量 1536 维 ANN。

## 2. 范围、方法与证据等级

合成模型保留 Project、Source、Artifact/版本工程语义、时间、类型、Authorization、证据状态、active、generation、tombstone，并按比例生成 Link、Derivation、Feedback 与最小 AuditEntry。每 200 条预置删除/旧 generation、撤回、拒绝授权和证据不可用；每 100 个 Source 有 1 个断开。全量含 128 个合成 Project、2,000 个 Source，避免“纯随机、无过滤”的虚假快测。具体分布见 `fixtures.md`。

SQLite 候选采用 WAL、`synchronous=FULL`、外键、60 秒 busy timeout、FTS5 external-content 和关系型元数据索引。批量导入后实建 FTS；查询先连接当前内容、Source 与权限/状态，再返回候选。删除分两阶段：事务内写 tombstone、active block、最小审计；后台抹除全部 inactive 可还原原文、删除派生分块并重建 FTS。恢复从新控制事件之前的数据库感知备份开始，先重放 tombstone，确认泄漏为 0 后才视为可开放读取。

结果等级如下：

- **实测：** 三档 SQLite 装载、FTS、查询分位数、捕获、checkpoint、integrity、单条/Source/1% 阻断、物理清理、删除前备份、恢复复制、墓碑重放、FTS 重建、manifest/hash 扫描、日志隐私和并发维护探针。
- **估算：** 384/768/1536 维、100%/25%/10% 覆盖率、float32/float16 的向量值原始下界。
- **未验证：** PostgreSQL/FTS、pgvector、exact/HNSW/IVFFlat、过滤后 ANN 召回、真实 embedding、冷缓存、跨进程生产并发、真实附件、跨平台、真实 Vault、真实云与灾备 SLA。本机无 Docker、`psql` 或本地 PostgreSQL，且任务禁止创建外部资源。

## 3. 环境与规模结果

本机为 Apple M5 10 核、24 GiB RAM，执行开始时工作盘约 838 GiB 可用，达到任务候选最低环境。最终整轮 77.65 秒，`/usr/bin/time -l` 最大 RSS 312,475,648 bytes，0 swap。每档数据库、备份和恢复副本均保留在 `work/` 供 PM 抽样；它们全部为合成、可重建数据。

| 指标 | 1 万 / 3 万 | 10 万 / 30 万 | 100 万 / 300 万 |
|---|---:|---:|---:|
| 主库 | 9.72 MiB | 90.64 MiB | 904.25 MiB |
| 生成+导入 | 0.086 s | 1.277 s | 41.695 s |
| FTS 初建 | 0.020 s | 0.320 s | 5.353 s |
| integrity check | 0.030 s | 0.371 s | 6.199 s |
| 关键词/权限 p95 | 0.081 ms | 0.740 ms | 7.104 ms |
| 恢复包 p95 | 0.300 ms | 1.408 ms | 7.080 ms |
| FTS 重建 | 0.023 s | 0.315 s | 4.137 s |
| 备份 | 0.009 s | 0.100 s | 1.032 s |

**[推断]** 数据库大小接近线性，100 万短文本本地权威数据与 FTS 在本环境可控。导入时间从 10 万到 100 万增长超过线性，但绝对值仍低；不能由此承诺真实长文、附件和多版本总量。备份约等于主库；主库 + 备份 + 恢复副本约 2.65 GiB，正式方案还需为 WAL、影子重建和失败重试预留至少一个额外数据库大小，不能只按主库容量规划。

## 4. 查询、恢复包与捕获

关键词测试用 257 个 topic 词汇叠加 Project、Source、状态和权限过滤；元数据覆盖 Project+时间、高/低选择性 Authorization；恢复包按类型与时间组装最多 240 个结构化构件。每类有预热，关键词、元数据和授权各 120 个样本，恢复包 80 个样本。查询计划和每档原始分位数在 `evidence/results.json`。

全量关键词 p95 7.104 ms，远低于 Spike 的 500 ms 门槛；恢复包 p95 7.080 ms，远低于 4 秒门槛。权限过滤没有为了速度被取消，且 Source disconnected、Authorization denied、evidence unavailable、inactive/tombstone、旧 generation 均不进入活跃结果。单条捕获 100 次采样 p95 0.327 ms、最大 15.254 ms；但这是无维护竞争下的短文本事务，不是 UI 端到端 SLA。

**[条件]** 全量 FTS rebuild 与捕获共用 SQLite 写者锁时，捕获等待 4.099 秒。因此正式候选必须把全量重建移出前台写路径：可评估维护窗口、从一致快照构建影子数据库/影子索引后短切换、可中断分段维护，或先完成权威短事务落盘再异步索引。该选择影响技术架构，需 PM 后续评审；本任务不冻结实现。

## 5. 删除、撤回、断源与旧代安全

单条删除在全量档约 1 ms 内完成活跃阻断。单 Source 影响 500 条，0.057 秒；1% 数据影响 10,000 条，0.535 秒。三者在同一短事务内写 tombstone/状态/最小 AuditEntry，随后再做物理清理。即使 FTS posting 尚未重建，查询仍通过权威 active、Authorization、Source 与 generation 门控拒绝使用；物理清理完成后受控原文残留 0、活跃 tombstone 泄漏 0，FTS integrity check 通过。

删除前数据库感知备份在全量档用时 1.032 秒、大小约 904 MiB。恢复副本先重放本轮控制集合，用时 0.600 秒；开放查询前验证墓碑关联 active 泄漏为 0，integrity 为 `ok`。这证明候选恢复 gate 能阻止旧快照复活本轮删除；它不证明真实多设备、跨版本包、备份保留期或断电恢复 SLA。

SQLite 当前 `secure_delete` 运行值为 FAST 候选语义；本任务没有把它单独当成物理删除证明。可解释替代路径是：提交即权威阻断；抹除 inactive 原文；删除可重建分块；全量重建 FTS；再执行完整性检查。若正式产品要求介质级不可恢复，还需加密密钥销毁、VACUUM/文件生命周期、APFS/SSD 行为与备份到期专项验证，不能把“查询不命中”写成“介质已不可恢复”。

## 6. 备份、恢复、导出校验与重建

全量 checkpoint 返回成功；integrity check 6.199 秒；FTS 初建 5.353 秒、删除后重建 4.137 秒、FTS integrity check 1.065 秒。manifest/hash 流式扫描 1,000,100 行用时 0.329 秒，约 303 万行/秒，输出聚合 digest，不记录原文。该扫描证明元数据级校验可流式执行，不代表 SP-08 完整人可读内容包、附件和引用闭包已经在百万级实测。

恢复文件复制 0.438 秒可能受 APFS 与热缓存影响，不能作为跨盘恢复承诺；数据库 Backup API 的 1.032 秒更适合作为本机一致快照证据。正式恢复必须继续遵守控制账本先行、来源不自动授权、索引由当前合法原始数据重建。向量、FTS posting、缓存和重排特征仍不进入用户权威导出核心。

## 7. SQLite、PostgreSQL 与向量候选比较

| 候选 | 本次证据 | 结论边界 |
|---|---|---|
| SQLite + FTS5 + 元数据过滤 | 三档全量实测；100 万装载、查询、删除、备份、恢复、重建通过；并发全量重建条件失败 | 可进入 V1 本地/早期搜索地基候选；必须解决维护写锁，不冻结 |
| PostgreSQL + FTS | 未实测；本机无本地服务/容器 | 仍是服务端关系与 FTS 候选，不能由 SQLite 结果替代；需后续具备 4 vCPU/16 GiB/足够 NVMe 的本地或获准环境 |
| pgvector exact/ANN | 未实测；仅存储下界估算 | 未证明过滤后召回、构建内存、索引倍数、更新/删除/VACUUM 成本，不得作为 V1 硬依赖 |
| FTS-first + 部分语义覆盖 | SP-07 无向量净增益；本次成本显著低于全量高维向量 | 当前推荐候选，需 PM 确认；真实中文/同义/跨语言价值仍待以后用授权数据验证 |

300 万向量的原始 float32 下界为：384 维 4.608 GB（约 4.29 GiB）、768 维 9.216 GB（8.58 GiB）、1536 维 18.432 GB（17.17 GiB）；float16 减半。25% 覆盖时分别约 1.07/2.15/4.29 GiB。真实 pgvector `vector` 值还有每行最小额外字节，ANN、表/MVCC、WAL、备份和构建峰值会继续放大。

**[建议｜需 PM 确认]** 向量默认后置。触发重新评估的必要条件是：真实授权标注集上相对 FTS-first 有稳定净增益；过滤后召回达标；撤权/删除可阻断和清理；磁盘峰值不超过候选 200 GB；常态内存不要求超过 16 GiB；备份与重建窗口可接受。优先级为部分高价值覆盖 > 低维 > 半精度 > 获准云端索引 > 专用向量组件；专用组件只在单 PostgreSQL/SQLite 候选经调优仍失败时评估。

## 8. 架构触发阈值、允许降级与禁止优化

以下是进入架构候选评审的**建议阈值**，不是冻结 SLA：

1. 本地关键词/元数据 p95 持续超过 500 ms，或恢复包数据组装超过 4 s，且索引/查询调优无效时，评估最近工作集、分区或获准云端索引。
2. 前台权威捕获因维护阻塞超过 1 s：必须采用影子构建/短切换、维护窗口或独立安全落盘路径；本次已触发。
3. 单次 Source/1% 阻断事务超过 1 s：拆分物理清理，但阶段 A 活跃阻断仍须原子、优先完成；不能分批期间继续消费。
4. 主库 + 备份 + 恢复 + 影子重建的磁盘峰值逼近用户预留空间，先减少可重建派生、向量覆盖与历史索引，不删除用户权威原文或墓碑。
5. 向量候选在 16 GiB 常态内存、200 GB 峰值磁盘、过滤后召回或删除重建任一条件失败时，保持 FTS-first，不引入分布式搜索作为默认补救。

可接受降级：向量关闭/部分覆盖；恢复包分段显示可核对构件；后台状态显示 `pending/delayed/failed` 与 ETA；全量重建进入维护窗口；云端只索引逐用途获准子集；附件和冷数据不进入默认全文/向量索引。

禁止优化：取消权限/状态过滤；查询先返回再异步撤回；让旧 generation/旧索引覆盖 tombstone；用 `synchronous=OFF` 或未耐久队列换时延；把 active blocked 写成物理清理完成；把用户原文静默截断、丢弃或改写；让 Project/Link/相似性扩权。

## 9. 用户可理解的状态合同

本次数字可映射为以下状态，而不是暴露运维控制台：正常捕获显示“已保存，索引更新中”；重建期间仍先保证保存，并显示“搜索索引维护中，部分结果可能延迟”；备份区分“正在创建一致快照”“快照可恢复”“校验失败”；恢复区分“控制记录已加载”“正在重建索引”“可安全打开”；删除区分“已停止使用”“正在清理可控副本”“清理失败将重试”“已完成可控副本清理”。

全量重建阻塞捕获说明正式体验不能只用 spinner 掩盖锁等待。若不能先耐久保存，应明确保留编辑内容并允许重试/复制；不得显示“已保存”。具体 UI、文案、ETA 算法与可访问性不在本任务范围。

## 10. 最终判定、关卡与 Stage 2 影响

**判定依据：`Pass with Conditions`。** 三档装载、容量、查询、权限与状态过滤、删除/撤回/断源/旧代安全、备份、恢复、墓碑重放、校验、FTS 重建和隐私最低断言均有可复跑证据；100 万/300 万实际完成，没有以外推冒充。但全量 FTS rebuild 阻塞捕获 4.099 秒，PostgreSQL/pgvector/ANN 未验证，真实长文、附件、冷缓存和生产并发也未覆盖。

可进入技术架构候选评审的结论：SQLite/FTS5/元数据门控可作为本地 FTS-first 候选；关系型控制账本与可重建派生方向成立；100 万短文本容量在 24 GiB 本机可控；向量默认后置；全量索引维护必须隔离前台权威写入；恢复必须控制账本先行。

不能冻结或外推的结论：数据库/Schema/API/FTS 模式、PostgreSQL/pgvector、分块/向量维度/ANN、生产 SLA、真实支持容量、附件策略、云端权威范围、备份/灾备方案、技术架构和 Stage 3 准入。SP-09 完成只提供 Stage 2 收口输入；技术架构冻结与正式 MVP 开发仍必须独立评审并由 PM/用户确认。
