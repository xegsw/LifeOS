# LifeOS PM Operating Model V0.1

更新时间：2026-08-22

## 项目管理原则

当前项目按“PM 主会话 + 专项任务会话”运行。

PM 主会话负责：

- 项目阶段判断
- 任务拆解
- 任务优先级
- 跨任务依赖
- 结果验收
- 决策记录
- 风险管理
- 范围控制
- 版本冻结

专项任务会话负责：

- 执行单一、明确、有边界的任务
- 按任务卡指定的主责角色、协审角色和评审关卡进行分析
- 产出可验收的文件型交付物
- 在聊天中只汇报摘要、交付物路径、是否需要 PM 决策
- 不自行扩大任务范围

一个专项会话在同一时间只能执行一个活动任务。前一任务已经完成或停止、PM 明确分派新任务且不存在独立性冲突时，同一专项会话可以顺序执行同一任务线的后续任务。会话复用不代表任务合并；每个任务仍必须保留独立任务卡、范围、交付物、evidence、预检和 PM 验收。

## 多 Agent 协作与分派机制

LifeOS 允许使用多个专项 Agent 分担执行压力并进行交叉印证，但项目仍保持“单 PM 中枢、单事实账本、单冻结裁判”。

### 基本规则

- PM 主会话是唯一任务分派者。
- PM 主会话是唯一项目账本维护者。
- 用户只需把 PM 生成的任务提示词复制给对应 Agent。
- 专项 Agent 不能自行转派任务，不能自行启动后续任务。
- 专项 Agent 不能更新 `CURRENT_STATUS.md`、`TASK_REGISTRY.md`、`FREEZE_STATUS.md`、`DECISION_LOG.md`、`RISK_LOG.md`、`OPEN_QUESTIONS.md`。
- 专项 Agent 不能自行冻结资产、关闭风险、宣布阶段切换或恢复工程基线。
- 同一任务只能有一个主责 Agent；另一个 Agent 可以作为后续独立评审或辅助复测者。
- 高风险冻结、MVP 准入、P0 修复复评、删除 / 撤回 / 权限 / 真实数据相关任务，执行 Agent 和独立评审 Agent 应尽量不同。

### PM 启动任务时必须输出

PM 每次启动新任务时，应在聊天中给出：

- 下一任务 ID 与名称
- 任务类型
- 推荐执行 Agent：Codex / WorkBuddy / TBD
- 推荐理由
- 推荐模型
- 推荐推理强度
- 模型选择理由
- 允许降级模型
- 禁止降级条件
- 必须升级条件
- 后备模型
- 是否需要后续独立评审
- 是否允许修改工程文件
- 是否允许修改项目账本（默认 No）
- 是否建议新建会话：Yes / No
- 推荐执行方式：复用现有专项会话 / 新建专项会话
- 推荐会话类型：PM / Codex 工程执行 / WorkBuddy 独立评审 / 产品定义 / 技术 Spike / Other
- 推荐复用的会话：如能识别则写明；不能识别则说明由用户选择对应任务线会话
- 会话判断理由
- 是否存在独立性隔离要求：Yes / No
- 本任务必须重新读取的文件
- 本任务可以复用既有读取结果的文件
- 因文件变化或上下文不确定而必须重新读取的基础文件
- 是否建议任务完成后保留该会话供后续同类任务复用
- 可复制给对应 Agent 的完整提示词

PM 不得只写“推荐 Agent：Codex / WorkBuddy”，却不说明是否需要新建会话。PM 在可复制任务提示词之前，必须用简短中文说明：本任务建议新建还是复用；建议复用或新建的原因；用户应把提示词发到哪类会话；是否需要独立评审会话；专项 Agent 的最小启动包、直接输入材料与定向规则补读清单。用户可只把任务卡路径发给新会话；任务卡是完整执行约束的唯一入口。

### 任务卡投递授权

- PM 创建任务卡时登记为 `Ready / Awaiting Task-card Delivery`，而不是暗示已经执行。
- 用户把任务卡路径发送到新建或 PM 已指定的专项会话，即授权该会话执行任务卡已限定的范围；PM 不得另要求“授权执行”口令。
- PM 创建任务时须在任务卡说明授权方式、指定会话类型、允许目录、禁止事项和任何仍需先行确认的例外。专项会话在首份会话报告记录任务卡路径、会话类型和接收时间，作为授权证据。
- PM 验收应核对上述授权证据与任务卡范围；只有投递发生在错误会话、投递不明确、范围与卡不一致，或任务卡要求的单独确认未取得时，才因授权问题 Blocked。
- 用户仅在 PM 主会话提及任务路径、PM 查看路径或事后提交交付物不构成专项执行授权。
- 真实个人数据、真实 DB、真实用户路径或真实文件、Vault、Tauri/IPC、网络、云／第三方、同步、多设备、L3、外部用户、风险关闭／重开、基线恢复、Schema/API 或关键冻结、Stage 4／阶段切换及任务卡列出的重大扩大，继续要求投递前另行明确确认。投递授权不覆盖这些例外。

### 会话路由与复用规则

LifeOS 的推荐会话结构是为了降低 Token 消耗和上下文切换成本，不要求强制创建固定数量的会话。

| 会话类型 | 默认用途 | 可复用范围 | 必须隔离的情况 |
|---|---|---|---|
| PM 主会话 | 长期项目中枢；方向、阶段、任务、验收、账本、风险、冻结、用户确认 | 长期保留，不按任务新建 | 不适用；PM 不替代专项任务执行 |
| Codex 工程执行会话 | 工程实现、P0 修复、技术 Spike、测试复跑、evidence 整理 | 同一工程线、同一受控目录、P3 快车道 P1 / P2 窄补丁、同一 Spike 条件补测 | 不得独立评审自己刚完成的高风险成果 |
| WorkBuddy 独立评审会话 | 独立评审、反例攻击、风险复核、P0 修复复评、冻结前检查 | 同一评审线的连续只读复核任务，且不评审自己产出的成果 | 必须与被评审成果的执行会话隔离 |
| 产品 / 定义专项会话 | PRD、IA、产品规则、低风险文档整改 | 同一产品定义线连续低风险任务 | 关键冻结、范围变化或需独立评审时隔离 |
| 技术 Spike 会话 | 可运行实验、性能验证、技术报告 | 同一 Spike 的补测、证据整理、复跑 | 架构冻结、风险关闭或高风险复评时隔离 |

#### 默认必须新建会话

出现以下任一情况时，PM 默认应建议新建会话，并说明隔离原因：

- 对当前执行 Agent 刚完成的成果进行独立评审。
- P0 修复后的独立复评。
- V1 范围冻结或调整。
- 核心领域模型冻结或核心实体调整。
- AI 权限与信任模型冻结或权限边界变化。
- 技术架构冻结或重大架构变更。
- 首页 / 今日页 PRD 或关键原型冻结。
- 正式 MVP 开发准入或阶段切换。
- 风险关闭的独立判断。
- 任务需要与之前执行上下文保持独立，避免自证循环。
- 新任务与现有专项会话任务线明显无关。
- 现有会话上下文过长，已经出现任务、范围或文件状态混淆。
- 发生上下文压缩后，无法可靠确认关键规则、授权边界或既有读取状态。
- 当前会话仍有未完成任务。
- PM 判断复用会增加范围污染、权限继承或证据混淆风险。

#### 优先复用会话

以下条件同时满足时，PM 可以建议复用已有专项会话：

- 前一个任务已经完成、停止或等待 PM 验收，不再继续修改。
- 新任务已由 PM 明确创建和分派。
- 新任务与原会话属于同一任务线或同一工程目录。
- 新任务不要求对该会话刚完成的结果进行独立评审。
- 不涉及关键冻结、阶段切换、风险关闭或核心权限边界变化。
- 不存在两个活动任务并行混合的问题。
- 当前会话对项目边界仍然清楚。
- 复用不会导致旧任务授权被错误继承。
- PM 已明确列出新任务允许修改范围和非范围。

典型可复用场景：同一受控工程目录内连续多个 P1 / P2 窄补丁；同一工程线连续测试复跑和 evidence 整理；同一技术 Spike 条件补测；同一产品定义线连续低风险文档整改；PM 验收后明确下发的同类后续任务。

#### 复用会话时的重新读取规则

复用会话不代表所有材料都不再读取。每个新任务开始时必须重新读取最小启动包中的最新 `CURRENT_STATUS.md`、任务卡、当前模板，以及：

- 当前任务指定的直接输入材料
- 与本任务存在直接依赖的最新 PM Review
- 自上次读取后已发生修改的项目规则文件
- PM 明确要求重新核对的文件

新建专项会话也遵循“最小启动包 + 任务卡定向补读”：最小启动包为 `AGENTS.md`、`CURRENT_STATUS.md`、任务卡与相关模板。普通任务只增加直接输入材料；独立评审、P0/P1、删除／撤回／权限、风险关闭、工程基线恢复、真实能力、冻结或阶段切换任务，任务卡必须列出 `PM_OPERATING_MODEL.md`、`ROLE_MATRIX.md`、`STAGE_GATES.md` 的相关章节或全文及理由；外部 Agent 另加 `AGENT_BRIEFING_PACK.md`。若任务卡不足以判断边界，专项 Agent 停止并要求 PM 补充。

以下稳定基础文件，在同一会话中已经完整读取、之后未修改、未发生上下文压缩且 Agent 能可靠确认读取状态时，可以不重复全文读取：

- 根目录 `AGENTS.md`
- `lifeos/AGENT_BRIEFING_PACK.md`
- `lifeos/PM_OPERATING_MODEL.md`
- `lifeos/ROLE_MATRIX.md`
- `lifeos/STAGE_GATES.md`

出现以下情况时必须重新读取相关基础文件：文件在上次读取后被修改；会话发生上下文压缩；Agent 无法可靠确认是否完整读到 EOF；上次工具输出发生截断；当前任务涉及该文件管理的高风险边界；PM 明确要求重新读取；文件版本或修改状态无法确认。不确定是否需要重读时，安全优先，重新读取。

### P3 Engineering Fast Lane / P3 工程快车道

P3 工程快车道用于有限 Stage 3 中的低风险、窄范围工程补丁，目标是在不降低关键安全质量的前提下减少等待、确认和文档成本。

#### 适用范围

仅当同时满足以下条件时，PM 可以启用 P3 工程快车道：

- 仅限有限 Stage 3 工程阶段。
- 仅限合成数据、单进程、受控测试包、本地 evidence 范围。
- 不改变 LifeOS 产品定位、V1 范围、技术架构 V0.1 冻结合同、核心领域模型或 AI 权限边界。
- 不启用真实数据、真实 Vault、真实 Tauri / IPC、云 / 第三方模型、向量、同步、多设备、L3 或外部用户。
- 不涉及真实用户或真实敏感数据。
- 不需要关闭风险、恢复工程基线、冻结资产或进入下一阶段。

#### 快车道允许

- P1 / P2 工程补丁可由 PM 验收后继续推进，无需每次等待用户单独确认。
- PM 可以批量创建 2-5 个窄范围工程补丁任务。
- 工程交付物可使用短报告 + evidence manifest，不写成长篇论文。
- PM Review 可以压缩为快车道 Review，只保留验收结论、测试摘要、风险状态、是否触发用户确认和下一步。
- WorkBuddy 可提前准备反例清单或评审清单，但不得与 Codex 同时修改同一工程目录。

#### 快车道不允许

- P0 修复后跳过独立复评。
- 删除 / 撤回 / 权限 / 导出 / 证据链 / AI 建议可信度核心边界跳过 PM 验收。
- 自动关闭风险。
- 自动恢复工程基线。
- 自动进入下一阶段。
- 自动启用真实能力。
- 自动修改 PM 账本之外的冻结资产。
- 将合成测试通过外推为真实 Tauri / IPC、真实 Vault、真实数据、云 / 第三方模型或生产 SLA 通过。

#### 用户确认降频规则

以下事项仍必须用户确认：

- 产品定位变化。
- V1 范围变化。
- 技术架构冻结或变更。
- 核心领域模型变更。
- AI 权限边界变更。
- 进入下一阶段。
- 恢复工程基线。
- 关闭 P0 / 高风险风险项。
- 启用真实数据、真实 Vault、真实 Tauri / IPC、云 / 第三方模型、同步、多设备、L3 或外部用户。
- P0 修复结论采纳。
- 独立评审 Rework / Blocked 结论采纳。

以下事项 PM 可在快车道内直接推进，但必须留下记录：

- 不改变架构 / 产品 / 权限边界的 P1 / P2 工程补丁。
- 文档勘误。
- evidence manifest 补充。
- 测试命名、日志整理、报告压缩。
- 同一工程任务内的非高风险回归补测。
- 已被用户授权的窄范围条件补丁。

PM 直接推进后，仍必须在 `CURRENT_STATUS.md`、`TASK_REGISTRY.md`、`DECISION_LOG.md` 或 PM Review 中记录：任务 ID、推进原因、测试摘要、风险状态、是否触发用户确认、下一步。

#### Batch Patch / 批量补丁机制

当多个 P1 / P2 工程问题均满足快车道条件时，PM 可以创建一个 Batch Patch 任务，一次处理 2-5 个问题。

Batch Patch 任务必须列出：

- 每个问题 ID。
- 严重级别。
- 修复边界。
- 对应测试。
- 是否触发独立复评。
- 是否触发用户确认。

Batch Patch 不得混入 P0，不得混入真实能力启用，不得把无关 P2 清洁项伪装成安全补丁。

#### P3 快车道 Agent 分派

- P3 快车道工程补丁默认推荐 Codex。
- P3 快车道独立复评 / 反例清单默认推荐 WorkBuddy。
- WorkBuddy 可以提前准备评审清单，但不能并行修改工程文件。
- 如果 WorkBuddy 发现 P0，必须回到 PM 主会话，由 PM 判断任务状态和下一步；WorkBuddy 不得自行要求 Codex 直接修。

#### P3 快车道 PM Review

P3 快车道 PM Review 可压缩为：

- 验收结论。
- 测试复跑摘要。
- 是否存在 P0。
- P1 / P2 是否可留在快车道。
- 风险状态是否变化。
- 是否触发用户确认。
- 是否允许继续下一工程补丁。
- 修改文件。
- evidence 路径。
- Agent 适配度记录。

以下情况必须退出快车道，恢复完整 PM Review：

- 发现 P0。
- 需要关闭风险。
- 需要恢复工程基线。
- 涉及真实数据 / 权限 / 删除 / 导出 / AI 建议可信度核心边界的最终判断。
- 涉及技术架构、领域模型、AI 权限边界变化。
- 需要进入下一阶段。

### 默认 Agent 分派

| 任务类型 | 默认推荐 Agent | 理由 |
|---|---|---|
| 工程实现 / P0 修复 / 回归测试 | Codex | 更适合修改代码、运行测试、整理 evidence |
| P3 快车道 P1 / P2 工程补丁 | Codex | 更适合快速完成窄范围代码、测试和 evidence 更新 |
| 技术 Spike / 性能验证 | Codex | 更适合构造可运行实验和技术报告 |
| 独立评审 / 反例攻击 / 二轮复评 | WorkBuddy | 更适合作为外部视角挑错，降低执行者自证风险 |
| P3 快车道独立复评 / 反例清单 | WorkBuddy | 更适合提前准备攻击清单和证据链复核，但不得并行修改工程目录 |
| PRD / IA / 产品规则初稿 | Codex 或 WorkBuddy | 由 PM 按任务重心判断：偏结构产出可交 Codex，偏质疑审查可交 WorkBuddy |
| 设计 / 文案 / 体验审查 | WorkBuddy 优先 | 更适合从用户理解、信息层级和风险角度复核 |
| 项目流程规则落地 | Codex | 更适合本地文件更新和模板维护 |

### 任务模型路由机制

Agent 路由与模型路由是两层独立判断：PM 先决定任务交给 Codex 还是外部 Agent，再为 Codex 任务选择模型与推理强度。模型路由只优化执行质量、时延和 Token 成本，不改变任务范围、授权边界、独立评审要求或用户确认规则。

#### 生效边界

- 本机制自 D-0215 后创建的下一张新任务卡起生效。
- 不追溯修改任何历史任务卡；已经创建的 `LIFEOS-P3-040` 保持原样。
- 新任务卡缺少任一模型路由字段时，不得标记为 Ready，应由 PM 补齐。
- 任务执行中不得因模型更换继承额外权限、扩大范围或跳过既定关卡。

#### Codex 可用模型白名单

新任务卡的 Codex 推荐模型、允许降级模型和后备模型只能从以下白名单选择：

自 D-0242 起，该白名单排除 `gpt-5.6-sol`，且只适用于之后创建的任务；已创建或正在执行的任务保留其任务卡原配置，不追溯改派、降级或重写历史记录。

- `gpt-5.6-terra`
- `gpt-5.6-luna`
- `gpt-5.5`
- `gpt-5.4`

不得填写模糊别名、未列出的模型、自动选择或第三方模型。`gpt-5.6` 这类未明确到变体的别名不得写入任务卡。

推荐推理强度使用 Codex 当前可选值，并受所选模型支持范围约束：

| 模型 | 可填写的推理强度 |
|---|---|
| `gpt-5.6-terra` | `low` / `medium` / `high` / `xhigh` / `max` / `ultra` |
| `gpt-5.6-luna` | `low` / `medium` / `high` / `xhigh` / `max` |
| `gpt-5.5` | `low` / `medium` / `high` / `xhigh` |
| `gpt-5.4` | `low` / `medium` / `high` / `xhigh` |

`ultra` 是 Codex 执行档位，不等同于 API 的 `reasoning.effort` 字段。PM 必须填写模型实际支持的值，不得用“最高”“自动”等不可核对表述。

#### 默认选择参考

| 任务特征 | 默认模型与推理强度 | 说明 |
|---|---|---|
| P0 修复、高风险工程、复杂安全边界、关键冻结输入、阶段准入、跨文件深度复核 | `gpt-5.6-terra` + `high` / `xhigh`；极难且可清晰拆分验证时才用 `max` / `ultra` | 质量与验证优先，不以节省 Token 为首要目标 |
| 常规工程实现、P1 / P2 窄补丁、技术 Spike、结构化产品 / 治理任务、一般 PM 支撑 | `gpt-5.6-terra` + `medium` / `high` | 作为质量、速度与成本平衡的默认路线 |
| 机械性文档勘误、日志 / manifest 整理、明确模板填充、低风险单点补测 | `gpt-5.6-luna` + `low` / `medium` | 仅限边界清楚、可自动验收、失败可安全重试的任务 |
| 5.6 系列不可用时的复杂任务后备 | `gpt-5.5` + `high` / `xhigh` | 作为明确后备，不得静默替换任务卡推荐模型 |
| 5.6 系列不可用时的有界常规任务后备 | `gpt-5.4` + `medium` / `high` | 不用于任务卡列明的禁止降级场景 |

PM 不得仅按任务标题或优先级机械选型。应同时考虑：错误后果、范围复杂度、跨文件依赖、证据要求、是否可自动验证、是否需要反例攻击、上下文长度以及失败后的返工成本。

#### 新任务卡必填字段

每张生效后的新任务卡必须填写：

- 推荐模型：单一首选模型。
- 推荐推理强度：与首选模型兼容的单一档位。
- 选择理由：说明任务风险、复杂度、验证方式与成本取舍。
- 允许降级模型：按优先顺序列出；没有安全降级方案时写 `None`。
- 禁止降级条件：列出一旦满足就不得使用较低配置的边界。
- 必须升级条件：列出执行中触发升级或退回 PM 的条件。
- 后备模型：首选模型不可用时的单一后备；没有安全后备时写 `None`。

允许降级模型与后备模型含义不同：前者用于低风险、可验证场景的成本优化；后者只处理模型不可用或容量受限。二者都不能覆盖“禁止降级条件”。

#### 禁止降级条件

至少出现以下任一情形时，任务卡不得把 `gpt-5.6-luna` 或 `gpt-5.4` 作为降级模型；PM 还应按具体任务判断是否完全禁止降级：

- P0 修复、P0 修复后的复评或独立评审 Rework / Blocked 处理。
- 风险关闭、工程基线恢复、关键资产冻结、阶段切换或正式开发准入。
- 产品定位、V1 范围、技术架构、核心领域模型或 AI 权限边界变化。
- 删除、撤回、权限、导出、证据链、AI 建议可信度核心边界。
- 启用或评估真实数据、真实 Vault、真实 Tauri / IPC、云 / 第三方模型、同步、多设备、L3 或外部用户。
- 证据相互冲突、测试结果不可稳定复现、存在不可逆技术风险或需要跨多个核心账本裁决。

#### 必须升级或退回 PM 的条件

执行中出现以下任一情形时，专项 Agent 不得自行维持低配路线，应停止扩大工作并按任务卡升级到推荐 / 后备配置，或回到 PM 主会话：

- 新发现 P0、高风险权限旁路、数据丢失 / 不可恢复风险或真实能力触达。
- 实际范围涉及架构、领域模型、AI 权限、冻结、风险关闭、基线恢复或阶段准入，而任务卡未声明。
- 任务直接依赖之间出现矛盾，或测试、报告与 evidence 不能相互印证。
- 当前模型无法可靠保持任务边界、完整理解关键上下文或形成可复核 evidence。
- 同一核心失败在允许降级模型上连续两次仍未解决。
- 任务复杂度已明显超过任务卡中的模型选择理由。

模型升级不得被解释为扩大任务授权。升级后仍无法在原范围完成时，任务应标记 Blocked 或回报 PM 重新拆卡。

#### 外部 Agent 规则

当推荐执行 Agent 为 WorkBuddy 或其他非 Codex 外部 Agent 时：

- `推荐模型`、`推荐推理强度`、`允许降级模型`、`禁止降级条件`、`必须升级条件`、`后备模型`统一填写 `N/A`。
- `选择理由`填写“外部 Agent，Codex 模型路由不适用”，并保留 Agent 路由本身的推荐理由。
- 若 PM 后续改派给 Codex，必须创建或更新当时尚未执行的新任务卡版本并完整填写模型路由；不得直接沿用 `N/A`。

#### 执行与异常记录

- 专项 Agent 应按任务卡指定模型和推理强度执行；无法选择指定配置时，不得静默替换。
- 如需使用允许降级模型或后备模型，必须在会话摘要或交付物中记录实际模型、触发原因和是否影响验收范围。
- 若可用模型不满足任务卡的禁止降级条件，应停止执行并回报 PM，不得以“先做一部分”为由绕过。
- 模型路由记录只证明执行配置，不替代测试、evidence、本地预检、PM 验收或独立评审。

## 外部 Agent 同步机制

为避免每次向 WorkBuddy 或其他外部 Agent 复制长背景，项目使用固定轻量同步包：

`lifeos/AGENT_BRIEFING_PACK.md`

使用规则：

- 外部 Agent 每次读取最小启动包，并额外读取 `AGENT_BRIEFING_PACK.md`。
- 如果外部 Agent 不能访问本地文件，由用户只复制 `AGENT_BRIEFING_PACK.md`、`CURRENT_STATUS.md` 和当前任务卡，不复制完整历史。
- `AGENT_BRIEFING_PACK.md` 只提供项目共识和边界；具体任务仍以任务卡为准。
- 若同步包与主账本冲突，以 `TASK_REGISTRY.md`、`FREEZE_STATUS.md`、`DECISION_LOG.md` 为准，并回报 PM 修正。

## Agent 交付物适配度评估机制

PM 主会话在验收不同 Agent 的交付物时，应顺手判断该 Agent 更适合哪类任务，并按需记录到：

`lifeos/AGENT_ROUTING_SCORECARD.md`

### 评估维度

- 范围纪律：是否严格按任务卡执行，未越权。
- 证据质量：结论是否被文件、测试、日志、截图或清晰推理支撑。
- 反例能力：是否能发现隐藏边界、自证循环和 P0 / P1 风险。
- 工程执行力：是否能稳定修改、复跑、补测和整理 evidence。
- 文档清晰度：结构、术语、风险、待确认问题是否便于 PM 验收。
- 上下文成本：是否遵守降耗规则，避免无差别读取和长篇聊天输出。
- PM 可验收性：PM 是否能快速判断结论、风险、路径和下一步。

### 评估输出

PM Review 中应增加一段轻量判断：

- 本任务实际执行 Agent
- 与任务类型的匹配度：High / Medium / Low / Unknown
- 更适合该 Agent 的后续任务类型
- 不建议分派给该 Agent 的任务类型
- 是否建议调整默认 Agent 分派

该判断只用于后续分派优化，不替代任务验收结论，也不替代独立评审或冻结判断。

## 上下文读取策略

为降低 PM 主会话和专项任务会话的 token 消耗，后续默认采用“先索引、再定向、最后完整核对”的读取策略。

### 默认读取原则

- 日常状态查询优先读取 `lifeos/CURRENT_STATUS.md`。
- 只有在验收、冻结、创建任务、阶段切换、冲突判断时，才读取对应完整文件。
- `DECISION_LOG.md` 默认只读取最近 5-10 条决策；除非要追溯历史决策冲突，不全量读取。
- `TASK_REGISTRY.md` 默认只读取当前阶段和最近任务；除非要做阶段盘点，不全量读取。
- `FREEZE_STATUS.md` 默认只读取核心资产看板和当前阶段判断；除非要做冻结 / 阶段判断，不全量读取。
- `PROJECT_CONTEXT.md` 只有在产品方向、阶段判断、范围冲突、跨任务口径冲突时才读取。
- 不要在一次工具调用中无差别读取多个大文件；应先用 `rg` 定位相关段落，再按需读取。
- PM 回复用户时默认输出结论、修改文件、需要确认事项，不重复长篇背景。
- 每个大型 Markdown 文件单独读取；禁止用一条命令连续 `cat` 多个大型文件。
- 读取前使用 `wc -l` 或等价方式检查规模；大文件按约 300–500 行分页读取直到 EOF。
- 当前会话维护轻量读取账本，记录文件路径、是否完整读到 EOF、是否发生截断、是否需要补读、读取后是否发生修改。
- 读取账本只供当前 Agent 控制上下文，不写入项目账本，也不要求在聊天中展示。
- 输出截断时，只补读缺失行段，不得从头重读。
- 已完整读取且未修改的文件不得无理由重复读取。
- 历史 Review、Decision、Risk、Evidence 和大型交付物，除非任务卡要求全文，否则优先使用 `rg` 定位后定向读取。
- 代码定位优先使用 `rg` / `rg --files`。
- 测试日志在聊天中只报告摘要，完整日志写入 evidence。
- Token 优化不得成为跳过基础必读文件、减少安全审查或降低 evidence 质量的理由。

### 文件读取分层

**A. 日常层**

- `lifeos/CURRENT_STATUS.md`
- 当前任务文件
- 最近 PM Review

适用：状态查询、下一步确认、生成专项任务提示词、轻量项目同步。

**B. 验收层**

- 当前交付物
- 当前任务卡
- `lifeos/templates/PM_REVIEW_TEMPLATE.md`
- 相关冻结状态行
- 最近 5-10 条决策

适用：PM 验收、判断 Accepted / Rework / Blocked、更新任务状态、提出下一步建议。

**C. 冻结 / 阶段层**

- `lifeos/PROJECT_CONTEXT.md`
- `lifeos/FREEZE_STATUS.md`
- `lifeos/DECISION_LOG.md`
- `lifeos/STAGE_GATES.md`
- 相关独立评审
- 相关主交付物

适用：关键资产冻结、技术架构冻结、正式 MVP 开发准入、阶段切换、重大范围冲突。

### 降耗不降质

降耗不是减少审查，而是减少重复读取和重复输出。以下情况仍必须完整核对：

- 产品定位变化
- V1 范围变化
- 技术架构冻结
- 数据模型核心实体调整
- AI 权限边界变化
- 正式 MVP 开发准入
- 关键资产冻结
- 独立评审验收
- 涉及真实数据、删除、权限、导出、外部用户或技术不可逆风险的任务

## 本地模型预检机制

为进一步降低 PM 主会话与专项任务会话的 token 消耗，项目允许使用局域网本地模型进行低风险预检。

默认配置：

- 本地模型地址：`http://192.168.5.17:11434`
- 默认模型：`qwen3:14b`
- 调用脚本：`lifeos/tools/local_precheck.py`
- 输出目录：`lifeos/local_prechecks/`

本地模型定位为“预检员”，不是 PM、不是独立评审人、不是冻结裁判。其输出只作为 `Local Precheck / 本地预检`，不得作为 Accepted、Rework、Blocked、Frozen、MVP 准入或 PM 决策依据的唯一来源。

### 默认调用场景

PM 主会话或专项任务会话在以下场景默认必须先调用本地预检脚本；只有符合“允许跳过场景”时才可跳过：

- 交付物摘要压缩。
- 任务卡覆盖检查。
- 模板完整性检查。
- 风险 / 待确认事项抽取。
- 检查是否误写成冻结、准入或已实现。
- 文案、术语和层级一致性检查。
- 技术日志或 evidence manifest 摘要。

默认命令：

```bash
python3 lifeos/tools/local_precheck.py <交付物或评审文件路径>
```

本地预检完成后，PM Review 或会话回复应引用预检报告路径；若跳过本地预检，必须简短说明跳过原因。

PM 验收时应优先读取本地预检报告，以减少重复摘要与初筛消耗；但仍必须读取当前任务卡、交付物核心结论、相关冻结状态行和最近决策。

### 禁止交给本地模型独立决定

以下事项不得由本地模型独立判断或输出最终结论：

- PM 最终验收结论。
- 独立评审最终结论。
- 技术架构冻结。
- MVP 开发准入。
- AI 权限边界变化。
- 数据模型核心实体调整。
- 删除 / 撤回 / 权限 / 真实数据等高风险判断。
- 任何项目账本更新。

### 失败降级

如果本地模型不可用、超时、输出为空或输出明显越界，应跳过本地预检，按原项目流程继续，不得阻塞任务。

### 允许跳过场景

- 本地模型不可用、超时、输出为空或输出明显越界。
- 当前任务没有明确交付物路径，无法形成可预检输入。
- 用户明确要求本轮不要调用本地模型。
- 当前任务涉及高风险最终判断，且本地预检可能造成误导；此时仍可跳过，但 PM 必须按原流程完整复核。

## 技术 Spike 降耗规则

- 技术 Spike 可以运行脚本和测试，但聊天中不粘贴完整日志。
- 聊天中的测试输出只报告摘要：PASS / FAIL 数量、P0 失败数、关键失败、证据路径。
- 详细日志、测试结果、夹具说明和证据包写入 `lifeos/spikes/{SP-ID}/evidence/`；如沿用既有 Spike 目录，也必须提供 `README.md` 或 `MANIFEST.md` 作为证据入口。
- 每个 Spike 交付物必须引用证据入口路径，不在交付物中内嵌大段原始日志。
- PM 验收技术 Spike 时，优先读取 Spike 报告摘要与 evidence `README.md` / `MANIFEST.md`；只有遇到 P0 失败、结论冲突、证据不足或抽样复核时，才读取完整日志。
- 如测试输出过大，应保存为文件并在交付物中引用路径。

## 角色与关卡机制

LifeOS 使用角色与关卡机制保证长期项目稳定推进。

角色定义见：

`lifeos/ROLE_MATRIX.md`

阶段关卡见：

`lifeos/STAGE_GATES.md`

每个专项任务必须指定：

- 主责角色
- 协审角色
- 必须通过的评审关卡

角色是专业视角，不代表增加真实成员或管理岗位。关卡是质量护栏，不是流程负担。

## 独立评审规则

日常专项任务允许由执行 Agent 按主责角色和协审角色进行多视角自审。

但以下关键冻结事项必须启动独立评审会话，不能只依赖执行任务 Agent 自审：

- V1 范围冻结
- 核心领域模型冻结
- AI 权限与信任模型冻结
- 技术架构冻结
- 首页/今日页 PRD 或关键原型冻结
- 进入正式 MVP 开发

独立评审会话的职责不是重写主交付物，而是专门从指定角色视角挑问题、判断是否通过关卡，并输出评审文件。

独立评审交付物必须保存到：

`lifeos/reviews/`

命名建议：

`{任务ID}_{角色英文简写}_independent_review.md`

示例：

`LIFEOS-P0-004_ai_trust_independent_review.md`

PM 主会话只有在读取主交付物和独立评审后，才能将关键资产标记为冻结或允许进入下一阶段。

- `LIFEOS-P0-001`：Stage 0 第 1 个任务
- `LIFEOS-P1-003`：Stage 1 第 3 个任务

任务类型可在标题中标记：

- `[PM]` 项目管理
- `[Product]` 产品
- `[Research]` 研究
- `[Design]` 设计
- `[Tech]` 技术
- `[Data]` 数据模型
- `[AI]` AI 机制
- `[Biz]` 商业

## 任务类型机制

为避免专项任务越写越大，LifeOS 后续任务默认分为以下四类。任务卡必须明确任务类型，并按对应范围和篇幅控制。

| 任务类型 | 适用场景 | 交付物特点 | 建议篇幅 | 是否允许提出新任务 | 是否允许扩展范围 |
|---|---|---|---:|---|---|
| 研究型任务 | 探索目标用户、问题、竞品、技术可行性、方案选项；用于形成输入，不直接冻结资产 | 事实、推断、方案对比、风险、待确认问题；重点是“看清楚” | 3000-6000 字 | 允许提出后续任务建议 | 不允许自行扩展执行范围；发现新问题写入“后续任务建议” |
| 评审型任务 | 独立评审 PRD、领域模型、AI 模型、架构、原型等关键资产是否可冻结或进入下一阶段 | Pass / Pass with Conditions / Rework / Blocked，列问题、条件、风险；不重写主交付物 | 2000-4000 字 | 允许提出整改任务或补充验证任务 | 不允许重写资产或扩大为新方案设计 |
| 补丁 / 条件整改型任务 | 针对评审提出的具体条件、缺口或勘误做有限补充 | 逐项回应整改项；输出补充规范、矩阵、验收补丁或勘误；与原资产合并阅读 | 1500-3000 字 | 允许提出剩余风险或后续验证任务 | 只允许覆盖指定整改项，不允许推倒重写 |
| 决策型任务 | PM 需要在多个清楚选项间做阶段、范围、冻结、取舍或优先级决策 | 选项、影响、PM 建议、推荐决策、未决风险；重点是帮助决策，不重新研究 | 1000-2000 字 | 允许提出执行任务 | 不允许引入未请求的大范围研究 |

篇幅边界用于控制范围，不限制质量。若内容超出建议篇幅，应优先放入“后续任务建议”“待验证问题”或“附录候选”，不要在当前任务中无限展开。

### 两层验收治理与 Acceptance Basis Freeze（D-0401 起）

完整规则以 `lifeos/ACCEPTANCE_GOVERNANCE.md` 为准。

#### L1：长期产品质量原则

L1 长期有效，覆盖数据主权、内容身份、生命周期完整、失败关闭、用户控制、审计可信、Evidence 诚实、历史保全、授权不漂移与可复核性。任务卡遗漏不取消 L1；PM 使用 L1 判定失败时必须记录具体原则、可复现事实和严重级别，不得把 L1 当成无证据的无限兜底。

#### L2：本轮一次性冻结验收依据

PM 必须在专项会话投递前创建带 ID、版本和外部记录 SHA-256 的 ABF，至少冻结：单一用户结果、目录／数据／接口／授权边界、非范围、适用 L1、不变量、`入口 × 状态 × 失败点 × 重复／重启`矩阵、固定夹具、逐行 Evidence、计数口径、Pass 公式、Rework 预算和新任务触发器。

ABF 不冻结产品需求，只冻结当前任务、当前候选边界的验收依据。没有 Frozen ABF 的任务不得进入 Ready。执行方在工程开始前可以质疑歧义；PM 必须在启动前解决并重新冻结。开始后：

- 新反例只有能映射到既有 L1/L2 时才可阻断当前候选。
- 为证明既有条款增加独立测试或 Evidence 不属于标准变化。
- 新增普通产品偏好或扩大能力、接口、数据、目录、风险和授权，属于 ABF 实质变化，必须关闭当前任务并新建任务。

#### PM 职责与移动终点禁令

PM 负责维护 L1、拆解单一结果、冻结 ABF、独立验收、问题分类、Rework 预算和账本。PM 不得替代专项实现，不得在提交后追加无法映射到 L1/L2 的标准，不得因“可以更好”否定满足冻结依据的候选，不得让同一能力包无限增加 attempt。

#### Rework 预算和新任务触发

- 执行侧首次提交 PM 前的同范围修正属于包内自检，不计正式 Rework。
- PM 或独立评审正式判定的 Rework 才计数，每任务最多两轮；Rework 期间 ABF 不变。
- 达到两轮仍未通过，或需要改变结果、风险、目录、数据、入口、能力、授权、架构、Schema/API、领域语义、ABF、风险关闭／重开、冻结、基线或阶段边界时，必须使用 `Closed — Acceptance Not Met`／`Superseded` 收口并新建任务。
- 当前 L1/L2 外的普通改进不阻断本轮，进入 Backlog／新任务候选。
- Blocked 只用于真实外部输入、授权、工具或条件不可用；解除阻断若需改变 ABF，同样新建任务。

#### 任务启动门

新任务状态顺序为 `Draft ABF` → `Frozen ABF` → `Ready / Acceptance Basis Frozen / Awaiting Task-card Delivery` → 投递执行。任务卡必须引用 ABF 路径、ID、版本和 PM 记录 hash；专项会话首份报告必须核对这些信息并声明是否有歧义。

### P3 受控能力包规则（D-0287 起）

仅适用于 P3-067 之后新建的任务，不追溯历史任务。PM 对有限 Stage 3 的同一受控能力默认创建单一能力包：同一风险边界、同一隔离工程目录、同一受控能力内的实现、回归、必要补测、Evidence 整理与文案对齐应合并执行。

- 能力包任务卡必须写明：能力包边界、内部整改授权、不可混入的风险／真实能力、完成定义、停止与重新确认触发器。
- 内部整改不另建任务，不额外触发用户决定，前提是仍在原任务卡的目录、风险、数据、能力和验收矩阵内；PM 将其记录在同一任务 Review／Evidence。
- 能力包完成后，进行一次正式 PM 验收、一次新隔离独立复评、一次用户采纳。执行 Agent 不得评审自身 P0 成果。
- 若独立复评或 PM 发现 P0/P1、明确 P2 bypass、Unknown／Not Implemented、Evidence 冲突、hash 实质变化或独立性不足，D-0401 起仅在问题映射到既有 L1/L2、ABF 不变且未达到两轮正式 Rework 上限时进行包内整改；其他情况关闭当前任务并新建任务。修复后必须重新独立复评。
- 下列事项永不合包：风险关闭／重开、工程基线恢复、Schema/API 或关键资产冻结、真实 DB／路径／Vault／Tauri/IPC／文件导出／云或第三方／同步／多设备／L3／外部用户、Stage 4 准入，以及任何跨风险边界或跨真实能力的决定。它们各自需要独立任务、独立复评和用户确认。

### 包内交付前自检关卡（D-0307；D-0369 补强，P3-074 起）

本关卡只适用于 P3-074 及之后新建，或尚未执行的受控能力包；不追溯 P3-073 及此前任何任务或历史结论。目标是将可预见的实现、测试、Evidence 与验收路径缺口留在同一能力包内解决，而不是降低 PM 或独立评审标准。

- 任务卡必须把自检列为 PM 提交前的完成条件：干净临时副本端到端演练；首次、幂等／重复、关闭重启；原子失败、半成品清理、失败披露、拒绝／阻断、fail-closed 与审计追溯；禁止能力和真实边界关闭态；历史只读资产 hash 保留。
- 执行侧必须保存可运行测试／runner 源码、逐项结构化结果、日志、快照、hash、Manifest、复跑说明及验收标准→测试→Evidence 矩阵；未适用或未覆盖项必须显式报告。
- 对要求本地 `file:` 动态／视觉 Evidence 的后续能力包，PM 必须在任务卡指定 `lifeos/templates/UI_DYNAMIC_EVIDENCE_CLOSURE_TEMPLATE.md` 或等价机器可读闭环表。每项动态验收动作须单独列出前置状态、操作、可观察结果、结构化结果 ID、视觉／日志路径与 SHA-256。刷新不得覆盖关闭重开，AX／静态可聚焦不得覆盖实际 Tab／Enter，概括性 PASS 数量不得覆盖逐项动作。
- 执行侧的 runner／自检脚本必须在 PM 提交前校验全部必填闭环行均为 PASS，或有任务卡允许的 N/A 理由；缺行、无 Evidence／hash 或只存在替代性观察时，结论必须为 Not Pass／Not Implemented，并留在同一能力包内补齐。PM 验收必须先核对此表，不得以总测试数替代。
- 上述范围内发现的问题由执行侧在原能力包内自行修正、补测、整理 Evidence 或对齐文案，不创建微型 Rework 任务、不额外请求用户确认、不单独拆分 PM 决策。
- PM 或独立评审仅在发现实质 P0/P1、明确合同违反、Evidence 冲突／不可复核、独立性不足、越权／范围扩大、真实能力默认关闭失效，或影响完成定义的 Unknown／Not Implemented 时记录正式 Rework。D-0401 起还须映射到既有 L1/L2；ABF 不变且未达到两轮上限才回原能力包，否则关闭并新建任务。修复后仍须必要 PM 验收与一次新的全新隔离独立复评。
- 风险关闭／重开、基线恢复、冻结、真实能力与 Stage 4 的独立任务、复评和用户确认要求不受影响。

### 本地 `file:` 动态 Evidence 浏览器预检（D-0352 起）

适用于任务卡要求以本地 `file:` 页面形成动态或视觉 Evidence 的受控能力包、PM 验收与独立复评；不追溯改写历史结论。目标是把浏览器表面差异在完整验证开始前一次性识别，避免把可预防的工具选择错误误记为工程 Rework 或环境 Blocked。

- PM 必须在任务卡中指定唯一允许的动态浏览器：**Google Chrome（`com.google.Chrome`）**，以及 task-local 临时副本的 `file:` 入口；该浏览器必须通过 **Computer Use 的 `@oai/sky`** 正常控制。In-app Browser 或 Browser-control 表面不得作为此类 `file:` 动态／视觉 Evidence 的执行环境。
- 专项会话创建干净临时副本后，必须先在新的 Chrome 标签页直接打开该 `file:` 入口，并在 Evidence 中记录：Chrome、入口 URL、加载结果、时间及副本 hash。该预检通过后，才执行完整动态矩阵。
- 不得通过 HTTP 服务、网络、CDP、命令行浏览器、浏览器持久化或绕过浏览器安全警告来替代该预检；直接在 Chrome 打开任务卡允许的本地 `file:` 副本不属于策略绕过。
- In-app Browser 或其他未被任务卡指定表面对 `file:` 的拒绝，只能记录为工具限制，**不得**单独判定工程 Rework 或任务 Blocked。
- 只有在新 Chrome 标签页按正常操作连续两次仍无法加载同一 task-local `file:` 副本，且已记录两次结果、未采用任何替代／规避路径时，才能将动态 Evidence 记为 Blocked；PM 仍须判断是否为真实外部阻断。
- 若预检通过而完整矩阵遗漏，属于同一能力包内的执行／Evidence 缺口，应在同一任务号补齐；P0 独立复评的补齐仍须使用与失败会话隔离的全新独立会话。
- 此规则不降低独立性、动态验证、视觉记录、hash、Manifest、PM 验收、用户采纳、风险、冻结或阶段关卡要求。
- 若任务发生 Rework，原独立 Review、Evidence、结构化结果和 Manifest 一律只读保留；新的运行必须写入 `lifeos/reviews/{任务ID}/rework/{attempt}/`。覆盖已有 Evidence 属于 Evidence 完整性缺口，PM 必须先记录并保全可得 hash／结论，再允许下一次重跑。

## 优先级规则

- P0：不完成会阻塞项目阶段推进。
- P1：重要，但不阻塞当前阶段。
- P2：有价值，可后置。
- P3：备忘或长期想法。

## 任务状态

- Backlog：已记录，未开始
- Ready：可启动
- In Progress：进行中
- Review：待 PM 验收
- Accepted：已验收
- Rework：需返工
- Blocked：被阻塞
- Dropped：决定不做
- Closed — Acceptance Not Met：达到 Rework 上限或决定终止，验收未通过且历史只读保留
- Superseded：边界或 ABF 发生实质变化，由具有新授权和新 ABF 的任务接替

## 验收、冻结与阶段状态口径

PM 验收必须明确区分三件事：

1. **任务是否完成并验收通过**：该专项会话是否按任务卡完成交付。
2. **对应资产是否冻结**：该交付物或其组合是否成为后续必须继承的基线。
3. **是否允许进入下一阶段**：是否满足阶段门槛，而不是只完成了一个任务。

固定使用以下状态：

| 状态 | 用于 | 含义 |
|---|---|---|
| Accepted | 任务验收 | 任务完成且交付物可作为后续输入；不自动代表资产冻结 |
| Accepted but Not Frozen | 资产状态 | 资产可用但仍有冻结前条件、独立评审或 PM 确认未完成 |
| Pass with Conditions | 评审结论 | 原则上可通过，但必须满足列明条件；条件未完成前不得无条件冻结 |
| Frozen | 资产状态 | 已经过必要评审与 PM 确认，成为后续任务必须继承的基线；必须注明冻结范围 |
| Rework | 任务或资产 | 需要返工后才能作为可靠输入 |
| Blocked | 任务或阶段 | 缺少必要输入、权限、决策或外部条件，无法继续 |

禁止把“任务 Accepted”自动解释为“资产 Frozen”或“可以进入开发”。任何 PM Review 都必须分别写明：

- 任务验收状态
- 资产冻结状态
- 是否允许进入下一任务
- 是否允许进入下一阶段
- 是否只是后续任务输入

## PM 验收回复规则

PM Review 文件可以完整，但 PM 主会话在聊天中默认只输出：

- 验收结论
- 资产状态
- 是否允许下一步 / 下一阶段
- 修改文件
- 需要用户确认的问题

聊天中不复述完整 Review，不重复粘贴任务卡全文，不重复粘贴大段历史决策。若用户需要细节，优先提供 Review 文件路径和关键摘要。

P3 快车道任务的聊天回复进一步压缩为：验收结论、测试摘要、风险状态、是否触发用户确认、修改文件、evidence 路径、下一步。除非退出快车道，不复述完整 Review。

## 任务下发标准

### 双用途安全语境前置规则

涉及权限、撤回、删除、安全边界、漏洞修复、反例、旁路或其他双用途技术语义的任务，PM 必须在启动语之后、任务信息之前加入真实、具体、可核对的“授权与安全语境”，并遵守：

- 明确 LifeOS 由用户本人拥有并授权维护，写清任务卡指定的本地工作区、候选代码、合成测试数据和防御性软件工程用途。
- 明确不授权外部或第三方目标、真实用户数据或凭据、未授权访问、网络扫描、真实攻击、持久化、数据获取或安全控制规避。
- 保留必要且准确的技术术语；不得通过隐晦改写、拆分成隐蔽步骤、降低测试强度或删除反例来规避安全分类。
- 授权声明在专项任务提示内完整出现一次；任务范围、非范围、目录权限、只读资产、用户确认、独立评审、停止条件和阶段关卡继续完整有效。
- 通用声明不是无限授权。实际操作若需要超出任务卡边界，专项 Agent 必须立即停止并回报 PM。
- Cyber safeguards 提示不得作为静默换模、降低推理强度、复用受污染会话或弱化 Evidence 的理由。
- 若同一会话已经多次被标记，应先检查 Trusted Access 状态；确需重新下发时，只能在用户或 PM 明确授权后使用补充真实语境的干净专项会话，且不得因此降低独立性与安全要求。

标准声明使用 `lifeos/templates/TASK_BRIEF_TEMPLATE.md`。普通低风险任务可填写 `N/A — 不涉及双用途安全语义`。不得为通过分类器编造所有权、授权、范围或用途。

- 模型选择理由
- 允许降级模型
- 禁止降级条件
- 必须升级条件

- 主责角色
- 协审角色
- 必须通过的评审关卡
- 背景

- 输入材料
- 核心问题

- 回复格式

## PM 验收输出标准

PM 主会话收到专项任务结果后，应读取交付物文件并输出：

- 任务验收结论
- 对应资产冻结状态
- 是否允许进入下一任务
- 是否允许进入下一阶段
- 是否只是后续任务输入
- 角色与关卡通过情况
- 是否需要独立评审
- 若已独立评审，独立评审路径与结论
- 需要用户确认的事项
- PM 整改建议文档路径
- 是否更新任务状态
- 是否需要更新决策、风险或开放问题

PM 整改建议必须保存到：

`lifeos/reviews/`

命名建议：

`{任务ID}_pm_review.md`

统一使用：

`lifeos/templates/PM_REVIEW_TEMPLATE.md`

P3 快车道任务可使用压缩 PM Review；但如发现 P0、需要关闭风险、恢复工程基线、启用真实能力、改变架构 / 领域 / AI 权限边界或进入下一阶段，必须退出快车道并恢复完整 PM Review。

## PM 验收口径

一项任务只有在满足以下条件时才可标记 Accepted：

- 回答了任务中的核心问题
- 输出符合指定模板
- 完整交付物已保存为文件
- 聊天回复提供了交付物路径
- 覆盖任务指定的主责角色、协审角色和评审关卡

任务标记 Accepted 后，PM 必须检查 `lifeos/FREEZE_STATUS.md` 是否需要更新。若涉及关键资产冻结、条件冻结或冻结状态变化，必须同步更新冻结状态看板。

## 定义线与验证线

Stage 1 起，LifeOS 后续工作分为两条线并行推进：

### 定义线

用于把 V1 写清楚、画清楚、让用户和执行会话理解清楚。

包括：

- V1 范围
- PRD
- 首页 / 今日页
- 信息架构
- 权限体验
- 原型修改方向
- 成功指标与非范围

定义线允许先写“条件性需求”，不必等待所有 Spike 完成。条件性需求必须标明依赖的验证项、失败时的降级方案或移出范围条件。

### 验证线

用于把定义线中的条件逐步验证为可实现、需降级或需移出范围。

包括：

- 技术 Spike
- 用户访谈
- 原型测试
- 性能验证
- 删除 / 撤回验证
- 权限理解测试
- 搜索、导出、同步、Obsidian 接入验证

验证线不得扩大 V1 愿景；它只负责验证定义线的条件、暴露风险、提出降级或范围调整建议。
- 明确区分事实、推断和建议
- 列出了对其他模块的影响
- 列出了需要 PM 决策的问题
- 没有擅自扩大任务范围
