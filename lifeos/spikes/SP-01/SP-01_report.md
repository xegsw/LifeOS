# SP-01 技术证据报告

## 结论

**Pass（限本 Spike 候选实现与本机环境）**。所有 15 项矩阵断言通过；1,000 次确定性随机强杀后逐次完整性检查失败 0，已回执内容丢失、hash 不一致、半写、不可解释重复、旧版覆盖和墓碑复活均为 0。该结论不冻结 SQLite、Schema、框架、同步或生产备份架构。

## 核心证据

- 基线：1,000 次提交、900 Artifact、1,000 Version、100 个双版本 Artifact；20 次等价重复全部复用，10 次冲突全部拒绝。
- 强杀：写前 270、写中 239、commit 后/回执前 249、回执后 242；回执后样本 242 条全部恢复；commit 后未回执的 249 条允许存在且存在，不被宣称为已回执。
- 故障：磁盘满与 I/O 写失败采用确定性注入；误报保存 0，事务前后计数不变，旧版本仍在，错误提供“保留编辑内容并重试/复制”的行动。
- 性能：基线 p95 0.078ms、p99 1.774ms、最大 5.725ms；长读、后台派生索引与被动 checkpoint 并发时 100 次捕获错误 0，p95 0.068ms、p99 0.188ms。
- 恢复：Online Backup API 在活跃写入中形成一致快照；恢复完整性 `ok`、计数一致、hash 不一致 0、删除/撤回活跃复活 0、待同步状态保留。
- 资源：活库约 772 KiB；主进程峰值约 20.0 MiB；完整运行约 33 秒。

## 回执耐久点

候选实现的顺序为 `BEGIN IMMEDIATE → Artifact/Version/Submission 同一事务写入 → COMMIT 返回 → ACK_SAVED`。子进程只在 `COMMIT` 返回后输出 `ACK_SAVED`。四时点测试使用真实 `SIGKILL`；因此写中事务被回滚，commit 后/回执前记录可以存在但不会被计入“用户已收到保存回执”，回执后记录必须存在。

## 状态合同

- 编辑中、保存中：仅 UI/调用态，不可输出已保存。
- 耐久已保存：commit 成功后的 `local_saved`。
- 离线本地已保存：commit 成功后的 `offline_local_saved`；与 `pending_sync` 正交。
- 失败：无回执，编辑器应保留原文并允许重试/复制。
- 恢复后：以数据库事实重建，不用客户端时钟猜测成功与否。

## 限制

真实验证的是进程级 `SIGKILL`、SQLite 事务恢复和确定性写错误注入；没有模拟突然断电、内核/控制器谎报 fsync、真实介质坏块或内核级 ENOSPC 发生在 commit 的每个内部字节位置。附件正文、云同步、多设备、生产恢复 SLA、加密、Schema 迁移和跨平台均未验证。上述限制不改变本任务明确断言的结果，但应进入后续架构与平台验证，不能被宣传为生产级耐久保证。
