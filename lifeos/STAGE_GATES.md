# LifeOS 阶段关卡与评审清单 V0.1

更新时间：2026-08-08

## 使用原则

本文件定义 LifeOS 在进入开发前，以及后续每个阶段推进时必须通过的评审关卡。

关卡不是管理流程，而是质量护栏。它的作用是让每个方案经得起产品、数据、AI、技术、用户和体验六个方向的检查。

任何准备冻结的 PRD、原型、数据模型、AI 机制或技术方案，都必须声明通过了哪些关卡，哪些关卡存在风险或例外。

## 独立评审要求

日常专项任务可以由执行 Agent 按指定角色进行多视角自审。

但以下关键冻结事项必须经过独立评审会话：

- V1 范围冻结
- 核心领域模型冻结
- AI 权限与信任模型冻结
- 技术架构冻结
- 首页/今日页 PRD 或关键原型冻结
- 进入正式 MVP 开发

独立评审会话必须满足：

- 只做评审，不重写主交付物
- 使用与冻结事项匹配的主审角色
- 明确哪些关卡通过、哪些未通过
- 明确必须整改项和可接受例外
- 输出文件到 `lifeos/reviews/`

PM 主会话必须同时读取主交付物和独立评审文件，才能做冻结决策。

## 五个固定评审关卡

### Gate 1：产品一致性评审

主审角色：产品架构负责人  
协审角色：体验设计负责人、PM

必须回答：

- 是否仍然服务个人终身外脑？
- 是否服务 V1 第一目标用户？
- 是否服务 V1 第一场景“开工/切换项目时的 5 分钟上下文恢复与下一步确认”？
- 是否服务“找回上下文 > 下一步/减少遗漏 > 今日重点”的价值排序？
- 是否偏向企业后台、IT 运维、开发者工具、普通笔记或普通任务管理？
- 是否把长期愿景提前塞进 V1？

通过标准：

- 有明确目标用户
- 有明确用户问题
- 能对应 V1 核心闭环
- 非范围清楚
- 未破坏产品宪法

### Gate 2：数据与来源评审

主审角色：数据 / 领域模型负责人  
协审角色：AI 信任与安全负责人、技术架构负责人

必须回答：

- 用户原文在哪里？
- 外部来源在哪里？
- AI 派生在哪里？
- 用户确认事实在哪里？
- 决定、行动、反馈如何记录？
- 来源、版本、权限、删除、导出如何表达？
- Obsidian Vault 只读来源如何处理？
- 派生产物是否可失效、可重建？

通过标准：

- 不混淆用户原文、AI 派生、AI 推断/建议和外部来源
- 关键内容可追溯到 Source/Artifact
- 用户确认和纠正有记录
- 删除、权限撤回和导出有处理方向
- 领域语义没有被误读为数据库表冻结

### Gate 3：AI 权限与信任评审

主审角色：AI 信任与安全负责人  
协审角色：产品架构负责人、数据 / 领域模型负责人

必须回答：

- AI 使用哪些数据？
- 数据权限来自哪里？
- 处理发生在本地、云端还是第三方模型？
- AI 输出是整理、生成、推断、建议还是候选行动？
- 用户如何确认、拒绝、纠正、撤回？
- 权限撤回后，派生物、缓存、索引和历史审计如何处理？
- 哪些操作必须明确确认？
- 是否触及心理、医疗、法律、财务等高风险边界？

通过标准：

- AI 输出身份清楚
- 证据和来源可见
- 重大操作不可自动执行
- 错误可纠正
- 权限撤回和派生失效有规则
- 没有用宽泛授权替代具体确认

### Gate 4：技术可行性评审

主审角色：技术架构负责人  
协审角色：数据 / 领域模型负责人、PM

必须回答：

- V1 是否能以合理成本实现？
- 哪些风险必须通过 Spike 验证？
- 是否存在过早重型架构？
- 是否存在后续不可扩展的硬伤？
- 本地保存、同步、搜索、来源追踪、Obsidian 接入、权限边界、派生失效是否可落地？
- 性能、容量、备份、导出、错误恢复是否有最低方案？

通过标准：

- 有明确技术风险清单
- 有 Spike 验证路径
- 未提前冻结数据库、微服务、图数据库、Kubernetes 等重型方案
- 关键质量属性可验证
- 技术方案服务 V1 闭环，不服务炫技

### Gate 5：用户价值验证评审

主审角色：用户研究 / 市场验证负责人  
协审角色：产品架构负责人、体验设计负责人

必须回答：

- 这是用户真实问题还是内部想象？
- 用户现在如何解决？
- LifeOS 是否明显更好？
- 用户是否愿意导入数据？
- 用户是否愿意学习新流程？
- 用户是否可能付费？
- 哪些证据会推翻当前方案？
- 如何用访谈、原型或行为数据验证？

通过标准：

- 有待验证假设
- 有反证问题
- 有研究或测试方法
- 不用表面活跃替代真实价值
- 不在无证据情况下设置留存/付费数字目标

## 进入开发前的硬门槛

正式进入 Stage 3 MVP 工程实现前，必须满足：

1. V1 第一目标用户已确认。
2. V1 第一场景已确认。
3. V1 范围和非范围已冻结。
4. 核心领域模型 V0.1 已通过。
5. AI 权限与信任模型 V0.1 已通过。
6. 技术可行性 Spike 计划已通过。
7. 首页/今日页 PRD 与原型方向已通过。
8. Obsidian Vault 只读接入策略已通过技术和权限评审。
9. 至少有一轮用户验证计划或验证结果。
10. 所有关键冻结项均完成独立评审，且 PM 主会话确认通过或记录例外。

若上述任一项未完成，只能做 Spike、原型、研究或文档工作，不进入正式 MVP 开发。

## 阶段推进标准

### Stage 0 结束标准

Stage 0 的目标不是把所有底层问题做到完美，而是达到“足够安全地进入 V1 定义”。

Stage 0 建议结束标准：

- 产品定位清楚。
- 目标用户清楚。
- V1 第一场景清楚。
- 核心领域模型有可用基线，或已明确冻结前条件、原因和下一步。
- AI 权限模型有可用基线，或已明确冻结前条件、原因和下一步。
- 技术 Spike 风险清楚，且关键阻断 Spike 已定义。
- 未冻结事项、未冻结原因和下一步已记录在 `lifeos/FREEZE_STATUS.md`。
- PM 明确允许进入 Stage 1 定义线。

Stage 0 结束不代表可以进入 MVP 开发；它只代表可以更安全地写 V1 范围、PRD、首页/今日页和信息架构。

### Stage 0 到 Stage 1

必须完成：

- 项目章程与产品宪法
- 目标用户与核心问题
- 核心领域模型
- AI 权限与信任模型
- 技术 Spike 计划

必须通过：

- Gate 1 产品一致性评审
- Gate 2 数据与来源评审
- Gate 3 AI 权限与信任评审

允许进入 Stage 1 时，尚未实测的技术能力必须以“条件性需求”进入定义线，并由验证线后续证明、降级或移出范围。

### Stage 1 到 Stage 2

必须完成：

- V1 范围冻结
- V1 PRD
- 首页/今日页 PRD
- Obsidian 接入需求
- 成功指标与非范围清单

必须通过：

- Gate 1 产品一致性评审
- Gate 2 数据与来源评审
- Gate 3 AI 权限与信任评审
- Gate 5 用户价值验证评审

### Stage 2 到 Stage 3

必须完成：

- 关键原型验证
- Obsidian 只读接入 Spike
- 本地保存与版本 Spike
- 来源追踪 Spike
- AI 派生与反馈 Spike
- 权限撤回/派生失效 Spike
- 搜索与项目恢复 Spike

必须通过：

- Gate 2 数据与来源评审
- Gate 3 AI 权限与信任评审
- Gate 4 技术可行性评审
- Gate 5 用户价值验证评审

### Stage 3 到 Stage 4

必须完成：

- 可真实使用的 MVP
- 基础导出
- 基础权限设置
- 错误和数据恢复策略
- Alpha 用户使用说明

必须通过：

- Gate 1 产品一致性评审
- Gate 3 AI 权限与信任评审
- Gate 4 技术可行性评审
- Gate 5 用户价值验证评审

## 任务级评审要求

每个专项任务应在任务卡中声明：

- 主责角色
- 协审角色
- 必须通过的关卡

专项交付物应说明：

- 本任务通过了哪些关卡
- 哪些关卡需要 PM 或后续任务继续确认
- 哪些风险应进入 `RISK_LOG.md`

PM Review 应说明：

- 验收结论
- 关卡通过情况
- 需要用户确认的事项
- 是否允许进入下一任务或下一阶段

## 例外机制

若某方案无法完全通过某个关卡，但 PM 判断仍需继续推进，必须记录：

- 未通过的关卡
- 例外原因
- 风险影响
- 适用范围
- 失效条件
- 后续补救任务

例外不得用于绕过以下底线：

- 用户原文保护
- AI 内容身份区分
- 重大操作确认
- 数据主权
- 高风险场景边界
- V1 范围控制
