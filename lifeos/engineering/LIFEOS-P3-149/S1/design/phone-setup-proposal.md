## 2. 类别映射：语义已知不等于本机文字已验证

下表的枚举语义来自 Apple HealthKit 分类；中文说明是本方案解释，不充当手机返回值白名单。[Apple 睡眠类别](https://developer.apple.com/documentation/healthkit/hkcategoryvaluesleepanalysis)

| 输入或类别 | 已证实部分 | 本机映射状态 | 接收与展示规则 |
|---|---|---|---|
| “睡眠时间” | 任务卡记录单次显示该文字 | 未验证 | 原样保留；mappingStatus=unknown；不得转成 asleep |
| inBed | 卧床类别，与睡着不同 | 未验证对应中文返回 | 只有可靠枚举证据成立才归为卧床；不计睡眠 |
| awake | 清醒类别 | 未验证对应中文返回 | 可靠枚举证据成立才归为清醒；不计睡眠 |
| asleepUnspecified | 未细分阶段的睡眠 | 未验证对应中文返回 | 映射成立后可进入已识别睡眠区间 |
| asleepCore / asleepDeep / asleepREM | 睡眠阶段 | 未验证对应中文返回 | 映射成立后可进入已识别睡眠区间 |
| 其他文字、缺值或无法转换的值 | 无确定类别证据 | unknown | 保留未知项及原因，不能丢弃后宣称全量 |

首版映射表为空，所有快捷指令类别文字默认 unknown。用户不必逐项截图或把真实值发给 Agent。后续若要启用映射，应由受控桥接取得稳定枚举，或以版本绑定的非敏感类别测试证明“动作字段 → 枚举”的对应；单凭中文字面、用户普通点击、类型为睡眠均不够。当前提案不要求先完成该桥接才能显示未知区间，也不实现桥接。

已确认的 asleep 区间至多按来源组分别取并集，标“已识别区间”；旁边始终显示“查询覆盖未知”和未识别情况。未知项为零也不能证明完整读取。不同来源不选最大值、不混成个人总量；没有来源字段时按“未区分来源组”显示。重叠的类别冲突保留，不推断清醒如何冲销睡眠，不生成健康判断。

## 3. 固定窗口、跨午夜与遗漏

推荐首轮目标窗口固定为 **2026-09-08T00:00:00+08:00 至 2026-09-09T00:00:00+08:00**，右端不包含。地区固定 Asia/Shanghai；后续重采仍使用完全相同窗口，不采用滚动“最近 24 小时”。这是一段日期观察，不命名为“昨夜完整睡眠”。

为减少午夜前开始的常见区间遗漏，手机查询候选范围拟为 **2026-09-07T00:00:00+08:00 至 2026-09-09T00:00:00+08:00**。仅查询睡眠类型；保守使用“开始日期在候选范围内，结束日期不晚于候选上界”的有界策略，随后自行比较原始起止时间。此范围只代表允许读取的候选范围，**不保证取得所有与目标窗相交的长区间**：早于候选起点开始、晚于候选终点结束的记录可能遗漏，必须保留 coverage=unknown 和 boundaryCoverage=unknown。若手机动作无法表达该有界筛选，不改为无界查询，停止导出并报告配置不支持。

收到候选后，仅保留 `originalStart < windowEnd && originalEnd > windowStart` 的项。展示裁剪为 `max(originalStart, windowStart)` 至 `min(originalEnd, windowEnd)`；原始起止保留，零长区间不计时。固定时区只适用于首轮，不把自然日一律按 86,400,000 毫秒推广到 DST 或旅行场景；地区或 offset 改变需新 scope。

纯合成例：区间 D−1 日 23:00 至 D 日 07:00 与 D 日零点窗口相交，窗口内显示 00:00–07:00；原始 23:00 起点仍可查。S1 的 fully-contained 会排除这整条跨窗记录，不能把剩余数据解释为全天睡眠。改用中午到中午只能减少某些常见切分，不能消除边界遗漏，所以不作为完整性的补救。

相邻窗口分别裁剪，不把同条区间的完整时长在两天重复相加。无样本 ID 时不声称识别出跨批次的同一条记录或删除事件；保存每批次观察。首轮只有一个目标窗口，不自动扩展其他日期。

## 4. 手机快捷指令：一次搭建的动作与变量流

以下为待在手机搭建的配方。动作搜索名沿用当前已观察到的中文菜单；未经过本轮实机逐动作验证。用户一次搭建后手动运行，首轮不设置自动化、定时器或锁屏触发，不使用“记录健康样本”。

| 顺序 | 动作与设置 | 输出及流向 |
|---|---|---|
| 1 | 用“日期”和“设定变量”固定上述 WindowStart、WindowEnd、FetchStart、FetchEnd；用“文本”设 sourceGroupKey=phone-sleep-visible-v1、queryKey=start-bounded-intersection-v1 | 固定配置，不由健康正文生成身份 |
| 2 | “当前日期”记 QueryStartedAt；本轮运行标识用“生成 UUID”（若该动作不可用，则由一次“要求输入”提供只含字母数字和连字符的新批次名） | BatchId 仅为导出批次身份；重传同一文件不换 ID，新查询换 ID |
| 3 | “查找健康样本”：类型睡眠；日期按第 3 节候选范围；不填“值=睡眠时间”等未验证筛选；开始日期升序；限制设 257 项作为 256 项容量的超限哨兵 | Candidates；不沿用先前限 1 项设置 |
| 4 | “计数”；结果达到 257 项则“显示结果”提示超限并“停止此快捷指令” | 不保存截断结果；少于 257 也不证明平台无其他限制或权限完整 |
| 5 | “重复每一项” → “获取健康样本的详细信息”，分别取开始日期、结束日期、值，来源可用时取来源 | Start、End、CategoryText、SourceText；值只保留文字，不强制转数字 |
| 6 | 嵌套“如果”执行目标窗相交判断；日期缺失、无法比较或 End≤Start 则整次停止，不静默漏行 | 只对相交项构造词典；未知类别并非失败，继续保留 |
| 7 | 用“格式化日期”的 ISO 8601 格式保留明确 offset；用“词典”组成 originalStart、originalEnd、categoryText、mappingStatus=unknown、sourceText（缺失用固定“未区分来源”） | “添加到变量”累积 Rows；不在文字模板内拼接 JSON，不把时间转换失败当 0 |
| 8 | 循环结束后取当前日期为 CapturedAt；“词典”建立批次封装，含 schema、BatchId、固定配置、Rows、rowCount、coverage=unknown、pagination=unknown、boundaryCoverage=unknown、mappingVersion=unmapped-v1 | schema 建议 health-phone-observation-v1；这不是旧 S1 有效输入 |
| 9 | 将词典序列化为 JSON 文本，通过“存储文件”保存 `<BatchId>.json`；首次手动定位第 7 节专用 iCloud 目录，拒绝覆盖同名文件 | 一个完整批次文件；保存失败不显示接入成功 |
| 10 | “显示结果”仅提示“文件已保存，等待 App 接收”；由用户自己在 App 查看接收状态和区间 | 不要求截图，不把本地保存等同 iCloud 到达或 DB 接收 |

Rows 应明确初始化为空列表；若该版本无法在词典内保留空数组，接收协议允许省略 rows 仅当 rowCount=0，并规范化为空，不能把任意缺字段视为空结果。此差异须在下一实施合同固定。建议先用内置非敏感测试词典检查数组、数字、Unicode 和日期序列化，再接真实查询；当前仅交配方，没有生成或签名 `.shortcut` 安装文件。

文件完整发布属于传输验证，不证明健康数据完整。拟接收器须对同名文件采用一次打开、有限读取、两次一致内容检查、完整 JSON 解析和 rowCount 校验；iCloud 写入中或不同步时等待/拒绝，不接收半包。批次同 ID 同内容幂等，同 ID 异内容拒绝；文件和库不回写健康。上述接收器行为尚未实现，不声称仅两次稳定读取能证明云同步完成。

## 5. 完整性未知时仍有可用结果

HealthKit 的读权限不能由保存权限状态接口证明；Apple 明确限制应用判断用户是否授予读权限。因此查找成功、无报错、空返回或用户点击允许均不是全量凭证。[Apple authorizationStatus 说明](https://developer.apple.com/documentation/healthkit/hkhealthstore/authorizationstatus%28for%3A%29)

观察视图应显示“本次可见的睡眠来源记录”，附目标窗、查询时刻、接收时刻及覆盖未知。unknown 类别仍显示原文字与起止，所有行都未知时仍能看到区间；不显示睡眠分钟数、不补 0、不替代确认状态，也不假装结果没有价值。

新批次只切换“正在查看的批次”，旧批次保留可回看；空批次显示“此次未返回记录，无法判断无数据还是权限/查询限制”，旧批次明确标历史。新时间相同内容不刷新样本观察时间，较旧批次不成为最新观察；异常文件不改变已展示批次。最新批次缺少某行仅说明该次没有看到，不认定删除。
