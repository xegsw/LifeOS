# LifeOS 项目统一背景包 V0.1

更新时间：2026-08-09

## 项目一句话

LifeOS 是一个由用户掌控、可追溯、可迁移的个人终身外脑：它可靠承接原始记录，连接知识、行动、项目与生活领域，并让 AI 在明确权限内帮助用户理解上下文、识别重点和推进下一步。

## 项目愿景

LifeOS 的长期目标不是做一个更漂亮的笔记软件，也不是做企业管理后台，而是成为个人的长期智能基础设施。

它最终可以在不同场景中扮演：

- 职业规划师
- 项目经理
- 生活帮手
- 学习教练
- 知识整理助手
- 情绪与心理支持型导师
- 个人决策参谋
- 主动发现问题并推动解决的 AI 合作者

“全知全能”是北极星，不是 V1 目标。项目早期必须先把底层数据、信任、权限、来源、记忆和执行闭环打牢。

## 产品定位

LifeOS 是：

- 个人长期使用的终身外脑
- 个人原始记录的承接层
- 个人知识、行动、项目、领域之间的连接层
- AI 辅助理解、整理、推断、规划和执行的智能层
- 用户可控、可追溯、可迁移的个人数据系统

LifeOS 不是：

- 企业管理后台
- IT 运维中心
- 单纯的任务管理器
- 单纯的笔记软件
- 单纯的 AI 聊天机器人
- 单纯的日历或待办应用
- 以焦虑驱动留存的效率工具

## 核心用户假设

V1 第一目标用户确认为技术型独立产品构建者。该人群是首个验证样本，不代表 LifeOS 被重新定位为开发者工具。

技术型独立产品构建者指：

- 个人或极小规模协作，但 LifeOS 服务的是其个人上下文，不是团队管理。
- 同时维护 1-3 个软件、AI 产品、技术型副业或长期项目。
- 每周多次在编码、产品思考、用户反馈、研究和个人事务之间切换。
- 已使用至少四类工具承接信息，并有主动记录和回顾习惯。
- 已使用 AI 进行编码、研究、写作或规划。
- 对本地保存、可导出、来源和模型数据边界有明确偏好。

V1 次级对照用户为：

- 技术/AI 产品经理
- 多客户独立顾问

这些用户通常有以下痛点：

- 信息散落在聊天、文档、网页、笔记、代码、日历和脑中。
- 记录很多，但难以形成持续可用的上下文。
- 项目、知识、任务、目标彼此断裂。
- 每天不知道真正重要的事情是什么。
- AI 可以回答问题，但不真正理解自己长期的生活和项目背景。
- 对数据主权、隐私、可迁移性有较高要求。

## 产品宪法

以下原则在 Stage 0 作为强约束接受，后续可通过 PM 决策记录修订。原则优先级高于单个功能设计。

### 数据主权

- 用户拥有自己的数据。
- 用户应能导出、迁移、删除自己的数据。
- 用户应能控制哪些数据进入云端、模型和自动化流程。

### 原文保护

- 用户原始记录不得被 AI 静默改写。
- AI 可以生成摘要、标题、标签、关联、建议，但必须作为派生层存在。
- 用户应能查看原始内容与 AI 派生内容之间的关系。

### 来源可追溯

系统必须区分：

- 用户原文
- 用户确认后的事实
- AI 整理内容
- AI 推断
- AI 建议
- 外部引用来源

重要 AI 输出应尽量记录：

- 输入来源
- 外部引用
- 模型或工作流版本
- 生成时间
- 用户反馈或确认状态

### 人在回路

AI 可以主动帮助用户发现问题、提出建议和生成计划，但以下行为必须用户确认：

- 对外发送消息
- 创建或修改重要日程
- 花钱、订阅、购买
- 删除重要数据
- 分享隐私内容
- 涉及健康、心理、法律、财务等高风险建议的执行
- 任何难以撤销或影响他人的动作

### 可审计与可逆

- 重要操作应可追溯。
- 重要派生结果应可解释其来源。
- 高影响操作应尽量可撤销。

### 模型可替换

- 不把产品核心能力绑定在单一模型或单一供应商上。
- 应通过模型网关、结构化输出、任务工作流和评估机制保持可替换性。

### 健康依赖

目标是让用户因真实价值、信任和掌控感形成高度依赖，而不是通过焦虑、操控或成瘾机制留住用户。

## 核心领域语义工作模型

当前接受 11 个对象 + `Link` 作为 V0.1 领域语义工作模型，但这不是数据库表、API 或 UI 模块冻结。

核心领域模型当前状态：`LIFEOS-P0-003` 与 `LIFEOS-P0-009` 已共同冻结为 **核心领域模型 V0.1 语义基线**。

本次冻结仅限语义定义、边界、身份 / 来源 / 确认 / 失效不变量、四类命令后果、Derivation 约束继承、状态分离、墓碑优先 / 导出不复活、AuditEntry 防反向识别。不冻结 Schema、API、UI、存储、事件流、L3 上线范围、删除 / 备份 SLA、供应商或技术架构。

V0.1 领域语义包括：

- `Project`：用户正在推进的上下文边界，用于回答“今天从哪里继续”。
- `Artifact`：具体内容本体，例如用户原文、Obsidian 笔记、文件、网页快照、摘录。
- `Source`：内容从哪里来、以什么权限取得，例如 Obsidian Vault、URL、本地输入通道。
- `Assertion`：可判断真假的陈述，例如用户确认事实、外部主张、AI 推断。
- `Decision`：用户做过的决定及理由。
- `Action`：可确认、执行和反馈的行动。
- `Event`：对项目或用户有意义的变化。
- `Derivation`：AI 或算法基于输入生成的派生产物，例如摘要、候选关联、推断、建议、索引。
- `Feedback`：用户对内容、AI 输出、行动或决定的确认、拒绝、纠正、完成、延期等响应。
- `Authorization`：用户授予系统在特定范围、目的、位置和时效内处理数据的许可。
- `AuditEntry`：关键读取、生成、授权、删除、导出、状态变更等操作记录。
- `Link`：对象之间有来源、确认状态和有效期的重要关系。

关键划界：

- `Project` 是 V1 核心上下文边界，但不是企业项目容器。
- `Source` 与 `Artifact` 必须分离。
- `Decision` 独立，负责保留“为什么这么决定”。
- `Action` 独立，`Commitment` 是行动类型/约束，`Next Step` 是某时点角色或用户选择。
- 重要 `Link` 需要来源、确认状态和有效期；普通展示关系可简化。
- 权限撤回后，相关派生物、缓存和索引需失效或进入待检查状态。

## V1 核心假设

V1 不追求完整生活自动化，而是验证 LifeOS 是否能成为用户每天可信赖的外脑入口。

V1 重点验证：

- 用户是否愿意把原始记录持续输入 LifeOS。
- 系统是否能可靠保存并恢复上下文。
- AI 是否能帮用户识别今日重点。
- AI 是否能把混乱记录转成可行动的下一步。
- 用户是否能理解 AI 内容来自哪里。
- 用户是否愿意根据系统建议调整行动。

V1 第一价值排序为：

1. 找回上下文
2. 下一步/减少遗漏
3. 今日重点

知识整理是支撑能力，不是 V1 的终点叙事。

## V1 基础闭环

V1 的核心闭环已确认以“捕获-保存-整理-找回/今日-确认行动-反馈”为范围判断基准：

1. 用户低摩擦捕获原始记录。
2. 系统可靠保存，满足离线捕获和本地可靠落盘要求。
3. AI 在明确权限内整理、分类、摘要和关联。
4. 用户通过检索或今日页找回上下文。
5. 系统呈现带理由和来源的今日重点或下一步。
6. 用户确认、纠正、拒绝或执行。
7. 系统沉淀结果与反馈，持续改善上下文。

## V1 第一场景

V1 第一场景确认为“开工/切换项目时的 5 分钟上下文恢复与下一步确认”。

这里的“5 分钟”不是严格计时功能，而是价值标准：用户在开始工作、午后恢复、跨项目切换、离开数日后返回或收到新反馈后，能快速回答：

- 上次做到哪里？
- 最近这个项目发生了什么？
- 有哪些未处理的记录、反馈、承诺或问题？
- 当时为什么这么决定？
- 今天最值得推进的下一步是什么？
- 这个下一步依据哪些原文、来源或 AI 推断？

## V1 AI 主动性边界

V1 AI 总能力上限为：可读、可整理、可建议，不可替用户确认。

V1 AI 主动性主体限制在：

- L0：被动读取、回答查询、展示原文、检索。
- L1：低风险派生，例如摘要、标签、候选关联、草稿。
- L2：主动建议，例如提醒冲突、提出今日重点或下一步。

L3 仅允许小范围、明确授权、可逆的内部动作。L4-L5 不进入 V1 自动执行。

高风险场景，包括心理、医疗、法律、财务等，V1 只做信息辅助或草稿，不做诊断和自动执行。

## AI 权限与信任模型

`LIFEOS-P0-004` 与 `LIFEOS-P0-007` 已共同冻结为 **AI 权限与信任模型 V0.1 原则与语义基线**。本次冻结不包含技术实现、删除 / 备份 / 第三方清理 SLA、供应商能力、授权 UI、任一 L3 上线范围、数据库、API、模型网关或技术架构。

核心规则：

- AI 可以读取、整理、摘要、分类、检索、发现关联、提出今日重点和候选下一步。
- AI 不可以替用户确认事实、承诺、决定、当前下一步或重大行动。
- 所有 AI/算法输出必须保留 `Derivation`，记录输入版本、目的、处理位置、授权、工作流/模型版本、输出身份、生成时间和有效状态。
- 用户确认、拒绝、纠正、忽略、完成、延期和撤回必须以 `Feedback` 保留历史。
- 授权采用六维模型：主体、范围、动作、目的、位置、时效。
- AI 推断、候选 `Action`、候选 `Decision` 必须经对象级确认才能变为用户确认状态。
- 撤回后必须先阻断活跃使用，再追踪物理清理状态。
- 历史审计只保留不可还原内容的最小元数据。
- Obsidian 本地读取/索引、AI 派生、云同步、第三方模型处理采用分层授权。
- 高风险场景不做主动诊断/评分，L3-L5 全部排除。

L3 内部可逆动作可进入 PRD/Spike 候选白名单，但不代表 V1 必做范围。后续必须验证其用户价值、撤销成本、状态一致性和审计成本。

## V1 范围 V0.1（已冻结）

`LIFEOS-P1-001` 与 `LIFEOS-P1-003` 已共同冻结为 **V1 范围 V0.1 产品范围与条件合同**。

本次冻结覆盖：

- V1 一句话范围。
- 第一目标用户、第一场景和价值排序。
- 经 P1-003 收紧后的 MoSCoW 与 Non-goals。
- 条件性需求、Spike 依赖和失败降级。
- 首页 / 今日页范围输入边界。
- 指标框架与最小用户验证合同。
- 四类命令在 V1 范围层的继承。

本次冻结不覆盖：

- 完整 V1 PRD。
- 信息架构和详细交互。
- 首页 / 今日页 PRD。
- Stitch 原型。
- 用户验证结果、样本量和数字阈值。
- Obsidian 实现。
- 技术 Spike 结果。
- 数据库、API、同步、搜索、导出和清理实现。
- 技术栈 / 技术架构。
- 任一 L3 上线范围。
- 删除 / 备份 / 第三方清理 SLA。
- 供应商能力、工程排期、Stage 2 或 Stage 3 准入。

V1 最小闭环是：用户能捕获并可靠保存项目原始记录，借助最低找回路径恢复可信 Project 上下文，获得至多一个有充分依据的候选下一步，完成核对与反馈，同时保有最低权限、删除、导出和审计保障。

V1 Must 的最低切片：

- 捕获与保存：支持文本、链接、文件 / 来源指针。文件最低能力仅包含指针及必要来源元数据；完整文件摄取、正文解析、附件管理、格式覆盖和内容提取属于 Should / 条件项。
- 找回与恢复：以 `Project` 为边界，通过 FTS + 元数据形成最低找回路径，并能回到相关 `Source / Artifact`。向量检索、混合重排、跨源自动关联及专用搜索基础设施不是 Must 前提。
- AI 最低产出：在有效授权与证据范围内，提供可核对的 Project 恢复信息，并在依据充分时提出 1 个候选下一步；若依据不足，应显示证据缺口或“暂无可靠建议”，不得强行生成。
- 支撑手段边界：摘要、分类、候选关联是形成恢复信息和候选下一步的可选手段，不要求各自成为独立、完整、通用的 Must 功能面。首页 / 今日页的 1-3 个候选只是呈现上限，不是强制凑数。
- 用户权威与信任底线：用户能核对原文 / 外部来源与 AI 派生，确认、编辑、拒绝、纠正、完成或延期；AI 不替用户确认事实、决定、承诺或当前下一步。

四类用户命令必须在后续 PRD 中显式区分：

- `revoke_processing`：撤回处理许可。
- `disconnect_source`：断开来源。
- `delete_content`：删除内容。
- `retract_feedback`：撤回反馈 / 纠正 / 确认。

四者不得互相冒充；活跃阻断、物理清理状态、用户确认历史、来源连接和内容保留必须分别处理。

Obsidian Vault 在 V1 中固定为 **Should Have + 条件性需求**：它是首批用户高价值来源和重要验证对象，但不是 V1 最小闭环成立前提。只有 SP-02 / SP-03 通过，并满足只读、来源身份、分层授权、不写回原文时，才进入实现范围；失败时降级为手工导入 / 来源指针或移出 V1，由 PM 记录范围结果。

## V1 外部来源边界

V1 外部来源最低接入深度为：

- 文本
- 链接
- 文件 / 来源指针
- 必要来源元数据

文件能力的 Must 最低切片仅包含文件 / 来源指针及必要来源元数据；完整文件摄取、正文解析、附件管理、格式覆盖和内容提取属于 Should / 条件项。

暂不追求 GitHub、日历、邮件、聊天、网盘等全量连接器。后续连接器应根据目标用户真实来源优先级逐步加入。

Obsidian Vault 是 V1 的 Should Have + 条件性需求，可作为优先验证的本地文件型来源，但不是 V1 最小闭环成立前提。只有 SP-02 / SP-03 通过，并满足只读、来源身份、分层授权、不写回原文时，才进入实现范围。

若进入 V1 实现范围，Obsidian Vault 可支持：

- 可读取 `.md` 笔记正文、文件路径、文件名、创建/修改时间。
- 可解析 YAML frontmatter、标签、Markdown 链接、`[[双链]]`、附件路径。
- LifeOS 应保留 Vault、文件、段落/块、时间和来源指针。
- AI 摘要、关联、下一步建议等派生内容默认保存在 LifeOS 派生层，不直接写回 Obsidian 原文。
- V1 不默认做 Obsidian 插件、双向同步或自动写回。
- 若 SP-02 / SP-03 失败，Obsidian 降级为手工导入 / 来源指针或移出 V1，由 PM 记录范围结果。

V1 暂不包含：

- 完整职业规划师
- 医疗、心理或法律诊断
- 自动替用户做重大决策
- 自动购物、付款或对外发送重要消息
- 完整移动端
- 多人协作
- 企业管理功能
- KPI 管理后台
- 多 Agent 组织系统
- 长期自主执行 Agent
- Kubernetes 或微服务基础设施
- 强依赖图数据库
- 强制本地大模型
